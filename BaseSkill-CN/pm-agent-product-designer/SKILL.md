# PM-Agent 产品设计 Skill

## 触发场景

当用户提出以下类型请求时使用本 Skill：

- 设计项目模块、页面、功能清单、MVP 范围；
- 梳理项目经理、研发、测试、管理层、个人开发者等角色视角；
- 将口头想法整理成产品需求、用户故事、验收标准；
- 判断某个功能是否进入当前阶段，或是否后置；
- 定义或维护统一产品术语表；
- 评审业务边界，避免项目管理、知识库、BI、OA、DevOps 混在第一版。

## 目标

帮助 Claude 围绕 PM-Agent 智能项目管理 Agent 平台进行产品设计，明确用户、边界、功能优先级、业务流程、术语和验收标准，确保后续后端、前端、数据模型、Agent 设计使用同一套产品语言。

---

## 一、产品定位与优先级

### 1.1 第一目标用户

第一版以**个人开发者 / 单人项目管理者**为核心目标用户，优先满足个人或小团队管理项目、需求、任务、风险和 Agent 辅助分析的需要。

### 1.2 第一版价值重心

第一版更强调 **Agent 智能分析能力**，但不能只做演示聊天页；必须把项目、任务、风险等基础业务逻辑确认下来，使 Agent 有真实业务数据可分析。

### 1.3 MVP 范围原则

1. MVP 尽量完整覆盖核心业务链路，可以接受部分体验或自动化能力稍弱；
2. 优先确认业务逻辑、实体关系、状态流转和 Agent 介入点；
3. 第一版先按个人项目级别设计，企业级多租户、复杂 RBAC、完整审批流后置；
4. 每个阶段必须能形成前后端闭环展示，避免只堆后端或只做页面。

---

## 二、模块边界

### 2.1 核心模块

| 模块 | 第一版定位 | 不负责什么 |
|---|---|---|
| 项目管理 | 项目基础信息、成员、进度概览 | 不做复杂项目组合管理 |
| 需求管理 | 需求记录、优先级、拆解入口 | 不做完整需求评审流程 |
| 任务管理 | 任务创建、分配、状态流转、看板展示 | 第一版不做复杂拖拽依赖编排 |
| 迭代管理 | 支持敏捷 Sprint 与瀑布阶段的统一周期容器 | 不做完整项目管理方法论配置器 |
| 风险管理 | 风险登记、Agent 识别、PM 确认、处理跟踪 | 不做企业级风控审批 |
| Agent 助手 | 项目问答、风险分析、需求拆解、周报草稿 | 不绕过业务 API 直接改库 |
| 报告中心 | 周报草稿生成、人工编辑确认 | 第一版不做复杂报表平台 |

### 2.2 阶段控制

- 第 1~2 阶段：项目、需求、任务、迭代、风险的核心业务闭环；
- 第 3~4 阶段：Agent 对话、工具调用、Trace、需求拆解、周报草稿；
- 第 5 阶段：风险分析、异步任务、规则增强；
- 第 6 阶段：RAG 知识库，不提前到第一版；
- 第 7 阶段：通知、审计、报告导出、数据看板、企业级增强。

## 三、统一产品术语表

本 Skill 负责维护 `docs/00-术语表.md`。其他 Skill 只引用并遵守术语表，不各自发明新术语。

### 3.1 术语治理规则

1. 新增业务概念前，先判断是否已有术语可复用；
2. 确需新增术语时，先更新 `docs/00-术语表.md`，再进入数据建模、接口设计和前端页面设计；
3. 术语表必须包含：标准中文名、英文标识、一句话定义、范围边界、禁用同义词、关联术语；
4. 代码命名、表名、API 路径、页面文案、Prompt 模板必须使用术语表中的标准叫法；
5. Agent 可以识别同义词，但对用户输出时必须回归标准术语。

### 3.2 已确认核心术语

| 标准术语 | 英文标识 | 说明 |
|---|---|---|
| 项目 | project | 一个独立交付目标，包含需求、任务、风险、报告等 |
| 需求 | requirement | 用户视角的业务诉求，可被拆解为任务 |
| 任务 | task | 开发执行的最小管理单元 |
| 迭代 | iteration | 统一承载敏捷 Sprint 与瀑布阶段的时间周期；代码、表名、API 使用 `iteration`，Sprint/阶段作为同义词 |
| 风险 | risk | 可能影响交付的不确定因素，区别于已经发生的问题 |
| 问题 | issue | 已经发生并影响进度或质量的事项 |
| 报告 | report | 周报、阶段报告等结构化输出 |
| Agent | agent | 具备工具调用和推理能力的智能执行者，不等同于底层模型 |
| 工具 | tool | Agent 可调用的受控业务能力 API |
| Trace | trace | Agent 单次决策的可追溯记录 |

## 四、产品方案输出格式

设计模块或功能时，按以下结构输出：

```markdown
# 产品方案：[模块/功能名称]

## 背景
（为什么现在要做，属于哪个阶段）

## 目标用户
（第一版优先个人开发者 / 单人项目管理者；如面向其他角色需说明）

## 业务价值
（解决什么问题，为什么值得做）

## 涉及术语
（复用术语 / 新增术语 / 禁用同义词；如新增术语，提示更新 docs/00-术语表.md）

## 功能范围
### 必须做
### 建议做
### 后置做

## 页面与交互
（页面清单、关键操作路径、状态反馈）

## 核心流程
（用步骤或 Mermaid 表达）

## 字段与规则
（关键字段、校验、状态、权限、Agent 介入点）

## MVP 范围
（当前阶段具体落地内容）

## 后续增强
（明确后续阶段，不混入当前实现）

## 验收标准
（可手动验收、可演示）

## 待确认问题
（只列真正影响设计或实现的问题）
```

## 五、工作流程

1. 先对齐当前阶段，判断功能是否属于 MVP、后续增强或暂不做；
2. 检查 `docs/00-术语表.md` 是否已有相关术语；
3. 明确目标用户与业务价值，不从技术方案倒推产品需求；
4. 拆分必须做 / 建议做 / 后置做，控制范围；
5. 输出可交给后端、前端、数据模型和 Agent Skill 继续细化的产品方案；
6. 对涉及高风险操作、Agent 自动写业务、权限变更的功能，明确人工确认边界。

---

## 六、不可越界

以下事项必须先经用户确认：

- 新增核心业务概念但未进入术语表；
- 把第 6 阶段 RAG 或第 7 阶段企业级能力提前塞入第一版；
- 第一版引入完整审批流、复杂 OA、BI、DevOps 或组织级 SaaS 能力；
- 改动已确认术语（如把 `iteration` 改成 `sprint` 或 `phase`）；
- 让 Agent 自动执行删除、权限变更、对外通知等高风险动作而不要求人工确认。
