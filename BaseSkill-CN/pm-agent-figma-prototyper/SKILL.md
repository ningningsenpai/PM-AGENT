# PM-Agent Figma 原型绘制 Skill

## 目标

为 PM-Agent 创建正式的 Figma 页面原型，用于直接指导后续 Vue 3 + Naive UI 前端实现。输出应像真实产品界面，而不是设计说明板。绘制时保持已确认的 PM-Agent **Warm Linear 工作台风格**，并按后续代码生成与交互评审的需要组织画板。

使用本 Skill 时，应配合官方 Figma MCP Skill：

- 每次调用 `use_figma` 写入前，先加载 `figma:figma-use`；
- 绘制完整页面或多区块界面时，同时加载 `figma:figma-generate-design`；
- 新建 Figma 文件前，先加载 `figma:figma-create-new-file`；
- 前端架构、组件边界和视觉 token 参考 `pm-agent-frontend-builder`。

---

## 一、触发场景

当用户提出以下请求时使用本 Skill：

- 在 Figma 中创建正式前端设计稿；
- 使用 Figma MCP 绘制 PM-Agent 页面原型；
- 将已确认的 PM-Agent 视觉方向转化为具体页面；
- 创建用于后续 Vue 实现参考的设计稿；
- 在同一个 Figma 文件中组织多个业务界面和交互状态；
- 精修或更新 PM-Agent Figma 界面，同时保持 Warm Linear 风格。

如果只是做普通前端方案规划、不需要 Figma 输出，应使用 `pm-agent-frontend-builder`。

## 二、已确认视觉方向

使用已确认的 **Warm Linear 工作台风格**：

- 暖白 / 米白背景：`#F8FAF5`、`#FFFFFF`；
- PM Blue：`#2F7DF6`、`#1F66D1`，用于主操作、选中导航、进度；
- PM Green：`#26B983`、`#15966A`，用于健康推进和完成状态；
- PM Yellow：`#F5B83D`、`#D8911E`，用于 Agent 洞察、风险提示、注意线索；
- 主文本：`#132033`；
- 次级文本：`#667085`；
- 弱化文本：`#98A2B3`。

建议视觉比例：暖白 / 背景 65%，蓝色 20%，绿色 10%，黄色 5%。

品牌主张：

> 把项目状态变成可追踪的执行线索。

Logo 方向：

- 深色圆角标识底；
- 蓝色执行轨道；
- 绿色状态节点；
- 黄色洞察节点；
- Trace 连接线。

在卡片、状态条、时间线、进度、Agent 洞察区域中复用“执行线索线”视觉符号。

## 三、正式 Figma 画布规则

正式设计稿不是思路板，应只呈现产品界面。

### 3.1 可见画布中不要出现

避免在设计稿可见内容中出现：

- 设计理念；
- 视觉风格说明；
- 推理过程；
- “为什么这样设计”的说明；
- 内部实现备注；
- Claude / 任务执行过程说明；
- 色彩 token 文档面板，除非用户明确要求创建设计系统页面。

Frame 名称可以便于设计师和开发者理解，但画板内可见文字应像真实产品 UI 文案。

### 3.2 使用真实感模拟数据

使用后续产品中可能真实出现的数据。优先使用术语表中的 PM-Agent 业务术语：

- 项目、需求、任务、迭代、风险、报告、Agent、Trace；
- 示例项目：`PM-Agent 平台 MVP`、`项目管理后台改版`、`风险分析实验`；
- 示例用户：`宁宁`、`ning`、`admin@pm-agent.local`。

避免 `Lorem ipsum`、`Title`、`Text`、`Button` 这类纯占位文本。

### 3.3 界面排列规则

在同一个 Figma 页面中按以下规则组织界面：

1. 不同业务的界面按 **从上到下** 排列；
2. 同一业务的交互状态按 **从左到右** 排列在基础界面右侧；
3. 如果交互变化很小，只绘制变化组件并用箭头标注关系；
4. 如果交互导致大部分界面变化，则在右侧创建完整新界面；
5. 对存在争议的界面，可以并排生成多个版本，并标注 `备选 A`、`备选 B` 等短标签，等待用户选择。

推荐间距：

- 桌面网页 Frame 宽度：1440px；
- 基础 Frame 高度：900–1024px，按内容调整；
- 同业务交互态横向间距：120–180px；
- 不同业务组纵向间距：160–240px。

### 3.4 命名规则

节点命名建议：

- 页面：`PM-Agent 正式界面设计稿`；
- 业务组：`业务组 / 系统介绍`、`业务组 / 用户认证`；
- 界面：`系统介绍页 / 默认`、`登录页 / 默认`、`注册页 / 切换后`；
- 交互箭头：`交互箭头 / 点击注册账号`。

可见标签只在有助于评审交互状态时使用，且必须简短，不要写长解释。

## 四、页面要求

### 4.1 系统介绍界面

正式系统介绍页通常包含：

- Header：Logo、导航、登录/注册入口；
- Hero：产品定位和主 CTA；
- 产品 UI 预览或工作台预览；
- 价值卡片：围绕项目、任务、风险、Agent 洞察、报告；
- Warm Linear 背景光晕和 Trace 视觉符号；
- 引导登录/注册的 CTA。

不要暴露设计意图，页面应该像真实的落地介绍页。

### 4.2 用户认证界面

登录和注册应绘制成正式应用界面：

- 登录页作为基础状态；
- 注册页作为点击“注册账号”后的交互状态，放在登录页右侧；
- 如有需要，可在右侧只绘制小型组件状态：校验错误、密码可见、登录 loading；
- 使用真实中文 UI 文案和表单标签；
- 认证页可以比内部系统页更有品牌表现，但不能只有装饰而缺少产品可用性。

推荐字段：

- 登录：用户名/邮箱、密码、记住登录、忘记密码、登录按钮、注册入口；
- 注册：显示名称、用户名/邮箱、密码、确认密码、同意协议、注册按钮、返回登录。

## 五、Figma MCP 工作流

1. 先使用 `use_figma` 或 metadata 工具检查目标文件；
2. 如需新建文件，先加载 `figma:figma-create-new-file`，必要时调用 `whoami`，再调用 `create_new_file`；
3. 写入前加载 `figma:figma-use`；绘制完整页面时同时加载 `figma:figma-generate-design`；
4. 每个界面使用顶层 Frame，内容放在 Frame 内，不要散落在页面上；
5. 使用最终 UI 文案，不写规划说明；
6. 每次 `use_figma` 调用都返回创建或修改的节点 ID；
7. 重大写入后使用 `get_metadata` 校验结构，使用 `get_screenshot` 校验视觉；
8. 如果 `use_figma` 报错，停止、阅读错误、修正脚本后再重试。失败脚本是原子执行，不会留下半成品。

## 六、实践建议

### 字体

- 前端实现优先使用 `MiSans`、`HarmonyOS Sans SC`、`Microsoft YaHei`；
- Figma MCP 脚本中先检查可用字体；如果缺少中文字体，可使用 `Inter` 并保持中文可读。

### 布局

正式设计稿使用固定桌面 Frame。静态设计可以使用绝对定位，但相关 UI 元素应组织在 Frame 中。对于可复用或文本较多的区块，优先考虑 auto-layout。

### 视觉克制

Warm Linear 允许系统介绍页和认证页更大胆，但内部系统界面应保持清爽、可实现、低返工。避免堆叠装饰、紫色 AI 渐变、纯表格后台感。

---

## 七、绘制完成后的回复格式

创建或更新 Figma 界面后，用中文按以下结构回复：

```markdown
## 已完成
## Figma 文件
## 本轮生成界面
## 交互关系
## 关键规范落实
## 后续建议
```

回复中说明 Figma 链接、主要 Frame 名称或节点 ID。保持简洁、真实，不夸大。
