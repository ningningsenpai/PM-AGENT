# PM-Agent 前端开发 Skill

## 触发场景

当用户提出以下类型请求时使用本 Skill：

- 设计或实现 Vue 3 + TypeScript 前端工程结构；
- 设计页面、路由、布局、导航、表格、表单、详情页、看板页；
- 设计 Agent 对话页、工具调用过程展示、Trace 展示、周报生成交互；
- 设计前端 API 封装、状态管理、权限路由、错误提示；
- 评审前端改动是否符合 PM-Agent 的产品风格和阶段规划。

## 目标

帮助 Claude 为 PM-Agent 输出可读性强、组件边界清晰、视觉效果成熟的前端方案。默认以后台管理系统为基底，但避免做成单调表格页，要体现 Linear 风格的简洁、留白、层级和状态感。

## 二、视觉与交互风格

PM-Agent 已确认视觉方向为：**Warm Linear 工作台风格**。除非用户明确要求调整，否则前端页面设计、Figma 原型和后续实现都应以此作为默认设计语言。

### 2.1 核心方向

1. 默认采用 **Warm Linear 风格**：参考 Linear 的简洁、留白、清晰层级和低饱和状态色，同时使用更温暖的蓝、绿、黄、白基调；
2. 产品应呈现“项目执行工作台”的感觉，而不是普通后台管理系统。通过布局和视觉符号表达可追踪、状态流转和 Agent 洞察；
3. 暂不考虑深色模式；不要为了深色模式提前复杂化主题系统；
4. 不做移动端适配，优先桌面端后台管理体验；
5. 管理后台不等于纯表格：使用卡片、统计块、风险标签、时间线、看板列、洞察卡和状态色增强信息密度；
6. Agent 页面要突出：对话、工具调用步骤、引用数据、可执行动作、人工确认结果；
7. 动效仅用于状态反馈，不做花哨装饰。

### 2.2 已确认色彩系统

以蓝、绿、黄、白为基础色板。建议视觉比例为：暖白/背景约 65%，蓝色约 20%，绿色约 10%，黄色约 5%。

| Token | 建议色值 | 用途 |
|---|---|---|
| PM Blue | `#2F7DF6` / `#1F66D1` | 主按钮、链接、项目进度、选中导航 |
| PM Green | `#26B983` / `#15966A` | 健康状态、完成状态、正向推进 |
| PM Yellow | `#F5B83D` / `#D8911E` | Agent 洞察、风险提示、重点高亮 |
| Warm White | `#F8FAF5` / `#FFFFFF` | 页面背景、卡片、内容承载面 |
| Main Text | `#132033` | 主标题、重要数值 |
| Secondary Text | `#667085` | 描述、元信息、辅助正文 |
| Muted Text | `#98A2B3` | 空状态、提示、低优先级信息 |

黄色不要平均铺开使用。黄色在 PM-Agent 中代表“洞察 / 值得关注的线索”，尤其用于 Agent 建议或风险线索。

### 2.3 品牌与视觉符号

1. 品牌主张为：**把项目状态变成可追踪的执行线索**；
2. Logo 方向采用深色圆角底、蓝色执行轨道、绿色状态节点、黄色洞察节点和 Trace 连接线。后续精修品牌时保持这套逻辑；
3. 在卡片和布局中复用“执行线索线”符号，例如左侧细线、顶部进度线、连接圆点或时间线节点；
4. 背景可以采用“晨光工作台”氛围：米白底、柔和蓝色光斑、柔和绿色光斑、少量黄色洞察暖光。避免重渐变或紫色 AI 科技风。

### 2.4 布局规则

1. 主应用布局保持：左侧导航 + 顶部状态栏 + 内容工作区；
2. 项目工作台优先采用：页面标题区、指标卡、项目卡、看板预览、Agent 洞察预留区；
3. 业务详情页优先采用：摘要区 + Tab 区 + 主工作区 + 右侧执行线索/洞察栏；
4. 认证页可以比内部工作台更大胆：大品牌 Hero、执行路径视觉、玻璃质感登录/注册卡片；
5. 可以为风险、Agent、报告、Trace 预留入口，但不要提前实现后置阶段业务逻辑。

### 2.5 字体与组件尺寸

实现时优先使用偏产品工具感的字体，例如 `MiSans`、`HarmonyOS Sans SC`、`Microsoft YaHei`。如果 Figma 环境缺少中文字体，可在原型中使用 `Inter`。不要全局使用 `LXGW WenKai Screen`；如用户希望保留个性，可仅用于品牌 Hero 的少量强调文字。

| 元素 | 字号 | 字重 |
|---|---:|---:|
| 页面主标题 | 28–32px | 700–800 |
| Hero 标题 | 52–64px | 800 |
| 卡片标题 | 18–22px | 650–700 |
| 正文 | 14px | 400 |
| 辅助说明 | 12–13px | 400–500 |
| 指标数字 | 28–40px | 700–800 |

圆角与间距：

- 页面/大卡片圆角：24–30px；
- 普通卡片圆角：18–24px；
- 按钮/输入框圆角：10–14px；
- 标签圆角：`999px`；
- 间距使用 4px 基准：4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64。

### 2.6 已确认原型页面

当前 Figma 原型已确认以下基础界面方向：

1. 品牌与视觉规范：Logo、色板、字体和组件示例；
2. 登录/注册界面：更大胆的品牌 Hero 和认证卡片；
3. 系统主页/项目工作台：侧边栏、顶部栏、指标卡、项目卡、看板预览、Agent 洞察预留区；
4. 系统业务主布局：项目摘要、Tab、任务看板、右侧执行线索栏。

后续实现前端代码时，应尽量保持这些结构决策稳定，避免频繁推翻布局。

## 三、目录结构

按 **业务模块 → 页面/组件** 组织，避免按组件类型把业务打散。

```text
frontend/src
├── app                 应用初始化、全局 provider
├── router              路由配置、权限守卫
├── stores              Pinia 全局状态
├── api                 Axios 实例、模块 API
├── shared              通用组件、hooks、工具、类型
├── layouts             主布局、登录布局
└── modules
    ├── project
    │   ├── pages
    │   ├── components
    │   ├── api.ts
    │   ├── types.ts
    │   └── store.ts
    ├── task
    ├── requirement
    ├── risk
    └── agent
```

### 命名约定

| 类型 | 约定 | 示例 |
|---|---|---|
| Vue 组件 | PascalCase | `TaskBoard.vue` |
| 文件/目录 | kebab-case 或业务名小写 | `task-card.vue` / `modules/task` |
| API 函数 | 动词 + 资源 | `createTask`、`listProjects` |
| 类型 | PascalCase | `TaskDetailResponse` |
| Store | `useXxxStore` | `useTaskStore` |

## 四、API 与请求封装

1. 所有业务接口走 `/api/v1/` 前缀；
2. Axios 必须统一封装请求/响应拦截器；
3. 请求头规则：
   - `Authorization`：登录后自动携带；
   - `X-Trace-Id`：前端可生成并透传，后端兜底；
   - `X-Idempotency-Key`：所有写接口必须携带，由表单或动作级别生成并在重试时复用；
4. 统一响应结构按后端 Skill：`code/message/data/traceId`；
5. 非 0 错误码统一弹出中文错误提示，并在调试信息中保留 traceId；
6. 前端不要散落 `axios.get/post`，必须通过 `modules/<module>/api.ts` 或 `api/<module>.ts` 封装。

## 五、页面设计原则

### 5.1 项目与任务页

- 第 1 阶段必须能展示项目列表、项目详情、任务列表/看板；
- 任务看板第一版**暂不要求拖拽**，先用状态分组列展示；
- 后续如做拖拽，必须先确认状态流转规则和后端接口幂等。

### 5.2 Agent 页

Agent 页面不只是聊天框，至少预留四块区域：

1. 用户输入与模型输出；
2. Agent 工具调用过程（工具名、入参摘要、结果摘要、耗时、状态）；
3. 引用的项目/任务/风险数据；
4. 需要人工确认的动作卡片。

### 5.3 表单与反馈

- 表单使用 Naive UI 校验能力，错误提示为中文；
- 保存、删除、Agent 执行等写操作必须有 loading 和防重复提交；
- 高风险操作必须二次确认，不允许仅靠按钮颜色表达风险。

## 七、工作流程

1. 先确认页面属于哪个开发阶段，避免提前实现后置能力；
2. 查产品术语表，确保页面文案、组件命名、路由命名统一；
3. 先设计用户路径，再拆组件和状态；
4. 明确 API 依赖，标注后端是否已存在；
5. 优先用 Naive UI 组件解决，必要时用 UnoCSS 做布局微调；
6. 输出验收标准时必须包含手动操作路径。

---

## 八、不可越界

以下事项必须先经用户确认：

- 替换 Vue 3 / Naive UI / Pinia / Axios；
- 同时引入 Tailwind 和 UnoCSS；
- 第一版强行实现任务看板拖拽；
- 引入完整深色模式或移动端适配；
- 绕过统一 Axios 封装直接请求接口；
- 对高风险操作不做确认弹窗；
- 使用未进入术语表的新业务命名。
