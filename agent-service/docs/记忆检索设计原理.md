# 记忆检索设计原理

## 1. 背景

当前上下文压缩主要依赖“保留最近若干轮 + 旧消息规则摘要”，适合早期控制上下文长度，但对项目管理 Agent 来说，长期价值更高的是能从历史对话中找回与当前问题强相关的项目事实、决策、风险、Bug 结论和任务信息。

因此，记忆检索不应只做简单摘要，而应逐步演进为项目级长期记忆检索链路。

## 2. 目标

- 在同一用户、同一项目范围内检索强相关历史对话。
- 优先保留对后续问答有价值的信息，而不是完整保留所有聊天记录。
- 查询时结合最近对话和长期记忆，提升 Agent 回答的连续性和准确性。
- 第一版不依赖模型训练，后续再基于真实 Agent Trace 优化价值评分和排序效果。

## 3. 第一版：不涉及模型训练

### 3.1 写入侧链路

每一轮 `user + assistant` 对话完成后，异步处理：

```text
原始对话
  -> 规则预过滤
  -> LLM 结构化分析
  -> 价值评分
  -> Embedding 向量化
  -> 写入记忆索引
```

LLM 结构化分析建议一次性输出：

```json
{
  "message_type": "bug",
  "module": "用户认证",
  "entities": ["登录接口", "token"],
  "facts": ["登录 token 在刷新后失效"],
  "decisions": [],
  "risks": [],
  "value_score": 0.86,
  "half_life_days": 90
}
```

### 3.2 查询侧链路

用户再次提问时，同步检索上下文：

```text
当前问题
  -> 生成 query embedding
  -> 按 user_id + project_id 过滤
  -> 向量召回 top N
  -> 结合类型、模块、价值分、时间衰减粗排
  -> reranker 精排
  -> 拼接最近 N 轮对话和高相关历史记忆
  -> 交给 LLM 回答
```

### 3.3 推荐模型

| 环节 | 推荐方案 | 说明 |
|---|---|---|
| 结构化分析 | DeepSeek / Qwen / Claude | 通过 Prompt 输出 JSON，不需要训练 |
| 向量化 | `bge-base-zh-v1.5` / `bge-m3` | 将历史对话转成语义向量 |
| 精排 | `bge-reranker-base` / `bge-reranker-v2-m3` | 对召回结果做相关性排序 |
| 最终回答 | DeepSeek 默认，复杂场景升级 Claude / GPT | 按成本和质量路由 |

### 3.4 关键排序因子

最终进入上下文的历史消息不只看时间，应综合：

```text
最终排序分 = 语义相关性 + 消息价值分 + 时间新鲜度 + 类型/模块匹配度
```

其中：

- 语义相关性：当前问题和历史对话是否相关。
- 消息价值分：历史对话本身是否值得长期保留。
- 时间新鲜度：任务状态等短期信息随时间衰减。
- 类型/模块匹配度：例如当前问题是 Bug，应优先召回 Bug 结论和测试记录。

## 4. 后续版本：引入模型训练

当 Agent Trace 积累足够后，可以训练或微调两个位置。

### 4.1 价值评分模型

目标是替代或辅助 LLM 打分，判断一轮对话是否值得长期保留。

```text
输入：user + assistant 对话、工具调用摘要、项目元信息
输出：value_score、memory_type、half_life_days
```

推荐路线：

```text
LLM 弱标注
  -> 人工抽样校验
  -> 训练轻量分类/回归模型
  -> 在线替代部分 LLM 评分
```

候选模型：

| 模型 | 优点 | 注意点 |
|---|---|---|
| `bge-small-zh` + 分类头 | 快、成本低、适合本地部署 | 效果上限一般 |
| `bge-base-zh` + 分类头 | 中文语义更稳 | 推理成本略高 |
| `MacBERT` 分类模型 | 中文分类成熟 | 对长上下文不如向量模型灵活 |
| `Qwen` 小模型 LoRA | 可输出更丰富标签 | 训练和部署复杂度更高 |

### 4.2 微调 reranker

目标是让精排模型更懂 PM-Agent 的业务语义，例如需求、任务、风险、Bug、测试结论之间的关系。

```text
输入：当前问题 + 候选历史记忆
输出：相关性分数
```

训练数据可来自：

- 最终回答实际引用过的历史消息；
- 用户确认有帮助的检索结果；
- 人工标注的相关 / 不相关样本；
- LLM 生成的弱标注样本。

微调后的 reranker 用于查询侧精排，不负责生成回答。

## 5. 包结构与职责

记忆检索模块放在 `app/memory/` 下，按写入处理、检索查询、模型能力和存储访问拆分：

```text
app/memory/
├── __init__.py
├── schemas/
├── domain/
├── extractor/
├── scoring/
├── embedding/
├── retrieval/
├── repository/
├── tasks/
└── service/
```

| 子包 | 作用 |
|---|---|
| `schemas/` | 定义记忆检索相关 Pydantic 结构，如结构化分析结果、检索请求、检索结果和上下文片段。 |
| `domain/` | 定义记忆领域对象、消息类型枚举、模块标签、评分常量和时间衰减配置。 |
| `extractor/` | 负责对话结构化抽取，包括消息类型、业务模块、实体、事实、决策、风险等。 |
| `scoring/` | 负责价值评分、时间衰减、类型/模块匹配分和最终排序分计算。 |
| `embedding/` | 封装 embedding 模型调用、文本向量化和必要的文本切片逻辑。 |
| `retrieval/` | 负责查询侧召回、粗排、reranker 精排和最终上下文拼装。 |
| `repository/` | 封装 MySQL 和后续向量库读写，避免业务编排层直接依赖存储细节。 |
| `tasks/` | 放置异步记忆处理任务入口，例如对话完成后的分析、评分、向量化和索引写入。 |
| `service/` | 提供记忆写入和记忆检索的对外编排服务，供 Agent 层调用。 |

## 6. 取舍与边界

- 第一版不要训练模型，优先验证链路闭环和检索效果。
- 价值评分和结构化分析放在异步写入侧，避免影响用户主对话响应。
- 查询侧不要调用大模型做复杂判断，优先使用 embedding + reranker 控制延迟。
- 同一项目下的历史对话只是候选范围，不代表每条都强相关。
- 高价值历史不一定与当前问题相关，低价值历史也可能短期命中当前问题，因此需要综合排序。

## 7. 验收标准

- 能按 `user_id + project_id` 限定记忆检索范围。
- 能为每轮对话生成类型、模块、实体、价值分和时间衰减信息。
- 当前问题能召回同项目下的相关历史对话。
- 最终上下文包含最近对话和高相关历史记忆。
- 异步记忆处理失败时不影响主对话流程。

## 8. 待确认问题

- 第一版是否先只接入 embedding，暂缓 reranker。
- 记忆索引是否单独建表，还是扩展现有对话记录表。
- 价值评分的初始标签体系是否只保留开发、测试、Bug、需求、风险、闲聊。
