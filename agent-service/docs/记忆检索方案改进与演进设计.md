# 记忆检索方案改进与演进设计

## 1. 背景

当前 `agent-service/docs/记忆检索设计原理.md` 已给出第一版记忆检索思路：通过规则预过滤、LLM 结构化分析、价值评分、向量召回和 reranker 精排，补足项目管理 Agent 在长期对话中的上下文连续性。

第一版方案已经具备“增强版 RAG”的雏形，但要真正支撑 PM-Agent 的项目管理场景，还需要进一步补齐三类能力：

1. **检索效果可评估**：要能判断召回是否真的有用，而不是只看相似度高不高；
2. **记忆生命周期可管理**：要能区分有效、过期、冲突、归档等状态；
3. **演进路径可落地**：要能从当前工程版方案平滑演进到学习排序版、事件图谱版。

本文档单独整理：

- 当前方案的改进点；
- 方案二：学习排序版；
- 方案三：事件图谱 + 神经记忆版。

---

## 2. 目标

1. 让记忆检索真正服务于项目管理场景，而不是只做“语义相似文本召回”。
2. 在不影响主对话性能的前提下，提升历史事实、决策、风险和 Bug 结论的召回质量。
3. 为后续基于 Agent Trace 的训练和优化预留数据闭环。
4. 形成一条清晰的演进路线：**工程规则版 → 学习排序版 → 图谱与神经记忆版**。

---

## 4. 当前方案的改进点

当前第一版方案的核心路径可以概括为：

```text
原始对话
  -> 规则预过滤
  -> LLM 结构化分析
  -> 价值评分
  -> Embedding 向量化
  -> 写入记忆索引
```

查询侧为：

```text
当前问题
  -> query embedding
  -> user_id + project_id 过滤
  -> 向量召回 top N
  -> 结合类型、模块、价值分、时间衰减粗排
  -> reranker 精排
  -> 拼接最近对话和高相关记忆
  -> 交给 LLM 回答
```

这一版可以继续保留，但建议补足以下改进点。

### 4.1 补齐检索评估闭环

当前方案最大的问题不是链路不完整，而是**没有足够的判定依据证明链路有效**。建议从第一版开始就沉淀离线和在线评估数据。

#### 建议记录的评估信号

| 类别 | 建议字段 | 作用 |
|---|---|---|
| 查询信息 | `query`、`project_id`、`user_id` | 定位问题场景 |
| 召回结果 | `retrieved_memory_ids`、`rank`、`score` | 看召回是否命中 |
| 实际使用 | `used_memory_ids` | 看哪些记忆真的帮助了回答 |
| 用户反馈 | `helpful / unhelpful / corrected` | 形成监督信号 |
| 回答结果 | `answer`、`citation_memory_ids` | 看回答是否可追溯 |

#### 建议评估指标

| 指标 | 说明 |
|---|---|
| Recall@K | 正确记忆是否进入前 K 条 |
| Precision@K | 前 K 条里有多少是真的相关 |
| MRR | 第一条正确记忆是否排得够前 |
| NDCG@K | 排序质量是否合理 |
| Answer Helpfulness | 用户是否认为答案有帮助 |
| Citation Consistency | 回答是否确实引用了命中的记忆 |

### 4.2 记忆分层和记忆类型细分

不要把所有历史对话都放在一个池子里。建议至少拆成三类：

| 记忆类型 | 内容示例 | 生命周期 |
|---|---|---|
| 情节记忆 | 某次讨论、某次排查过程、某次临时判断 | 中短期 |
| 语义记忆 | 项目事实、Bug 根因、风险结论、架构决策 | 中长期 |
| 程序记忆 | 用户偏好、团队规范、Agent 行为习惯 | 长期 |

这样做的好处是：

- 记忆写入时的评分逻辑可以不同；
- 记忆过期策略可以不同；
- 检索排序可以更贴近业务语义。

### 4.3 引入记忆状态管理

建议给每条记忆增加状态，避免旧结论持续污染新回答。

| 状态 | 含义 |
|---|---|
| `ACTIVE` | 当前有效，可参与召回 |
| `SUPERSEDED` | 已被新结论替代 |
| `CONFLICTED` | 与其他记忆存在冲突 |
| `EXPIRED` | 超过有效期，默认不召回 |
| `ARCHIVED` | 归档保留，不默认进入上下文 |
| `DELETED` | 已删除 |

如果没有状态管理，Agent 很容易把已经过期的风险结论、任务状态或者 Bug 处理方式再次当成当前事实使用。

### 4.4 将记忆与业务事实分层

PM-Agent 不是纯聊天产品，很多信息本来就应该落在业务表里，而不是只存在记忆库中。

| 信息类型 | 推荐存储位置 | 说明 |
|---|---|---|
| 项目、任务、风险、需求状态 | 业务数据库 | 事实主源 |
| Agent 分析过程 | Agent Trace | 便于回放和审计 |
| 历史对话结论 | 记忆库 | 便于语境恢复 |
| 用户偏好 | 记忆库 / 偏好表 | 长期保留 |
| 临时上下文摘要 | 会话上下文 | 短期使用 |

建议遵循下面的原则：

> **业务数据库是事实主源，记忆系统负责上下文、解释和历史语境。**

### 4.5 从单一向量召回升级为混合召回

当前方案的召回重点在 embedding，相对容易出现“语义像但业务不相关”的问题。建议增加混合召回：

```text
当前问题
  -> 向量召回
  -> BM25 / 关键词召回
  -> 实体 / 模块召回
  -> 类型召回
  -> 图关系召回（后续版本）
  -> 合并去重
  -> reranker 精排
```

混合召回的意义在于：

- 向量召回负责语义相似；
- 关键词召回负责专有名词、接口名、错误码、任务编号；
- 实体召回负责模块、需求、风险、Bug 的强绑定；
- 后续图关系召回负责多跳关联。

### 4.6 记录“回答使用了哪些记忆”

每次 Agent 回答后，建议记录：

```json
{
  "query": "上次登录 token 刷新失败的问题最后怎么处理的？",
  "retrieved_memory_ids": [101, 118, 126],
  "used_memory_ids": [118, 126],
  "ignored_memory_ids": [101],
  "answer": "...",
  "user_feedback": "helpful"
}
```

这样做的价值很大：

1. 未来可以训练排序模型；
2. 可以识别哪些记忆虽然召回了，但其实没帮助；
3. 可以构造更真实的正负样本。

### 4.7 价值评分不要只依赖 LLM

LLM 评分可以作为冷启动，但不建议长期作为唯一依据。建议把价值分拆成几个可解释因子：

```text
value_score =
  业务类型基础分
+ 是否包含明确事实
+ 是否包含决策
+ 是否包含风险
+ 是否被后续引用
+ 用户是否确认有用
- 闲聊/重复/无结论惩罚
```

LLM 负责结构化抽取，规则和反馈负责修正分数，这样更稳定。

## 5. 方案二：学习排序版

### 5.1 定位

方案二是在方案一基础上的增强版，目标是：

> 在积累真实 Agent Trace 后，使用轻量模型替代部分人工规则，让“哪些记忆更值得保留、哪些记忆更该排前面”这件事逐步模型化。

### 5.2 核心思路

保留多路召回，但将排序能力从手工权重逐步迁移到学习模型：

```text
多路召回
  -> 特征构造
  -> 轻量学习排序模型
  -> 小型 reranker 精排
  -> LLM 回答
```

### 5.3 训练数据来源

训练数据主要来自真实使用过程中的反馈信号：

| 信号 | 类型 | 用途 |
|---|---|---|
| 用户点击“有帮助” | 正反馈 | 训练正样本 |
| 用户追问“不是这个” | 负反馈 | 训练负样本 |
| 回答实际引用的记忆 | 弱正样本 | 训练排序模型 |
| 召回但最终未使用的记忆 | 弱负样本 | 识别噪声召回 |
| 用户纠错 | 强负样本 | 提升精排质量 |
| 人工抽样标注 | 高质量监督样本 | 冷启动与校准 |

### 5.4 模型组成

#### A. 价值评分模型

输入可以包括：

- 对话文本；
- 工具调用摘要；
- 项目阶段；
- 消息类型；
- 实体数量；
- 是否包含决策、风险、Bug 结论。

输出：

- `value_score`
- `memory_type`
- `half_life_days`

#### B. Learning-to-Rank 排序模型

输入特征可以包括：

| 特征 | 说明 |
|---|---|
| `dense_score` | 向量召回分 |
| `bm25_score` | 关键词相关分 |
| `reranker_score` | 精排得分 |
| `value_score` | 记忆价值分 |
| `freshness_score` | 时间新鲜度 |
| `memory_type` | 记忆类型 |
| `module_match` | 模块是否匹配 |
| `entity_match_count` | 实体命中数 |
| `used_count` | 历史被使用次数 |
| `last_used_at` | 最近使用时间 |
| `source_confidence` | 抽取置信度 |

输出：

- 排序分 `rank_score`

#### C. 小型 reranker

如果候选很多，可以先用轻量排序模型粗排，再用 reranker 精排少量候选，控制延迟。

### 5.5 推荐实现路径

建议优先级如下：

1. **特征工程 + LightGBM / XGBoost**：最稳，最适合小数据冷启动；
2. **轻量 reranker 微调**：当 Trace 足够多时再做；
3. **蒸馏模型**：把大模型判断蒸馏成小模型，进一步降本。

### 5.6 性能要求

| 环节 | 设计要求 |
|---|---|
| 价值评分 | 放在写入侧异步处理 |
| 排序模型 | 毫秒级完成 |
| reranker | 仅处理 top 20~50 候选 |
| 特征构造 | 尽量预计算 |
| 模型部署 | 独立推理服务或 ONNX |

### 5.7 适用场景

方案二适合：

- 真实使用数据已经积累一段时间；
- 希望减少手工规则；
- 希望检索结果更贴近 PM-Agent 的业务语义；
- 希望在性能可控前提下提升排序质量。

### 5.8 取舍

| 维度 | 优点 | 缺点 |
|---|---|---|
| 效果 | 能随数据增长持续提升 | 初期不一定优于规则版 |
| 性能 | 仍可保持较低延迟 | 需要额外推理服务 |
| 工程复杂度 | 比图谱版低 | 需要训练、标注和版本管理 |
| 可解释性 | 比纯黑盒强 | 仍不如完全规则可解释 |

## 6. 方案三：事件图谱 + 神经记忆版

### 6.1 定位

方案三是更长期的演进方向，目标不是只做“相似文本召回”，而是让系统理解：

- 项目中的关键实体是什么；
- 这些实体之间发生了什么事件；
- 事件之间有什么因果、依赖和版本关系；
- 当前问题在图谱中处于什么位置。

### 6.2 核心思路

把对话和业务信息抽取成事件与关系，而不是只存文本：

```text
事件：登录 token 刷新失败
主体：登录接口
原因：Redis 会话未同步刷新
影响：用户刷新后被迫重新登录
决策：补充会话刷新逻辑
关联任务：TASK-102
关联风险：认证稳定性风险
```

形成图结构后，查询不只是相似度检索，而是：

```text
当前问题
  -> 实体识别
  -> 图谱邻域扩展
  -> 向量召回补充
  -> 时序重建
  -> 冲突检测
  -> 上下文组装
  -> LLM 回答
```

### 6.3 记忆层次

建议拆成三层：

| 层次 | 内容 | 作用 |
|---|---|---|
| 文本记忆层 | 原始对话、摘要、证据 | 保留可追溯原文 |
| 结构记忆层 | 事实、决策、风险、任务状态 | 支撑业务查询 |
| 图谱记忆层 | 实体、事件、关系、版本 | 支撑多跳推理 |

### 6.4 可用技术

| 能力 | 可选技术 |
|---|---|
| 实体识别 | 规则 + 小模型 NER |
| 关系抽取 | LLM 异步抽取 / 信息抽取模型 |
| 图存储 | 关系表起步，后续图数据库 |
| 图嵌入 | Node2Vec、GraphSAGE、R-GCN |
| 图排序 | Personalized PageRank、GNN ranking |
| 时序建模 | 时间衰减边权、Temporal Graph |
| 冲突检测 | 同实体多版本对比 |

### 6.5 查询方式

图谱版更适合以下问题：

- “登录模块之前还有哪些遗留风险？”
- “这个需求为什么后来被拆成两个任务？”
- “上次这个 Bug 的修复依赖了哪些前置任务？”
- “当前项目里和接口认证相关的历史决策是什么？”

这类问题不是单纯向量相似就能解决的，需要实体和关系的推理能力。

### 6.6 性能要求

图谱版必须把重计算尽量放到离线：

| 阶段 | 处理内容 | 说明 |
|---|---|---|
| 离线 / 异步 | 实体抽取、关系抽取、图谱更新、图嵌入计算 | 避免阻塞主对话 |
| 在线 | 实体识别、图邻域扩展、轻量排序 | 保证响应速度 |

### 6.7 适用场景

方案三适合：

- 项目数据积累较多；
- 需要多跳推理；
- 需要解释“为什么召回这条记忆”；
- 需要处理任务、风险、需求、Bug、决策之间的关系；
- 希望从“检索”升级到“记忆理解”。

### 6.8 取舍

| 维度 | 优点 | 缺点 |
|---|---|---|
| 推理能力 | 多跳关联能力强 | 工程复杂度高 |
| 可解释性 | 结构清晰，便于追溯 | 图谱抽取错误会污染关系 |
| 性能 | 在线可做轻量查询 | 需要离线维护图谱和嵌入 |
| 适配性 | 很适合 PM 场景 | 不适合一开始就大规模上线 |

## 7. 推荐演进路线

建议按下面顺序推进：

### 第一步：先把当前方案做成可评估的工程版

重点是：

- 增加检索评估数据；
- 增加 memory_id 引用日志；
- 增加记忆状态；
- 增加混合召回；
- 保留异步写入，确保主对话不被拖慢。

### 第二步：在真实 Trace 基础上做学习排序

重点是：

- 用真实反馈训练价值评分和排序模型；
- 减少人工规则；
- 降低 LLM 打分依赖；
- 保持线上延迟可控。

### 第三步：在业务图谱成熟后引入事件图谱记忆

重点是：

- 抽取实体、事件、关系；
- 管理版本和冲突；
- 支持多跳推理；
- 将“检索”升级为“项目记忆理解”。

---

## 8. 风险与取舍

| 风险 | 说明 | 建议 |
|---|---|---|
| LLM 抽取不稳定 | 结构化字段可能漂移 | 用规则、抽样和反馈校正 |
| 旧记忆污染回答 | 过期结论再次被召回 | 引入状态和过期机制 |
| 向量召回偏语义 | 语义近但业务无关 | 增加关键词、实体、类型召回 |
| 训练数据不足 | 学习排序效果不稳定 | 先规则后学习，逐步升级 |
| 图谱抽取错误 | 关系可能被污染 | 先把图谱控制在高置信事件上 |
| 性能膨胀 | 查询链路过重 | 候选数控制、离线预计算、缓存 |

---

## 9. 验收标准

### 当前方案改进后的验收标准

1. 能区分情节记忆、语义记忆和程序记忆；
2. 能记录记忆状态、价值分和半衰期；
3. 能按 `user_id + project_id` 限定检索范围；
4. 能记录回答实际使用了哪些记忆；
5. 能通过离线评估集判断召回质量；
6. 主对话响应不因记忆写入或检索而明显变慢。

### 方案二的验收标准

1. 可使用真实 Trace 数据训练排序模型；
2. 排序结果优于纯规则版本；
3. 线上延迟仍然可控；
4. 训练数据和模型版本可追踪；
5. 用户反馈可以持续回流到训练集。

### 方案三的验收标准

1. 能抽取项目中的实体、事件和关系；
2. 能从图谱中召回和当前问题相关的历史链路；
3. 能识别并标记冲突记忆；
4. 能解释召回路径；
5. 能支持任务、风险、需求、Bug、决策之间的多跳查询。

## 10. 待确认问题

1. 当前第一版是否先落地混合召回，再考虑学习排序。
2. 记忆状态是否需要和业务状态强绑定，例如任务关闭后自动降低相关记忆权重。
3. 方案二的训练数据是否优先使用用户反馈，还是先使用 Agent Trace 的弱标注。
4. 方案三是否先在关系表中表达图谱，还是直接引入图数据库。
5. 是否需要为“程序记忆”单独拆分存储和召回策略。
