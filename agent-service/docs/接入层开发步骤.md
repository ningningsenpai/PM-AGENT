# 接入层后续开发步骤

> 本文档记录接入层当前已完成基础（请求入口、SSE 流式协议、事件类型标准化）之后，按优先级排列的后续完善事项。
> 已完成的 SSE 事件类型定义和 SSE 格式化工具封装不在本文档中重复。

---

## 一、扩展请求 Schema

**目标**：让 Agent 请求携带足够上下文，支撑 Prompt、工具调用、RAG 等后续模块。

**当前状态**：

`app/schemas/chat.py` 中 `ChatRequest` 仅有 `message`、`project_id`、`stream`、`use_tool_demo` 四个字段。

**待新增字段**：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `conversation_id` | `str \| None` | 否 | 多轮会话 ID，同一会话内多条消息共享 |
| `scene` | `str \| None` | 否 | Agent 场景标识，如 `project_chat`、`requirement_decompose`、`weekly_report`、`risk_analysis` |
| `enable_tools` | `bool` | 否，默认 true | 是否允许 Agent 调用工具 |
| `enable_rag` | `bool` | 否，默认 false | 是否启用 RAG 检索，当前阶段默认 false |
| `metadata` | `dict \| None` | 否 | 扩展上下文，如页面来源、业务模块、前端状态 |

**涉及文件**：`app/schemas/chat.py`

---

## 二、新增 Agent 请求上下文对象

**目标**：将 HTTP header 中的 `trace_id`、`user_id`、`tenant_id` 等信息封装为统一上下文，贯穿 Agent、工具、Prompt、Trace 各层。

**当前状态**：

`app/api/v1/agent.py` 中 header 信息仅在接口层使用，未传入 `ProjectChatAgent`。

**待实现**：

1. 新增 `AgentContext` 数据类（建议放在 `app/schemas/` 或新建 `app/core/context.py`）：

```text
AgentContext
├── trace_id          # 贯穿全链路
├── user_id           # 工具 API 鉴权和审计
├── tenant_id         # 多租户隔离
├── conversation_id   # 多轮会话
├── scene             # Agent 场景
├── idempotency_key   # 写操作防重复
└── source            # 调用来源：frontend / java_backend / internal_task
```

2. 在接口层构造 `AgentContext` 并传入 `ProjectChatAgent`
3. `ProjectChatAgent` 将上下文透传给工具层和 LLM 调用层

**涉及文件**：
- 新建 `app/core/context.py` 或 `app/schemas/context.py`
- 修改 `app/api/v1/agent.py`
- 修改 `app/agents/project_chat_agent.py`

---

## 三、统一响应与错误结构

**目标**：确保 JSON 响应和 SSE 流式输出在成功和失败时都返回一致的结构，对齐项目错误码规范。

**当前状态**：

成功路径已返回 `ApiResponse(code=0, data=..., traceId=...)`，但错误路径缺少统一处理。

**待实现**：

1. **错误码定义**：在 `app/schemas/` 下新增错误码常量或枚举，Agent 类错误使用 `4xxxx` 段：

| 错误码 | 含义 |
|---|---|
| `40001` | Agent 参数错误 |
| `40002` | 模型调用失败 |
| `40003` | 工具调用失败 |
| `40004` | 工具超时 |
| `40005` | 不支持的操作 |

2. **统一异常处理**：在 `app/api/v1/agent.py` 或全局异常处理器中捕获异常，返回 `ApiResponse(code=4xxxx, message=中文错误, traceId=...)`，即使失败也要返回 `traceId`

3. **SSE 错误事件**：流式输出中途失败时，推送 `event: error` 事件，data 包含 `code`、`message`、`traceId`

**涉及文件**：
- 新建 `app/schemas/errors.py`
- 修改 `app/api/v1/agent.py`
- 可选：新建 `app/core/exception_handlers.py`

## 四、Agent 场景路由

**目标**：根据 `scene` 字段将请求分发到不同 Agent 编排，避免所有逻辑堆在一个 `ProjectChatAgent` 中。

**当前状态**：

只有 `ProjectChatAgent`，接口直接硬编码实例化。

**待实现**：

1. 定义 Agent 注册机制（字典映射或简单工厂）：

```text
scene → Agent 类
project_chat         → ProjectChatAgent
requirement_decompose → RequirementDecomposeAgent（后续实现）
weekly_report        → WeeklyReportAgent（后续实现）
risk_analysis        → RiskAnalysisAgent（后续实现）
```

2. 在接口层根据 `request.scene` 选择 Agent
3. 新增 Agent 基类或协议（`BaseAgent`），定义 `chat()` 和 `stream_chat()` 接口

**涉及文件**：
- 新建 `app/agents/base.py`
- 修改 `app/api/v1/agent.py`
- 后续按场景新建具体 Agent

## 五、预留 Trace 记录结构

**目标**：在代码中预留 Trace 记录入口，确保所有 Agent 决策可追踪，后续对接 Java 后端 Trace 表。

**当前状态**：

仅有 `traceId` 在响应中返回，未记录 Prompt、工具调用、模型输出等过程数据。

**待实现**：

1. 定义 `AgentTrace` 数据结构（建议放在 `app/schemas/` 下）：

| 字段 | 说明 |
|---|---|
| `trace_id` | 统一追踪 ID |
| `user_input` | 用户原始输入 |
| `prompt_snapshot` | 实际发送给模型的 messages |
| `model_info` | provider、model、temperature |
| `token_usage` | prompt_tokens、completion_tokens |
| `tool_calls` | 工具名、入参、出参、耗时、状态 |
| `final_output` | 模型最终回答 |
| `error_info` | 异常信息，有则记录 |
| `created_at` | 创建时间 |

2. 在 `ProjectChatAgent` 中构造 Trace 对象并返回给接口层
3. 短期内可用日志输出代替持久化，待 Java 后端 Trace API 就绪后切换

**涉及文件**：
- 新建 `app/schemas/trace.py`
- 修改 `app/agents/project_chat_agent.py`

## 六、预留 Java 工具 API 调用上下文

**目标**：为后续替换 Demo 工具做准备，确保 Python Agent 能以受控方式调用 Java 后端工具 API。

**当前状态**：

`DemoProjectTool` 返回固定数据，不调用外部服务。

**待实现**：

1. 在配置中增加 `JAVA_BACKEND_BASE_URL`
2. 新建 `app/tools/base.py`，定义工具基类和 HTTP 调用封装
3. 工具调用时自动携带 header：
   - `X-Trace-Id`
   - `X-User-Id`
   - `X-Tenant-Id`
   - `X-Idempotency-Key`
4. 工具异常处理：Java 返回错误时，工具层不抛原始异常，而是返回结构化错误供 Agent 理解
5. 超时控制：单次工具调用超时不可阻塞整个 Agent 请求

**涉及文件**：
- 修改 `app/core/config.py`
- 新建 `app/tools/base.py`
- 新建 `app/tools/http_client.py`

## 七、预留人工确认动作结构

**目标**：确保高风险操作（删除、权限变更、对外通知等）不会由 Agent 自动执行，而是生成确认卡片，由用户确认后由 Java 后端执行。

**当前状态**：

Prompt 中已声明"高风险动作只能生成建议"，但代码层未实现确认机制。

**待实现**：

1. 在 `ChatResponse` 中增加字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `requires_confirmation` | `bool` | 是否需要人工确认 |
| `pending_actions` | `list[PendingAction]` | 待确认动作列表 |

2. `PendingAction` 结构：

```text
PendingAction
├── action_id          # 动作 ID
├── action_type        # 操作类型
├── tool_name          # 确认后执行的工具名
├── input_schema       # 待执行参数
├── risk_level         # 风险等级：low / medium / high
├── summary            # 人类可读的操作摘要
└── status             # pending / confirmed / rejected
```

3. 在 `ProjectChatAgent` 中检测高风险意图，生成待确认动作而非直接执行

**涉及文件**：
- 修改 `app/schemas/chat.py`
- 修改 `app/agents/project_chat_agent.py`

## 建议优先级

按对后续模块的支撑作用排列：

```text
1. 扩展请求 Schema          ← 最优先，Prompt / 工具 / RAG 都依赖
2. Agent 请求上下文对象       ← 与 Schema 同步完成
3. 统一响应与错误结构         ← 前端联调前必须完成
4. Agent 场景路由            ← 第二个 Agent 场景出现前完成
5. 预留 Trace 结构           ← tool_calls 开发前完成
6. 预留 Java 工具 API 上下文  ← tool_calls 开发前完成
7. 预留人工确认动作结构       ← 高风险工具开发前完成
8. 预留 RAG 开关             ← 第 6 阶段前完成即可
```
