# 文件树构建与 MinIO 上传链路风险审计

本文档记录 `用户根路径 → 文件树扫描 → MinIO 上传` 这条链路当前存在的隐藏风险与对应修改建议，作为后续重构和测试补齐的依据。

涉及代码：

- `app/api/v1/project_files.py`
- `app/api/internal/minio_files.py`
- `app/project/files/tree_service.py`
- `app/project/files/service.py`
- `app/project/files/storage.py`
- `app/project/context/scanner/walker.py`
- `app/project/context/scanner/ignore_rules.py`
- `app/project/context/indexer/tree_index.py`
- `app/project/context/schemas.py`
- `app/project/files/schemas.py`

---

## 一、高风险

### 1. `walk()` 把所有节点一次性放进内存

- 当用户根目录文件数十万级，`nodes` 列表与最终 `Project_Index.json` 会撑爆内存或产生超大 JSON。
- `Project_Index.json` 单文件无分片，每次更新都是全量重写。

**修改建议**

- 引入分批处理：扫描时按目录批次写入临时索引片段。
- 给 `walk()` 增加最大节点数与最大深度上限，超过即拒绝并返回错误。
- 长期看可将 `Project_Index.json` 拆为：
  - `index_meta.json`：总信息、版本号、统计摘要
  - `index_nodes.jsonl`：按行存储节点

---

### 2. 上传链路对每个文件都把整个文件读进内存两次

- `_upload_file_from_path` 用 `SpooledTemporaryFile(max_size=1MB)` + `source.read()` 一次性读完文件。
- `upload_project_file` 又 `await file.read()` 一次。
- `service.upload_file` 再 `len(file_bytes)` 与 `put_object(file_bytes)`，整条链路没有流式上传。
- 单个 50MB 文件过程中会同时存在多份字节副本，N 个文件就 N 倍。

**修改建议**

- 在内部上传函数中允许直接传 `Path` 或 `BinaryIO`，下沉到 MinIO 客户端时使用 `put_object(stream, length, content_type)` 流式上传。
- 删除 `SpooledTemporaryFile(max_size=1MB)` 这种过小 spool；要么用磁盘临时文件，要么直接传 `open(path, "rb")`。
- HTTP 上传接口保留 `UploadFile`，但 service 层提供基于流的入口。

---

### 3. 文件大小限制由“读完之后再判断”

- `ProjectFileService._validate_file_size` 在 `await file.read()` 之后才校验 `len(file_bytes) > max_size`。
- 用户传一个 1GB 文件，进程已经先把它读进内存。

**修改建议**

- 上传前先做大小预检：
  - 本地文件：`Path.stat().st_size`
  - HTTP 请求：`request.headers.get("content-length")`
- 超过 `max_file_size_mb` 直接 400 拒绝，不再 `await file.read()`。

---

### 4. 文件名校验过严

- `ProjectFileStorage._validate_file_name` 只允许 `[A-Za-z0-9._\-一-鿿]`。
- 常见文件名包含：空格、`(1)`、`、`、`+`、`#`、日文、繁体、CJK 扩展 B/C 区字符、emoji，全部会 400。
- 构建链路上只要 1 个不合规文件就会中途抛错，且前面已上传文件不会回滚。

**修改建议**

- 拓宽允许字符集：
  - 接受空格、英文括号、`+`、`#`、`@`、`、`、`,`、`'`
  - 通过 Unicode 字符类别允许 `L`、`N`、`P`、`Zs`
- 仍然禁止：
  - `/`、`\`、`..`、控制字符、不可见字符、`*`、`?`、`<`、`>`、`|`、`:`
- 校验失败不要让整次 `build_tree` 整体失败，应将该节点标记为 `scan_status="error"`，跳过上传，最终一次性返回错误清单。

---

### 5. 构建中途失败没有事务保护

- `build_tree` 中第 N 个文件 MinIO 失败时，前 N-1 个对象已经写入 MinIO；
- 但 `Project_Index.json` 还没写，等于 MinIO 里有孤儿对象，本地索引一无所知；
- 后续 `update_tree` 也无法清理这些孤儿。

**修改建议**

- 在 `build_tree` 增加“增量持久化”：每成功上传一个文件就 append 到临时索引文件，失败时仍可恢复。
- 失败回滚策略二选一：
  - 失败时尝试删除已上传的 MinIO 对象；
  - 失败时把已上传对象写入 `Project_Index.json` 与异常清单，让 Java 端通过补偿任务清理。
- 接口返回结构中明确区分 `success` 与 `failed`，避免“静默吞掉”。

---

### 6. fingerprint 用 `mtime` 会误判“无变更但被 touch”

- `quick_fingerprint(path, size, mtime)` 不读内容；
- 只要 `mtime` 改变（git checkout、IDE 保存、跨平台拷贝、网盘同步）就会触发 `update_project_file`，每次都会重新覆盖 MinIO；
- 而 `_node_fingerprint` 也只比较 `(size, quick_fingerprint, content_hash)`，没有让 `content_hash` 起到“一票否决”的作用。

**修改建议**

- 修改 `_node_fingerprint` 判定顺序：
  - 优先比较 `content_hash`：相同即认定文件无变化，跳过 MinIO 覆盖；
  - `content_hash` 为空时再 fallback 到 `(size, quick_fingerprint)`；
- 对 `skipped_hash` 文件，至少加一次内容大小变化与扩展名变化判定，避免完全靠 `mtime`。

---

### 7. `update_tree` 没考虑 `skipped_hash` 文件

- `_active_file_nodes` 只取 `scan_status == "active"`，命中 `should_skip_hash` 的文件 `scan_status="skipped_hash"`，会被直接过滤掉；
- 也就是说图片、PDF、压缩包等永远进不了 MinIO；
- 如果你的预期是“整个项目都上传 MinIO”，这就是 bug。

**修改建议**

- 明确产品定义：
  - 若仅索引代码 → 当前行为符合预期，需要在文档中说明；
  - 若需上传全部 → 修改 `_active_file_nodes`，把 `skipped_hash` 文件也包含，仅跳过内容哈希但仍走上传链路。
- 在 `should_skip_hash` 中拆分“跳过哈希”与“跳过上传”两类，避免一个判定决定两件事。

---

## 二、中风险

### 8. `print(normalized)` 残留

- `_validate_file_name` 中存在 `print(normalized)`；
- 高频调用会污染日志。

**修改建议**

- 移除 `print`，必要时使用统一 logger，并降级到 `DEBUG`。

---

### 9. `output_dir` 和 `root_path` 没做白名单

- Java 直接传字符串路径，意味着 `output_dir` 可写到任意盘符目录，`root_path` 可扫描 `C:\Windows`、`/etc` 等系统目录；
- 当前单机本地服务尚可，多用户/多机部署后即路径注入。

**修改建议**

- 在 `app/core/config` 中维护一组允许的工作根目录（白名单或前缀匹配）。
- `root_path` / `output_dir` 必须落在白名单目录之下，否则 400。
- `output_dir` 必须在 `agent-service` 受控目录内，禁止逃逸到用户主目录或系统盘根。

---

### 10. 没有并发控制

- 同一项目并发触发两次 `build` / `update`：
  - 两个进程都会写 `Project_Index.json`，后写覆盖前写；
  - MinIO 对象 prefix 用 `uuid.uuid4().hex[:8]`，并发可能上传两份重复对象；
  - 没有锁/幂等键防御。

**修改建议**

- 引入 `project_id + user_id` 维度的进程内/Redis 互斥锁；
- 写 `Project_Index.json` 时使用临时文件 + `os.replace` 原子替换；
- 后端调用方传 `X-Idempotency-Key`，服务端短期缓存防重。

---

### 11. `update_tree` 中删除 MinIO 失败不会回滚 `Project_Index.json`

- 已经在循环里 `delete_project_file(...)`，删除失败抛异常会中断流程；
- 前面新增/修改节点已经写过新的 `file_info`；
- 此时 `Project_Index.json` 还没写，本地索引仍是旧的，MinIO 状态和索引脱节。

**修改建议**

- 将“扫描结果 → MinIO 操作 → 索引写入”改为两阶段：
  1. 第一阶段：收集所有 add / update / delete 计划；
  2. 第二阶段：批量执行，失败时记录并跳过单个失败项，最终统一写索引；
- 索引写入应在 MinIO 操作之前先准备“候选索引”，所有操作完成后再原子替换。

---

### 12. `business` 默认值是字符串

- `FileTreeCommand.business` 默认 `FileBusiness.PROJECT.value`，是字符串而非 enum 实例；
- Pydantic 会再解析一次，语义和文档容易割裂。

**修改建议**

- 改为 `default=FileBusiness.PROJECT`，保持 enum 一致性。

---

### 13. 上传写 MinIO 时没有内容类型回退

- `mimetypes.guess_type` 对一些常见后缀（`.md`、`.ts`、`.tsx`、`.vue`、`.proto`、`.kt`）会返回 `None`，最终落到 `application/octet-stream`；
- 不是 bug，但会让前端 view 时无法做预览。

**修改建议**

- 在 `tree_service` 或 `storage` 中维护一份扩展 `mimetypes` 表，例如：
  - `.md → text/markdown`
  - `.ts / .tsx → application/typescript`
  - `.vue → text/x-vue`
  - `.kt → text/x-kotlin`
  - `.proto → text/plain`

---

### 14. MinIO `object_name` 没保留原始相对路径

- `object_name = f"PM-AGENT/{user_id}/{project_id}/{business.value}/{prefix}"`；
- `prefix` 只放纯文件名，本地相对目录在 MinIO 里完全丢失；
- 多个不同子目录里有同名文件时，只能靠 uuid 区分；
- 从 MinIO 反查“这是项目里哪个相对路径”不可能。

**修改建议**

- 在 `FileUploadResult` 或 `file_info` 中新增 `source_relative_path`；
- 或调整 object_name 规则为：
  - `PM-AGENT/{user_id}/{project_id}/{business}/{relative_dir_safe}/{prefix}`
- 数据库映射表中明确保留 `source_relative_path`。

---

## 三、低风险

### 15. `Project_Index.json` 没有 schema 版本号

- 后续 `FileNode` 字段变化（例如刚加的 `file_info`），旧索引文件直接 `FileNode(**node)` 会失败。

**修改建议**

- 在索引顶层加 `index_version` 字段；
- 读取时按版本走兼容分支或自动迁移；
- 版本不匹配时给出明确报错信息。

---

### 16. `update_tree` 拿不到旧索引时直接调 `build_tree`

- 表现没问题，但语义上“更新接口”悄悄执行了“构建”操作；
- 调用方可能没预期。

**修改建议**

- 返回结果中加 `mode: build | update` 字段；
- 或在接口文档中显式说明这个 fallback 行为；
- 也可以拆为 `is_first_build: bool`。

---

### 17. `_node_fingerprint` 字段冗余

- `quick_fingerprint` 已经包含 `path|size|mtime`，再加 `size` 是冗余；
- 真正想判断“内容是否变化”应优先比较 `content_hash`，再 fallback 到 `size + mtime`。

**修改建议**

- 重写为：
  - 有 `content_hash` 时只用 `content_hash` 判定；
  - 没有 `content_hash` 时使用 `(size, quick_fingerprint)`；
- 避免冗余字段误导后续维护者。

---

### 18. `download_project_file` 一次性把整个对象读到内存

- 当前更新链路未直接用到下载，但 `/download` 路由通过 `iter([content])` 流式响应；
- 实际读对象时仍是 `get_object_bytes`，对大对象会内存炸。

**修改建议**

- MinIO 客户端层提供 `get_object_stream(bucket, object_name)`；
- 路由层 `StreamingResponse` 直接消费 stream，不再先 `read()`。

---

### 19. `_raise_file_tree_error` 把所有未识别异常映射为 500

- 路径不存在 (`ValueError("root_path 不存在或不是目录")`) 映射为 400 是对的；
- 但 IO 错误、`PermissionError` 会变 500，调用方无法区分。

**修改建议**

- 增加分支：
  - `FileNotFoundError` → 404
  - `PermissionError` → 403
  - 其他 OS 错误 → 500，但 message 中带原始错误码

---

### 20. `_load_file_info` 没有版本兼容

- `tree_service._load_file_info` 用 `node.file_info` 字典构造 `FileUploadResult`；
- 当旧索引被手动编辑或写过老版本字段时会 raise，无 fallback。

**修改建议**

- 配合“15. 索引 schema 版本号”实现兼容层；
- 至少在异常 message 中提示“索引版本不匹配，请重新构建”。

---

## 四、建议的修复优先级

如果先修三件事，建议按以下顺序：

1. **修高风险 2、3**：上传链路改成流式，并把大小预检挪到读文件之前。
2. **修高风险 5、11**：build/update 引入两阶段执行 + 索引原子写入，避免“MinIO 已写但索引没写”的脱节态。
3. **修高风险 6、低风险 17**：`update_tree` 优先用 `content_hash` 判定变化，减少不必要的 MinIO 覆盖。

后续按 RAG / Java 落库节奏推进文件名规则放宽、并发控制、`source_relative_path`、索引版本化等中低风险项。

## 五、待确认问题

- 文件树是否需要包含图片、PDF、压缩包等 `skipped_hash` 文件？
- `output_dir` 是否限定在 `agent-service` 内的固定目录？
- `Project_Index.json` 是否需要拆为 `meta + nodes.jsonl`？
- 文件上传失败时是“整批回滚”还是“失败清单 + 部分成功”？
- 是否引入 Redis 做项目级互斥锁？
