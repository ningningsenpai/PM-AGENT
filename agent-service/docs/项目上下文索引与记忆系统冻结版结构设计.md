# 项目上下文索引与记忆系统冻结版结构设计

## 1. 背景

PM-Agent 需要在用户选择本地项目目录后，持续理解项目文件、项目规则、用户习惯、项目记忆和近期任务上下文，为后续 Agent 问答、代码分析、风险识别、需求拆解和报告生成提供稳定上下文。

当前设计已经形成七类输出文件：

- 总索引文件；
- 文件详情文件；
- 用户习惯文件；
- 项目规划 / 项目规范文件；
- 长期记忆文件；
- 短期记忆文件；
- 面向用户的 `project.md`。

冻结版方案的目标不是继续增加文件数量，而是明确每类文件的职责边界、更新策略、检索路径和覆盖规则，避免后续出现索引膨胀、信息重复、错误覆盖和检索性能下降。

## 2. 设计目标

1. 保证项目文件持续演化时，索引仍然轻量、可快速命中；
2. 保证 LLM 只接收必要内容，避免无意义投喂；
3. 保证 LLM 输出只覆盖目标内容，不误伤其他文件或其他类别记忆；
4. 保证各类文件职责清晰，减少冗余；
5. 保证不同文件之间通过稳定引用串联，不形成信息孤岛；
6. 第一版不引入完整向量数据库、图数据库或复杂 RAG；
7. 为后续 BM25、向量检索、AST 深度解析和长期记忆演进预留结构。

## 3. 总体冻结结构

推荐冻结为：

```text
系统应用目录：
.pm-agent/projects/<project_id>/
  project_meta.json
  index.json
  file_details/
    <file_id>.json
  project_specification.json
  long_term_memory.json
  short_term_memory.json
  user_habits/
    work.json
    life.json
    thinking.json
    specification.json
    tooling.json
  update_journal.jsonl

用户项目目录：
  project.md
  .pm-agent-link
```

其中：

| 文件 | 格式 | 是否用户可见 | 职责 |
|---|---|---:|---|
| `project_meta.json` | JSON | 否 | 项目绑定、根目录、指纹、版本信息 |
| `index.json` | JSON | 否 | 总索引，只做快速命中和路由 |
| `file_details/*.json` | JSON | 否 | 单文件详情摘要和可召回切片 |
| `project_specification.json` | JSON | 否 | 项目规范、开发阶段、技术约束 |
| `long_term_memory.json` | JSON | 否 | 长期稳定决策、阶段事件、演化记录 |
| `short_term_memory.json` | JSON | 否 | 当前任务窗口内的临时上下文 |
| `user_habits/*.json` | JSON | 否 | 用户习惯，按五类拆分 |
| `update_journal.jsonl` | JSONL | 否 | 增量更新日志，用于审计和回滚参考 |
| `project.md` | Markdown | 是 | 面向用户审查的项目理解摘要 |
| `.pm-agent-link` | 文本 / JSON | 是 | 绑定项目和系统目录 |

## 4. 核心原则

### 4.1 总索引只做路由

`index.json` 不保存大段摘要、不保存文件内容、不保存复杂推理结果。

它只回答一个问题：

```text
用户问题或系统任务应该优先读取哪些详情文件、记忆文件或原始文件？
```

### 4.2 文件详情只描述单个文件

`file_details/*.json` 只处理文件，不处理文件夹，不写项目规范，不写用户习惯，不写长期记忆。

它只回答一个问题：

```text
这个文件在项目中负责什么，有哪些可召回的关键内容？
```

### 4.3 项目规范是强约束

`project_specification.json` 保存后续开发、分析和 Agent 执行必须遵守的规则。

它不记录临时任务、不记录用户个人习惯、不记录文件内容摘要。

### 4.4 长期记忆是项目演化脉络

`long_term_memory.json` 只记录长期有效、对后续开发有影响的项目决策、阶段转折和验证结论。

它不记录可从当前代码直接读取的结构快照。

### 4.5 短期记忆是任务缓存

`short_term_memory.json` 必须具备生命周期管理。

每条短期记忆都需要：

- `ttl_hint`
- `status`
- `next_check`
- `promote_candidate`

任务结束后必须清理、压缩或晋升。

### 4.6 用户习惯按类别分文件

用户习惯保留五类拆分：

- `work`
- `life`
- `thinking`
- `specification`
- `tooling`

这样可以避免单个习惯文件无限膨胀，也能在检索时只读取相关类别。

### 4.7 project.md 只做用户视图

`project.md` 是用户审查系统理解的入口，不是系统真实索引，不参与内部召回评分。

用户修改 `project.md` 后，系统需要解析变更，再分类写入规范、记忆或用户习惯候选，不能直接把整份 `project.md` 覆盖进内部 JSON。

## 5. 文件结构设计

### 5.1 project_meta.json

#### 职责

记录项目绑定关系、项目指纹和系统文件版本。

#### 建议结构

```json
{
  "project_id": "local-pm-agent-001",
  "display_name": "PM-AGENT",
  "root_path": "D:/Code/ning/PM-AGENT",
  "root_fingerprint": "sha256:xxx",
  "git_root": "D:/Code/ning/PM-AGENT",
  "git_remote": "",
  "index_version": "1.0.0",
  "created_at": "2026-07-02T00:00:00",
  "last_scan_at": "2026-07-02T00:00:00",
  "status": "active"
}
```

#### 更新规则

| 场景 | 处理 |
|---|---|
| 首次绑定 | 创建 |
| 项目路径变化但指纹一致 | 更新 `root_path` |
| 指纹变化 | 标记 `pending_review` |
| 项目解绑 | 标记 `inactive`，不立即删除 |

### 5.2 index.json

#### 职责

作为所有内部文件的总入口，负责快速检索和路由。

#### 不允许存放

- 原始文件全文；
- 大段代码；
- 大段文档；
- Prompt 内容；
- 内部评分细节；
- 用户敏感信息；
- 文件详情中的完整 `content_slice`。

#### 建议结构

```json
{
  "project_id": "local-pm-agent-001",
  "schema_version": "1.0.0",
  "generated_at": "2026-07-02T00:00:00",
  "summary": {
    "total_nodes": 1200,
    "active_files": 430,
    "ignored_files": 700,
    "deleted_files": 3,
    "detail_files": 180
  },
  "entries": [
    {
      "id": "file-backend-auth-controller",
      "path": "backend/src/main/java/com/ning/pm/auth/controller/AuthController.java",
      "node_type": "file",
      "file_type": "code.backend.java",
      "module": "backend-auth",
      "language": "java",
      "status": "active",
      "size_bytes": 12345,
      "mtime": "2026-07-02T00:00:00",
      "content_hash": "sha256:xxx",
      "quick_fingerprint": "path-size-mtime",
      "summary": "认证接口控制器",
      "keywords": ["认证", "登录", "注册", "Sa-Token"],
      "entities": {
        "classes": ["AuthController"],
        "functions": [],
        "apis": ["/api/v1/auth/login"]
      },
      "tags": ["auth", "backend", "api"],
      "priority": 0.9,
      "detail_ref": "file_details/file-backend-auth-controller.json",
      "source": "scan",
      "updated_at": "2026-07-02T00:00:00"
    }
  ],
  "context_refs": {
    "project_specification": "project_specification.json",
    "long_term_memory": "long_term_memory.json",
    "short_term_memory": "short_term_memory.json",
    "user_habits": "user_habits/"
  }
}
```

#### 检索规则

`index.json` 第一版采用轻量规则检索：

1. 关键词匹配；
2. 模块匹配；
3. 文件类型匹配；
4. 实体匹配；
5. 优先级排序；
6. 状态过滤；
7. 命中 `detail_ref` 后读取文件详情。

#### 性能控制

| 控制项 | 冻结规则 |
|---|---|
| 单条 `summary` | 建议不超过 80 个中文字符 |
| `keywords` | 建议 3 到 12 个 |
| `entities` | 只保留关键实体名 |
| `entries` | 可按模块分页或分片，但第一版可先单文件 |
| 删除文件 | 保留软删除状态，不立即移除 |

### 5.3 file_details/*.json

#### 职责

记录符合规则的单个文件详情。

#### 文件命名

推荐使用稳定 `file_id`：

```text
file_details/<file_id>.json
```

`file_id` 不直接使用原始路径，避免路径移动后文件名频繁变化。

可由以下内容生成：

```text
module + normalized_path_hash
```

#### 建议结构

```json
{
  "id": "file-backend-auth-controller",
  "project_id": "local-pm-agent-001",
  "original_path": "backend/src/main/java/com/ning/pm/auth/controller/AuthController.java",
  "module": "backend-auth",
  "file_type": "code.backend.java",
  "language": "java",
  "status": "active",
  "importance": "high",
  "content_hash": "sha256:xxx",
  "role": "提供认证相关 HTTP 接口入口，负责登录、注册和当前用户查询。",
  "content_slices": [
    {
      "slice_id": "api-login",
      "type": "api",
      "summary": "登录接口接收账号密码并调用认证服务完成登录。",
      "keywords": ["登录", "认证", "Sa-Token"],
      "entities": ["/api/v1/auth/login", "AuthService"],
      "source_range": {
        "start_line": 20,
        "end_line": 45
      }
    }
  ],
  "related_topics": ["auth", "login", "backend-api"],
  "related_files": [
    {
      "path": "backend/src/main/java/com/ning/pm/auth/service/AuthService.java",
      "relation": "service_dependency"
    }
  ],
  "risk_flags": [],
  "sensitive_flags": [],
  "evidence": [
    {
      "source": "file_content",
      "quote": "认证控制器相关摘要"
    }
  ],
  "previous_versions": [
    {
      "content_hash": "sha256:old",
      "role": "旧职责摘要",
      "changed_at": "2026-07-01T00:00:00",
      "reason": "文件内容变化后重新摘要"
    }
  ],
  "updated_at": "2026-07-02T00:00:00"
}
```

#### 覆盖规则

| 场景 | 处理 |
|---|---|
| 文件新增 | 创建详情 |
| 文件修改 | 只更新当前文件详情 |
| 文件删除 | `status=deleted`，保留旧详情 |
| 文件移动 hash 不变 | 更新 `original_path`，保留 `id` |
| 文件敏感 | 不生成内容切片，只记录脱敏状态 |
| 文件过大 | 采样或结构提取，不全文投喂 |

### 5.9 update_journal.jsonl

#### 职责

记录每次更新动作，辅助调试、审计和后续回滚参考。

#### 结构示例

```json
{"event_id":"evt-001","project_id":"local-pm-agent-001","event_type":"file_modified","target":"file_details/file-backend-auth-controller.json","source":"backend/src/main/java/.../AuthController.java","created_at":"2026-07-02T00:00:00","summary":"文件 hash 变化，已更新文件详情"}
```

#### 记录范围

| 动作 | 是否记录 |
|---|---:|
| 文件新增 | 是 |
| 文件修改 | 是 |
| 文件删除 | 是 |
| 文件移动 | 是 |
| project.md 内化 | 是 |
| 短期记忆晋升 | 是 |
| 长期记忆演化 | 是 |
| 用户习惯覆盖 | 是 |

## 6. 检索链路设计

### 6.1 第一版检索链路

```text
用户问题 / 系统任务
→ 意图分类
→ 读取 index.json
→ 按关键词、模块、类型、实体、priority 命中候选
→ 读取候选 file_details
→ 按任务需要读取规范 / 长期记忆 / 短期记忆 / 用户习惯
→ 必要时读取原始文件
→ 组装 Prompt
→ LLM 输出
```

### 6.2 检索优先级

| 任务类型 | 优先上下文 |
|---|---|
| 代码问答 | `index.json` → `file_details` → 原始文件 |
| 架构分析 | `project_specification.json` → `long_term_memory.json` → `file_details` |
| 当前任务推进 | `short_term_memory.json` → 相关 `file_details` |
| 用户协作偏好 | `user_habits/specification.json`、`work.json` |
| 风险分析 | `project_specification.json` → `file_details.risk_flags` → 原始文件 |
| 项目总览 | `project.md` 生成源数据 + `index.json.summary` |

### 6.3 防止指数增长

1. `index.json` 不保存长文本；
2. `file_details` 按文件分片；
3. 用户习惯按五类分片；
4. 短期记忆必须 TTL 清理；
5. 长期记忆只保存稳定结论；
6. `project.md` 不作为内部召回主索引；
7. 删除文件软删除，定期压缩；
8. 后续需要时再引入索引分片或 BM25。

## 7. 初始化链路

### 7.1 初始化流程

```text
用户选择项目目录
→ 生成 project_id 和 root_fingerprint
→ 创建 project_meta.json
→ 扫描文件树
→ 应用 ignore 规则
→ 分类文件
→ 计算 quick_fingerprint
→ 对候选文件计算 content_hash
→ 生成 index.json
→ 为高优先级文件生成 file_details
→ 初始化 project_specification.json
→ 初始化 long_term_memory.json
→ 初始化 short_term_memory.json
→ 初始化 user_habits 五类文件
→ 生成 project.md
→ 写入 .pm-agent-link
→ 记录 update_journal.jsonl
```

### 7.2 初始化时进入 LLM 的内容

| 内容 | 是否进入 LLM |
|---|---:|
| README / CLAUDE / docs | 是 |
| 核心配置文件 | 是 |
| 关键代码文件摘要或结构 | 是 |
| `.env` 内容 | 否 |
| 密钥、证书 | 否 |
| node_modules / .venv | 否 |
| lock 文件全文 | 否 |
| 二进制资源 | 否 |

## 8. 演进链路

### 8.1 项目文件演进

```text
重新扫描文件树
→ 对比旧 index.json
→ 得到 added / modified / deleted / moved
→ 只处理变化文件
→ 更新对应 file_details
→ 更新 index.json 对应 entry
→ 必要时更新 project_specification 或 long_term_memory
→ 记录 update_journal
```

### 8.2 记忆演进

```text
新对话 / 新结论 / 新测试结果
→ 先进入 short_term_memory
→ 任务完成或结论稳定
→ 判断是否进入 long_term_memory
→ 如果是规范类内容，进入 project_specification
→ 如果是用户习惯，进入 user_habits 对应分类
```

### 8.3 project.md 演进

```text
检测 project.md 修改
→ 只解析用户可编辑区
→ 分类变更内容
→ 生成候选更新
→ 高风险或冲突内容要求用户确认
→ 写入对应内部 JSON
→ 重新生成 project.md 非编辑区
```

## 9. 更新与覆盖规则

### 9.1 文件更新规则

| 变化 | index.json | file_details |
|---|---|---|
| 新增文件 | 新增 entry | 新增详情 |
| 修改文件 | 更新 hash、mtime、summary、keywords | 更新对应详情，保留旧版本 |
| 删除文件 | `status=deleted` | `status=deleted`，保留旧详情 |
| 移动文件 | 更新 path，保留 id | 更新 original_path，保留 previous_versions |
| 忽略文件 | 记录 ignored 和原因 | 不生成详情 |

### 9.2 内容覆盖规则

所有 LLM 输出必须带目标对象 ID。

禁止出现：

```text
读取旧 JSON
→ LLM 输出一个新 JSON
→ 程序整文件覆盖
```

必须采用：

```text
读取旧 JSON
→ LLM 输出 changes
→ 程序按 id 合并
→ 未命中的旧条目原样保留
→ 冲突条目标记 conflicted / evolved / pending_review
```

### 9.3 各文件覆盖边界

| 文件 | 可覆盖范围 |
|---|---|
| `index.json` | 可由扫描器整体重建，但 entry 必须保留稳定 id |
| `file_details/*.json` | 只覆盖对应文件详情 |
| `project_specification.json` | 只覆盖目标规则或字段 |
| `long_term_memory.json` | 只覆盖同 id 记忆 |
| `short_term_memory.json` | 可清理过期项，但需记录 changes |
| `user_habits/*.json` | 只覆盖同 category 内同 id habit |
| `project.md` | 可重新生成系统摘要区，不覆盖用户编辑区 |

## 11. 安全与污染防护

### 11.1 敏感信息

以下内容不得进入索引详情、记忆或 Prompt：

- API Key；
- token；
- 密码；
- 私钥；
- `.env` 明文；
- 证书文件；
- 数据库连接串敏感值；
- 用户隐私信息。

允许保存脱敏摘要：

```json
{
  "path": ".env",
  "status": "ignored",
  "sensitive_flags": ["env_file", "possible_secret"],
  "summary": "检测到环境变量文件，已跳过内容索引"
}
```

### 11.2 Prompt Injection

项目文件中的文本只作为数据，不作为系统指令。

发现类似内容时：

```json
{
  "risk_flags": ["possible_prompt_injection"],
  "summary": "文件中包含疑似指令注入文本，后续仅作为数据处理"
}
```

### 11.3 高风险动作

删除、权限变更、对外通知、业务写入等动作不能由该索引系统直接执行，只能生成建议或候选动作，并交由后端工具 API 和用户确认链路处理。

## 12. 版本与压缩策略

### 12.1 schema_version

每个 JSON 文件必须包含：

```json
{
  "schema_version": "1.0.0"
}
```

用于后续结构升级。

### 12.2 压缩策略

| 文件 | 压缩策略 |
|---|---|
| `index.json` | 删除长期 deleted entry 或归档 |
| `file_details` | deleted 文件保留一段时间后归档 |
| `short_term_memory` | 按 TTL 清理 |
| `long_term_memory` | 不轻易删除，只演化 |
| `user_habits` | 合并同义 habit，保留 previous_versions |
| `update_journal` | 按时间滚动归档 |

## 14. 验收标准

1. 首次扫描项目后，可以生成完整内部目录结构；
2. `index.json` 不包含原始文件全文；
3. 符合规则的文件可以生成对应 `file_details/*.json`；
4. 修改单个文件后，只更新该文件的 index entry 和 file detail；
5. 删除文件后，索引和详情均进入软删除状态；
6. 用户习惯可以按五类文件拆分保存；
7. 短期记忆具备 TTL 和晋升候选字段；
8. 长期记忆只记录稳定决策和阶段性结论；
9. 项目规范不混入用户习惯和临时任务；
10. `project.md` 只展示用户可读内容；
11. 修改 `project.md` 后，不会直接覆盖内部 JSON；
12. 敏感文件不会进入 Prompt 或详情摘要；
13. 项目文件中的疑似指令注入文本只作为数据处理；
14. 后续 Agent 问答可以按 `index → detail → 原文 / 记忆` 的顺序召回上下文。

## 15. 最终冻结结论

冻结版结构采用：

```text
一个轻量总索引
+ 多个单文件详情
+ 一个项目规范库
+ 一个长期记忆库
+ 一个短期记忆库
+ 五类用户习惯库
+ 一个用户可见 project.md
+ 一个更新日志
```

最终边界如下：

| 类型 | 冻结职责 |
|---|---|
| 总索引 | 快速命中和路由 |
| 文件详情 | 单文件职责和内容切片 |
| 项目规范 | 强约束和开发规则 |
| 长期记忆 | 稳定决策和项目演化 |
| 短期记忆 | 当前任务缓存 |
| 用户习惯 | 用户稳定协作偏好 |
| project.md | 用户审查系统理解 |
| update_journal | 更新审计和调试 |

该结构可以支撑第一版轻量召回，也能平滑演进到后续 BM25、向量检索、AST 解析和更完整的 RAG 能力。
