# 事件图谱与神经记忆最终实现方案

## 1. 背景

当前记忆检索方案已经具备基础的文本记忆写入、结构化分析、Embedding 向量化、向量召回和 reranker 精排能力，能够解决“从历史对话中找回相似内容”的问题。

但 PM-Agent 的核心场景不是普通聊天，而是围绕项目、需求、任务、风险、问题、决策和 Trace 进行持续管理。很多用户问题并不只是语义相似问题，而是关系推理问题，例如：

- 某个风险最初是由哪个问题引发的；
- 某个任务为什么被创建；
- 某个需求为什么后来被拆成多个任务；
- 某个历史结论是否已经被新的决策替代；
- 某个模块过去有哪些相关风险、问题和处理结论。

因此，最终方案决定在现有记忆检索基础上引入轻量事件图谱，将历史对话和 Agent Trace 中的关键内容抽取为实体、事件、关系和证据，再与向量召回、关键词召回、reranker 组合使用。

本方案不以训练数据集建设为当前重点，也不在第一版引入图数据库或图神经网络。当前目标是先落地一条工程可控、可追溯、可评估的事件图谱记忆链路。

---

## 2. 目标

1. 将长期记忆从“相似文本召回”升级为“项目历史事件理解”。
2. 支持围绕项目、需求、任务、风险、问题、决策的关系型查询。
3. 保留原始文本证据，确保每个图谱结论可以追溯到来源记忆或 Trace。
4. 避免旧结论污染当前回答，通过状态、时间和冲突机制识别过期记忆。
5. 在不显著增加主对话延迟的前提下，引入图谱召回作为向量召回的补充。
6. 为后续学习排序、图嵌入和神经记忆预留扩展点，但当前不提前实现重型能力。

---

## 3. 范围

### 3.1 本期范围

本期实现以“轻量事件图谱 + 混合召回”为边界，包含：

- 从对话、记忆摘要和 Agent Trace 中抽取实体、事件、关系；
- 使用关系表表达事件图谱，不直接引入图数据库；
- 为节点和关系记录来源、置信度、时间和状态；
- 查询时进行实体识别、图谱邻域扩展、向量召回补充和 reranker 精排；
- 组装包含历史链路、当前事实、证据来源的上下文；
- 对需要当前业务状态的问题，通过 Java 工具 API 查询业务数据库；
- 记录图谱召回、向量召回、最终使用记忆和回答引用关系。

### 3.2 不做范围

本期不做以下内容：

- 不引入 Neo4j、NebulaGraph 等图数据库；
- 不训练或微调图神经网络；
- 不建设大规模人工标注数据集；
- 不让 Agent 直接操作业务数据库；
- 不将记忆库作为项目、任务、风险等当前状态的事实主源；
- 不覆盖所有问法，优先支持高价值项目管理查询。

---

## 4. 总体决定

最终采用以下路线：

```text
现有文本记忆检索
  -> 结构化事件抽取
  -> 关系表版事件图谱
  -> 图谱召回 + 向量召回 + 关键词召回
  -> reranker 精排
  -> 状态与冲突检查
  -> 上下文组装
  -> LLM 回答
```

核心原则：

1. **业务数据库是当前事实主源**：项目、需求、任务、风险、问题的实时状态必须以 Java 后端业务数据为准。
2. **记忆系统负责历史语境**：记忆库保存历史对话、历史结论、决策依据、风险来源和处理过程。
3. **图谱负责关系推理**：事件图谱用于回答“为什么、怎么关联、后来如何变化”。
4. **向量召回负责语义补充**：图谱不能覆盖的背景信息仍由向量召回补齐。
5. **每个图谱结论必须可追溯**：节点和边都必须保留 `source_memory_id` 或 `source_trace_id`。
6. **先做轻量工程版，再考虑神经增强**：第一版不追求 GNN，而是保证链路稳定、可解释、可维护。

## 5. 核心概念设计

### 5.1 记忆层次

| 层次 | 内容 | 作用 |
|---|---|---|
| 文本记忆层 | 原始对话、摘要、证据片段 | 保留可追溯来源 |
| 结构记忆层 | 事实、决策、风险、问题结论 | 支撑结构化理解 |
| 事件图谱层 | 实体、事件、关系、版本、状态 | 支撑多跳关系查询 |
| 当前事实层 | Java 后端业务表中的项目、任务、风险等状态 | 回答当前状态类问题 |

### 5.2 实体类型

第一版只保留高价值实体类型，避免抽取范围过大。

| 实体类型 | 说明 | 示例 |
|---|---|---|
| `PROJECT` | 项目 | PM-Agent |
| `MODULE` | 业务或技术模块 | 认证模块、任务管理模块 |
| `REQUIREMENT` | 需求 | 用户登录能力 |
| `TASK` | 任务 | TASK-102 |
| `RISK` | 风险 | 认证稳定性风险 |
| `ISSUE` | 已发生问题 | 登录刷新后被踢回登录页 |
| `DECISION` | 决策 | token 刷新后同步续期 |
| `API` | 接口 | token 刷新接口 |
| `USER` | 用户或责任人 | 项目成员 |

### 5.3 事件类型

| 事件类型 | 说明 | 示例 |
|---|---|---|
| `ISSUE_FOUND` | 发现问题 | 发现登录刷新后退出 |
| `CAUSE_IDENTIFIED` | 定位原因 | 定位为 Redis 会话未同步续期 |
| `DECISION_MADE` | 做出决策 | 决定补充 Sa-Token 续期逻辑 |
| `TASK_CREATED` | 创建任务 | 创建 TASK-102 |
| `RISK_CREATED` | 登记风险 | 登记认证稳定性风险 |
| `STATUS_CHANGED` | 状态变化 | 风险关闭、任务完成 |
| `REQUIREMENT_SPLIT` | 需求拆分 | 需求拆成多个任务 |
| `DECISION_SUPERSEDED` | 决策替代 | 新方案替代旧方案 |

### 5.4 关系类型

| 关系类型 | 说明 | 示例 |
|---|---|---|
| `BELONGS_TO` | 归属 | 问题归属于认证模块 |
| `RELATES_TO` | 关联 | 风险关联任务 |
| `CAUSES` | 导致 | Redis 会话未续期导致登录退出 |
| `RESOLVES` | 解决 | TASK-102 解决认证稳定性风险 |
| `DEPENDS_ON` | 依赖 | 修复任务依赖认证接口调整 |
| `BLOCKS` | 阻塞 | 接口未完成阻塞前端联调 |
| `TRIGGERS` | 引发 | 问题引发风险 |
| `SUPERSEDES` | 替代 | 新决策替代旧决策 |
| `EVIDENCED_BY` | 证据来源 | 事件由某条记忆证明 |

## 6. 写入侧链路

### 6.1 输入来源

写入侧主要来自三类输入：

1. 用户与 Agent 的一轮或多轮对话；
2. Agent Trace 中的工具调用、模型回答、引用记忆；
3. Java 工具 API 返回的业务对象摘要。

### 6.2 处理流程

```text
原始对话 / Trace
  -> 文本记忆写入
  -> 结构化抽取
  -> 实体归一化
  -> 事件生成
  -> 关系生成
  -> 置信度校验
  -> 写入关系表版事件图谱
  -> 写入向量索引
```

### 6.3 结构化抽取输出

LLM 或规则抽取结果必须使用 Pydantic Schema 校验，禁止直接信任自由文本。

```json
{
  "entities": [
    {
      "type": "MODULE",
      "name": "认证模块",
      "aliases": ["登录模块"]
    },
    {
      "type": "TASK",
      "name": "TASK-102"
    }
  ],
  "events": [
    {
      "type": "ISSUE_FOUND",
      "title": "登录刷新后被踢回登录页",
      "event_time": "2026-06-10",
      "summary": "用户刷新页面后登录态失效"
    }
  ],
  "relations": [
    {
      "source": "登录刷新后被踢回登录页",
      "relation": "CAUSES",
      "target": "认证稳定性风险"
    }
  ],
  "confidence": 0.86
}
```

### 6.4 写入规则

| 场景 | 处理规则 |
|---|---|
| 高置信度实体 | 直接写入图谱 |
| 中置信度实体 | 写入但不默认参与高优先级召回 |
| 低置信度实体 | 仅保留在 Trace，不进入默认图谱 |
| 已存在实体 | 进入实体归一化，不重复创建节点 |
| 新结论替代旧结论 | 为旧记忆增加 `SUPERSEDED` 状态或替代关系 |
| 涉及当前业务状态 | 不直接改业务表，只记录历史语境 |

## 7. 查询侧链路

### 7.1 查询流程

```text
用户问题
  -> 查询意图识别
  -> 实体识别与归一化
  -> 图谱邻域扩展
  -> 向量召回补充
  -> 关键词召回补充
  -> 候选合并去重
  -> 状态与冲突检查
  -> reranker 精排
  -> 必要时调用 Java 工具 API 查询当前事实
  -> 上下文组装
  -> LLM 回答
  -> 记录 used_memory_ids 和引用路径
```

### 7.2 示例流转

用户问题：

```text
登录模块之前还有哪些遗留风险？
```

实体识别结果：

```json
{
  "intent": "查询历史风险",
  "entities": [
    {
      "type": "MODULE",
      "raw_name": "登录模块",
      "normalized_name": "认证模块"
    }
  ]
}
```

图谱邻域扩展结果：

```json
{
  "start_entity": "认证模块",
  "paths": [
    {
      "path": "认证模块 -> 登录刷新后被踢回登录页 -> 认证稳定性风险",
      "relation_summary": "历史问题曾引发认证稳定性风险",
      "source_memory_id": "MEM-001",
      "confidence": 0.88
    },
    {
      "path": "认证稳定性风险 -> TASK-102 -> 风险关闭",
      "relation_summary": "风险已通过 TASK-102 处理并关闭",
      "source_memory_id": "MEM-008",
      "confidence": 0.91
    }
  ]
}
```

上下文组装结果：

```json
{
  "question": "登录模块之前还有哪些遗留风险？",
  "current_entity": "认证模块",
  "history_chain": [
    {
      "event": "登录刷新后被踢回登录页",
      "cause": "Redis 会话未同步续期",
      "risk": "认证稳定性风险",
      "task": "TASK-102",
      "current_status": "已关闭",
      "evidence_memory_ids": ["MEM-001", "MEM-008"]
    }
  ],
  "answer_hint": "历史上存在认证稳定性风险，但后续记录显示该风险已关闭。"
}
```

最终回答应基于历史链路和当前状态生成，而不是直接复述相似文本。

## 8. 存储设计方向

第一版使用关系表表达事件图谱，后续如果查询复杂度上升，再考虑图数据库。

### 8.1 建议表职责

| 表 | 职责 |
|---|---|
| `memory_text` | 保存文本记忆、摘要、向量索引引用和基础状态 |
| `memory_entity` | 保存实体节点，如模块、任务、风险、问题、决策 |
| `memory_entity_alias` | 保存实体别名和归一化关系 |
| `memory_event` | 保存事件，如问题发现、原因定位、任务创建、风险关闭 |
| `memory_relation` | 保存实体与事件之间的关系边 |
| `memory_retrieval_trace` | 保存每次检索召回、排序、使用和引用情况 |

### 8.2 关键字段

图谱节点和关系至少需要以下字段：

| 字段 | 说明 |
|---|---|
| `project_id` | 项目范围隔离 |
| `user_id` | 用户范围隔离 |
| `entity_type` / `event_type` | 节点或事件类型 |
| `name` / `title` | 展示名称 |
| `normalized_key` | 归一化标识，避免重复节点 |
| `source_memory_id` | 来源记忆 |
| `source_trace_id` | 来源 Trace |
| `confidence` | 抽取置信度 |
| `status` | 当前记忆状态 |
| `event_time` | 事件发生时间 |
| `created_at` / `updated_at` | 系统记录时间 |

### 8.3 记忆状态

| 状态 | 含义 |
|---|---|
| `ACTIVE` | 当前有效，可参与召回 |
| `SUPERSEDED` | 已被新结论替代 |
| `CONFLICTED` | 与其他记忆存在冲突 |
| `EXPIRED` | 超过有效期，默认不召回 |
| `ARCHIVED` | 归档保留，不默认进入上下文 |
| `DELETED` | 已删除 |

## 9. 模型与组件选择

### 9.1 第一版组件

| 环节 | 推荐方案 | 说明 |
|---|---|---|
| 结构化抽取 | DeepSeek 默认，复杂场景可升级 Claude | 输出 JSON，并通过 Pydantic 校验 |
| 实体归一化 | 规则 + LLM 辅助 | 优先维护别名表和标准名称 |
| 向量化 | `bge-m3` 或同类中文 Embedding | 用于文本记忆和事件摘要召回 |
| 关键词召回 | BM25 或数据库全文索引 | 用于任务编号、接口名、错误码等精确词 |
| 精排 | `bge-reranker-v2-m3` 或同类 reranker | 对合并候选进行最终排序 |
| 图谱查询 | MySQL 关系表 + 1~2 跳邻域扩展 | 第一版不引入图数据库 |

### 9.2 后续增强组件

| 能力 | 引入时机 | 说明 |
|---|---|---|
| Learning-to-Rank | Trace 数据稳定后 | 替代部分手工排序权重 |
| 图嵌入 | 图谱规模扩大后 | 让实体关系参与向量排序 |
| 图数据库 | 关系表查询复杂度明显升高后 | 支持更复杂多跳查询 |
| GNN Ranking | 图谱数据和评估体系成熟后 | 不作为近期目标 |

## 10. Agent 与 Java 后端协作

事件图谱记忆不能绕过 Java 后端的业务边界。

### 10.1 职责划分

| 层 | 职责 |
|---|---|
| Java 后端 | 项目、需求、任务、风险、问题等当前业务事实和权限校验 |
| Python Agent 服务 | 记忆抽取、事件图谱维护、检索编排、上下文组装 |
| LLM | 结构化抽取、意图识别、回答生成 |
| 前端 | 展示 Agent 回答、引用来源、人工确认卡片 |

### 10.2 当前事实查询规则

当用户问题涉及当前状态时，必须调用 Java 工具 API，例如：

- “TASK-102 现在完成了吗？”
- “这个风险现在还打开吗？”
- “当前项目还有多少未完成任务？”

记忆系统只能提供历史依据，不能替代业务表回答当前状态。

### 10.3 高风险动作规则

涉及以下动作时，Agent 只能生成建议或人工确认卡片：

- 删除项目、任务、风险、需求；
- 修改权限或成员；
- 对外发送通知；
- 自动创建、关闭、更新任务或风险；
- 将历史分析结论写入业务对象。

执行路径必须是：

```text
Agent 生成建议
  -> 前端展示人工确认卡片
  -> 用户确认
  -> Java 工具 API 执行
  -> Trace 和状态日志记录
```

## 11. 排序与上下文组装

### 11.1 候选来源

候选记忆来自三路：

```text
图谱召回候选
+ 向量召回候选
+ 关键词召回候选
```

### 11.2 排序因子

第一版使用规则排序 + reranker，排序因子包括：

| 因子 | 说明 |
|---|---|
| 图谱路径距离 | 距离当前实体越近越优先 |
| 关系类型权重 | `CAUSES`、`RESOLVES`、`SUPERSEDES` 等强关系优先 |
| 向量相关度 | 当前问题和记忆摘要的语义相似度 |
| 关键词命中 | 任务编号、接口名、模块名命中优先 |
| 记忆价值分 | 高价值决策、风险、问题结论优先 |
| 时间新鲜度 | 当前状态相关内容优先使用较新记录 |
| 置信度 | 高置信抽取结果优先 |
| 记忆状态 | `ACTIVE` 优先，`SUPERSEDED` 默认不作为当前结论 |

### 11.3 上下文结构

最终提供给 LLM 的上下文建议分为四块：

```text
1. 用户当前问题
2. 当前业务事实
3. 历史事件链路
4. 原始证据片段
```

这样可以避免 LLM 把历史结论误当成当前事实。

## 12. 开发计划

### 12.1 第一阶段：事件图谱基础能力

目标：从文本记忆和 Trace 中抽取实体、事件和关系。

任务：

1. 定义实体、事件、关系的 Pydantic Schema；
2. 实现结构化抽取 Prompt；
3. 实现实体归一化和别名处理；
4. 设计关系表版图谱存储；
5. 写入 `source_memory_id`、`source_trace_id` 和 `confidence`。

验收：

- 一段历史对话可以抽取出实体、事件和关系；
- 每个节点和关系都可以追溯来源；
- 低置信度结果不会进入默认召回链路。

### 12.2 第二阶段：图谱召回链路

目标：查询时能从实体出发召回相关历史链路。

任务：

1. 实现查询实体识别；
2. 实现实体归一化；
3. 实现 1~2 跳邻域扩展；
4. 实现图谱候选打分；
5. 返回图谱路径和证据来源。

验收：

- 能根据模块查询相关风险；
- 能根据任务查询相关历史决策；
- 能解释召回路径。

### 12.3 第三阶段：混合召回与上下文组装

目标：将图谱召回、向量召回、关键词召回合并，并生成可控上下文。

任务：

1. 合并图谱候选、向量候选、关键词候选；
2. 实现去重和排序；
3. 接入 reranker；
4. 组装当前事实、历史链路和证据片段；
5. 记录检索 Trace。

验收：

- 同一问题可以看到候选来源；
- 最终回答引用的记忆可追踪；
- 上下文不会混淆历史结论和当前事实。

### 12.4 第四阶段：状态与冲突管理

目标：避免旧记忆污染新回答。

任务：

1. 引入记忆状态；
2. 识别新旧结论替代关系；
3. 查询时过滤或降权过期记忆；
4. 对冲突结论进行提示；
5. 对当前状态类问题调用 Java 工具 API 校准。

验收：

- 已关闭风险不会被回答成当前未关闭风险；
- 被替代决策不会作为当前建议直接输出；
- 回答能说明“历史上存在，但后来已处理”。

### 12.5 第五阶段：神经记忆增强预留

目标：为后续学习排序和图嵌入留出接口，不在当前阶段强行实现。

任务：

1. 记录排序特征；
2. 记录用户反馈；
3. 记录 used_memory_ids；
4. 保留 rank_score 和 retrieval_source 字段；
5. 预留图嵌入向量字段。

验收：

- 后续可以基于 Trace 分析排序效果；
- 后续可以替换规则排序为学习排序；
- 当前工程不依赖未完成的训练能力。

## 13. 风险与取舍

| 风险 | 说明 | 取舍 |
|---|---|---|
| 抽取错误污染图谱 | LLM 可能抽错实体或关系 | 用置信度、Schema 校验和来源追溯控制影响 |
| 工程复杂度上升 | 图谱会增加写入和查询链路 | 先用关系表和有限实体类型控制复杂度 |
| 查询延迟增加 | 多路召回和 reranker 会增加耗时 | 图谱写入异步，在线只做轻量邻域扩展 |
| 旧记忆污染回答 | 历史结论可能已经过期 | 使用状态、时间和 Java 当前事实校准 |
| 图谱节点碎片化 | 同一实体可能出现多个名称 | 维护实体别名和归一化 key |
| 上下文过长 | 多跳链路可能产生大量候选 | 默认 1~2 跳，限制候选数和证据片段长度 |

## 14. 验收标准

1. 能从历史对话或 Trace 中抽取实体、事件和关系。
2. 能将抽取结果写入关系表版事件图谱。
3. 每个实体、事件和关系都能追溯到 `source_memory_id` 或 `source_trace_id`。
4. 查询时能识别用户问题中的核心实体并进行归一化。
5. 能基于实体进行 1~2 跳图谱邻域扩展。
6. 能将图谱召回、向量召回和关键词召回合并排序。
7. 能在回答上下文中区分当前业务事实和历史记忆。
8. 当前状态类问题必须通过 Java 工具 API 校准。
9. 已替代、过期或冲突的记忆不会被直接作为当前结论输出。
10. Trace 中能记录召回候选、最终使用记忆、引用路径和回答结果。
