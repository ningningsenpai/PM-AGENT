2026-09-08，分支 `codex/project-analysis-mvp`，只推送该任务分支。后端及调试脚本已完成固定 MVP 样本验收；不代表任意真实项目、并发规模或生产部署均已验证。

## 实现结果与代码入口

```text
项目创建 → 文件 plan → 上传/覆盖/删除 → 解析 → 状态与定向重试
  → 持久化会话 → 只读工具问答 → 显式 learn → 开发/风险报告
  → 用户纠正 → 显式 learn → 有效内容更新 → 后续回答核对原文

API → 公开业务 Service → Repository → MySQL
          ├─ LLM 编排 → ToolRegistry → ToolExecutor → 公开 Service
          └─ MinIO 原文件、解析产物及学习快照
Redis：JWT 会话与已有缓存；MySQL：业务状态、有效上下文与调用轨迹
```

## 最小算法与边界

1. 文件同步沿用规范路径和 SHA-256 比较，测试脚本的 `update` 聚合覆盖与删除接口。
2. 用户词条采用归一化文本、Aho-Corasick 和最长匹配；按用户、项目、有效版本编译缓存。
3. 学习对消息游标之后的用户原话执行一次结构化提取，规范主题去重、明确替代、乐观版本检查；助手输出和失败工具结果不作为学习事实。推断待确认，明确确认才生效，短期默认七天。
4. 召回先过滤所有者、项目、状态和期限，再做词法相关性排序；持久化会话最多预读两个文件、合计 12 KiB 原文。摘要、原文和用户陈述分别标记，摘要未提及不能推断原文不存在。
5. 精确工具最多返回 200 行、32 KiB；服务器核对内容哈希和真实行号，带截断标记，复用脱敏规则。
6. 报告分批取证、合并去重，服务端分配证据 ID 并渲染引用；来源版本变化拒绝保存。引用编号错误限定纠正一次；文件详情字段错误也限定纠正一次，保持严格 Schema，不填空值伪造成功。
7. 模型选择只读工具，经输入校验和 Service 执行后按 `tool_call_id` 回填；限制模型交互和工具次数，调用、校验失败、耗时及 token 可在 run 中查询。

三轮分别出现 1、1、2 次召回限额拦截，保留为失败调用，不计为成功覆盖。既有上限是每次请求三次不同召回，前置召回占一次；模型用尽后继续检索时受到拒绝。错误完整回填，回答均明确说明风险专项检索未成功，后续原文工具与报告完成核查，没有将失败工具结果学成事实。第十二轮有一次无效重复检索，仍受限并已记入费用。这些属于已解释的边界事件，不是零错误调用率。

最终汇总脚本最初把所有工具失败状态都设为不通过，因上述限额事件停止。逐条审阅后按原计划的“限额错误可观察、无未解释失败”核对，要求每个失败 callId 都有审阅记录、错误码限定为召回上限且业务运行成功；没有更改工具状态、事实基准或模型输出。

每轮均完成创建、plan、upload/update、parse/status、会话、八工具、learn、两类报告、纠正、再次问答及重启恢复。报告核心能力和风险结论无误；修改删除鉴权未被称为已实现，部署未开始，查询 SQL 注入与参数化新增区分正确，原日期与纠正后的日期分别归于文档和有效记忆。被展示的精确引用可按本轮源文件行号或用户消息定位。基准 F01 的项目名称与代号未在每份报告完整覆盖，未默认记为正确。

用户与项目隔离检查通过，未观察到固定用例中的跨用户泄露或项目记忆跨项目传播。用语质量和证据语义强度仍需人工审阅，不能把“引用 ID 存在”当作模型每句话均准确。
