# PM-Agent 项目深度问答

本文档从产品定位、请求链路、Agent 编排、数据与文件一致性、分层检索、证据治理及测试体系等角度，总结 PM-Agent 当前实现与主要设计取舍。内容以当前代码为准，并明确区分已实现能力、当前边界与后续演进方向。

## 1. 项目介绍

### 1.1 三分钟介绍

PM-Agent 面向个人开发者和小型研发团队，主要解决项目资料分散、上下文持续膨胀、项目现状难以判断，以及大模型回答缺乏来源依据的问题。

普通知识库问答通常将文档切片后直接检索，但研发项目中的信息具有明显层次：代码反映当前实现，需求和设计文档描述目标，项目规范定义约束，对话还可能包含最新决策和用户纠正。直接把全部资料交给模型，不仅会增加上下文成本，也容易混淆“已经实现、计划实现和用户建议”。

PM-Agent 因此建立了完整的项目资料闭环：前端同步项目目录，后端通过 SHA-256 判断文件新增、修改、移动和删除；文件写入 MinIO 后进行结构化解析，生成全局索引、文件详情、项目规范、长期记忆和短期记忆。用户提问时，系统先完成输入归一化和轻量召回，再由受限 Agent 根据问题类型选择工具，必要时读取精确原文，最终返回带来源的项目回答，或者通过独立流程生成开发报告和风险报告。

项目目前支持项目与文件管理、项目问答、多维分析、上下文学习、开发报告、风险报告和运行轨迹查询。作为个人项目，主要工作覆盖产品边界与整体架构、Vue 与 FastAPI 前后端闭环、MySQL 与 MinIO 文件一致性、分层知识资产、归一化与可解释检索、模型原生工具调用、多维请求理解、对话记忆、证据型报告及自动化测试体系。

### 1.2 为什么不只是“大模型加知识库”

知识库主要解决“从静态文档中找到相似文本”，PM-Agent 还需要解决以下项目级问题：

- **事实生命周期**：文件修改或删除后，旧索引、规则和证据需要失效。
- **状态区分**：不能把规划写成已实现，也不能把用户建议写成项目事实。
- **多来源冲突**：代码、文档、规范和用户纠正可能同时存在并相互矛盾。
- **复合分析**：进度、风险、下一阶段计划和规范核查需要不同来源与分析顺序。
- **权限控制**：模型不能自行生成路径、SQL 或项目 ID 越权读取数据。
- **过程恢复**：模型超时、页面断开或重复提交后，不能重复生成或丢失运行状态。
- **证据追溯**：关键结论需要关联当前文件哈希、真实行号和来源版本。
- **长期协作**：目标、临时事项和表达偏好需要分类保存，而不是全部塞进聊天历史。

因此，RAG 是 PM-Agent 的底层能力之一，项目的核心是围绕项目状态建立可更新、可失效、可恢复和可追溯的工程闭环。

## 2. 请求链路与多维分析

### 2.1 项目问答链路

从用户发送问题到返回答案，当前正式链路如下：

1. 前端生成 `X-Trace-Id` 和 UUID 幂等键，携带 JWT 提交消息，并在 `sessionStorage` 保存待恢复操作。
2. FastAPI 校验 JWT，并通过 Redis 中的 `jti` 会话确认登录状态仍然有效。
3. 后端校验会话、项目和当前用户的归属关系。
4. `RunService` 在 MySQL 创建 `agent_run`，使用用户、操作类型和幂等键的唯一约束防止重复执行，并占用当前会话运行租约。
5. 用户输入经过敏感信息处理，再进入请求理解模块。
6. 请求理解模块通过一次结构化模型调用拆分问题；失败时降级到确定性关键词规则。
7. 用户消息写入 `agent_message`；明确的上下文更新进入正式上下文，不确定内容只形成待确认草稿。
8. 系统恢复最近五组完整历史协议，避免拆开 `assistant.tool_calls` 和对应的 `tool` Observation。
9. 当前问题经过归一化和分层召回，首次最多注入五个轻量候选。
10. 后端根据请求计划生成本轮工具白名单，并将 Pydantic JSON Schema 注册为模型原生工具。
11. Agent 循环执行“模型决策—工具调用—结果校验—Observation 回传”，最多五轮模型决策、八次工具调用及三次不同的上下文召回。
12. 最终回答和完整工具协议写入 assistant 消息，运行记录更新为成功或失败终态。
13. 前端接收 JSON；连接异常时复用原幂等键，或者根据 `runId` 查询运行状态并重新加载持久化消息。

### 2.2 报告生成链路

报告生成是独立业务接口，不由聊天 Agent 隐式触发：

1. 创建幂等报告运行并记录当前来源版本。
2. 遍历当前可读文件，按最多 200 行、32 KiB 生成证据片段，单次最多收集 80 段。
3. 加入有效的短期和长期用户陈述。
4. 按约 45 KB 将证据分批交给结构化模型。
5. 校验模型引用的每个证据 ID；引用不存在时纠正一次，再失败则拒绝保存。
6. 生成结束后重新比较来源版本，期间发生文件或上下文变化则拒绝发布。
7. 服务端渲染引用并保存报告正文、证据快照和来源版本。

### 2.3 复合问题拆解

系统将复合问题转换为最多八个 `RequestUnit`，每个单元包含动作、分析对象、时间范围、依赖关系、置信度和对应用户原文。当前支持：

- 普通项目问答；
- 项目进度分析；
- 下一阶段任务草案；
- 项目风险分析；
- 项目约束核查；
- 信息来源追溯；
- 项目历史解释。

例如“分析当前进度和风险，检查是否违反项目规范，并给出下一阶段计划和依据”可拆为进度、风险、约束、规划和来源五个单元。其中下一阶段规划依赖进度分析，不同单元映射到不同召回范围：

| 分析维度 | 主要召回范围 |
|---|---|
| 进度、规划 | 文件详情、长期记忆、短期记忆 |
| 风险、约束 | 项目规范、文件详情、必要的原文证据 |
| 来源追溯 | 文件、精确证据、更新日志 |
| 历史解释 | 记忆、变更记录、已有报告 |

请求计划只控制分析范围、依赖关系和工具权限，不直接创建任务或风险业务对象。

### 2.4 Agent 形态选择

PM-Agent 采用 **确定性工作流外壳 + 有限自主规划 Agent**。

确定性部分包括身份与权限、状态机、幂等与事务边界、请求协议、工具白名单、上下文预算、报告证据校验和数据持久化。模型自主决定如何理解复合问题、选择已授权工具、调整召回关键词、补充原文并整合答案。

完全自主 Agent 的路径、成本和写入行为难以预测；完全固定工作流又难以覆盖自然语言问题的多种组合。混合方式在灵活性、可测试性、成本和安全性之间取得平衡。

## 3. 模型原生工具调用

### 3.1 工具注册

每个工具统一声明名称、说明、Pydantic 输入与输出模型、操作类型、确认策略和超时时间。后端根据输入模型生成 JSON Schema，并只向模型暴露当前请求允许的工具。

当前工具覆盖项目查询、文件列表、上下文召回、上下文条目、变更历史、报告读取和原文证据读取等只读能力。用户、项目、会话和运行身份由服务端注入，不接受模型自行指定。

### 3.2 执行与异常处理

工具执行器依次完成白名单检查、注册表查询、JSON 解析、Pydantic 入参校验、确认门禁、超时控制、业务 Service 调用和输出结构校验。

| 异常场景 | 处理方式 |
|---|---|
| 参数错误 | 返回 `TOOL_ARGUMENT_INVALID`，允许模型在剩余轮次内纠正 |
| 未注册或未授权 | 返回结构化失败，不执行工具 |
| 工具超时 | 终止等待并返回超时 Observation |
| 业务异常 | 映射为安全错误信息后回传模型 |
| 输出结构错误 | 按工具执行失败处理 |
| 重复调用 ID | 协议校验直接拒绝 |
| 超过循环上限 | 终止运行并记录失败 |

相同召回请求使用请求内缓存；不同调用 ID 但参数相同的普通只读工具目前不做统一语义去重。写工具没有开放给普通聊天 Agent，高风险能力必须经过人工确认。

## 4. 输出方式与断线恢复

从使用场景看，项目问答主要是服务端向客户端单向发送 Token、工具状态和完成事件，SSE 比 WebSocket 更符合标准 HTTP 接入、网关代理、日志追踪和低频单向流式输出需求。

但当前正式持久化会话接口仍是 **JSON 响应 + Agent Run 状态恢复**。`stream_chat()` 和 `token`、`tool_call`、`tool_result`、`done`、`error` 等事件结构已经存在，但尚未接入正式 `StreamingResponse` 路由。

当前断线恢复策略为：

- 未取得 `runId` 时，使用原幂等键重新提交；
- 已取得 `runId` 时，仅查询运行状态，不重新生成；
- 运行完成后重新读取服务端消息或报告；
- 页面刷新后从 `sessionStorage` 恢复未完成操作。

后续正式接入 SSE 时，还需要增加单调事件 ID、事件序号持久化、`Last-Event-ID` 回放和按 `runId` 补拉。当前只能可靠恢复最终结果，不能声称中间 Token 已实现无损重放。

## 5. 对话、记忆与数据职责

### 5.1 持久化模型

| 数据实体 | 职责 |
|---|---|
| `agent_conversation` | 用户、项目、标题、当前运行和会话租约 |
| `agent_message` | 消息角色、正文、所属运行和完整工具协议 |
| `agent_run` | 幂等键、请求哈希、Trace、状态、事件、结果和错误 |
| `agent_learning_draft` | 待确认学习草稿、状态和乐观锁版本 |
| `pm_report` | 报告正文、来源版本和证据快照 |

### 5.2 记忆划分

- **对话历史**：保持当前会话连贯性，当前恢复最近五组完整协议。
- **短期记忆**：当前阶段焦点、临时任务和待核实事项；未指定期限时默认七天。
- **长期记忆**：稳定目标、已确认决策、里程碑和经过验证的项目事实，一般不自动过期。
- **用户偏好**：只影响回答格式、详略和协作方式，不能作为项目事实证据。

当前 `user_habits` 按“当前用户、当前项目”隔离，还不是跨项目共享的全局用户画像。

### 5.3 MySQL、MinIO 与 Redis

| 组件 | 保存内容 |
|---|---|
| MySQL | 用户、项目、文件元数据、对象路径、SHA-256、状态、锁版本、会话、消息、运行、草稿和报告记录 |
| MinIO | 原始项目文件，以及 Index、Detail、项目规范、长短期记忆、用户习惯和更新日志 |
| Redis | 可撤销 JWT `jti` 会话，以及文件写请求的短期幂等门禁 |

MinIO 是文件内容事实源，MySQL 是身份、状态和版本控制面。读取文件时必须通过对象位置和内容哈希相互验证。

## 6. 文件增量更新与最终一致性

### 6.1 增量更新

前端提交路径、大小、修改时间和 SHA-256，后端生成未变化、修改、移动、新增、删除、拒绝和歧义七类同步结果。

- 内容和路径均未变化：保留 Detail，不重复调用模型。
- 内容变化：覆盖对象，清空旧摘要、关键词和 `detail_ref`，删除该文件的规范来源，再重新解析。
- 路径变化：更新对象路径，并使旧 Detail 和旧路径锚点失效。
- 文件删除：删除原对象、Detail 和对应规范来源，再重建索引。
- 重新上传：产生新文件身份，或通过覆盖接口更新现有文件。
- 已生成报告：保留当时证据快照，但只代表历史状态。
- 历史工具结果：可以保留，下一轮关键事实需要重新召回。

当前限制是：同一文件重新解析时能够替换文件派生的长期事实，但文件被直接删除后，相关长期记忆尚未覆盖所有自动失效场景。因此，涉及已移除来源的结论必须通过现存原文重新核实。

### 6.2 状态流转

上传、覆盖和删除都先在 MySQL 发布中间状态，再在数据库事务外操作 MinIO：

```text
上传：uploading → active/success 或 upload_failed/failed
覆盖：active → updating → active/success、verify_required 或 upload_failed
删除：active → deleting → 删除完成或 delete_failed
```

索引和证据读取只接受 `active + success`，并再次校验 SHA-256。该方案不是分布式事务意义上的原子一致性，而是通过可观察状态、失败重试和读取校验实现最终一致性。进程在对象写成功、数据库提交前崩溃时，仍需要重试或对账机制恢复。

### 6.3 幂等键与乐观锁

**幂等键解决重复请求**：文件接口通过 Redis `SET NX` 短期防重；Agent 运行通过 MySQL 唯一约束和请求哈希持久化防重。相同键、相同内容复用原运行，相同键、不同内容直接冲突。

**乐观锁解决并发修改**：文件更新、移动和删除同时检查文件 ID、当前状态和 `lock_version`。成功后版本加一，失败说明数据已经被其他操作修改。

版本冲突后应重新读取文件状态和最新版本，再判断原操作是否仍然成立；不能拿旧版本盲目重试。Agent Run 的传输恢复则继续使用原幂等键查询结果。

## 7. 输入归一化与分层检索

### 7.1 完整检索流程

1. 查询逐字符执行 Unicode NFKC。
2. 使用 `casefold` 统一英文大小写并折叠连续空白，同时保留到原文的位置映射。
3. 合并公共、项目管理领域和项目三级词库，记录版本集合与合并指纹。
4. 使用 Aho-Corasick 一次扫描找出全部别名命中。
5. 根据起始位置、长度、词库作用域和优先级执行最长不重叠匹配。
6. 将别名映射为标准术语并恢复原文命中范围。
7. 生成带权查询词：标准术语 1.5、ASCII 技术词 1.25、完整查询短语 1.0、中文回退片段 0.5。
8. 根据请求意图选择文件、规范、记忆、偏好或更新日志等来源。
9. 从 `index.json` 和正式上下文资产生成候选，并过滤失效文件、过期记忆和无效规则。
10. 使用高、中、低字段完成初排，权重分别为 6、3、1；完整短语加 8，高重要度文件加 1。
11. 只加载初排前 8～16 个文件的 Detail，并校验项目、文件、路径、哈希和 `detail_ref`。
12. 将 Detail 中的关键词、实体、主题、摘要、风险和内容切片加入字段后重新评分。
13. 选择最相关的原文切片范围并输出 Top-K。
14. 需要核实代码、实现或行号时，为最多两个文件补充合计 12 KiB 的脱敏原文。

当前线上排序是确定性字段词法评分，并非 BM25。

### 7.2 为什么使用 Aho-Corasick

Aho-Corasick 主要承担查询术语归一化，而不是完整的文档排序。它适合一次扫描同时匹配大量稳定技术术语，能够保留别名、标准词和命中位置，结果清晰可解释。

它的不足是只能处理字面匹配，无法理解真正的语义近似；词库变化后需要重建自动机，也不处理 TF、IDF 和文档长度。

倒排索引适合大规模文档过滤；BM25 能利用词频、逆文档频率和文档长度排序；Elasticsearch 进一步提供分词、过滤和分布式索引能力，但会增加部署和索引一致性成本。未来可以采用“Aho-Corasick 做查询归一化，BM25F 或 Elasticsearch 做文档召回”，两者并不冲突。

### 7.3 同义词与字段权重

公共、领域和项目词库按作用域合并。项目词库优先级最高，但别名冲突必须显式声明覆盖关系；未声明的冲突会阻止词库发布。命中别名统一映射为 canonical 后再参与召回。

误召回主要通过停用片段过滤、最长不重叠匹配、显式词库覆盖、按意图限制来源、状态与哈希过滤、Detail 二次排序，以及不强行填满 Top-K 等方式控制。

当前权重来自领域规则和固定样本回归，并非模型学习结果；子串匹配仍可能误召回，后续需要扩大人工标注集并按问题类型校准阈值。

## 8. 证据绑定与上下文预算

### 8.1 原文证据治理

原文工具只接受当前项目的 `file_id` 和行号范围，不接受任意路径或 URL。服务端校验权限、文件状态和 SHA-256，并返回真实路径、内容哈希、实际行号、截断状态和脱敏标记。

报告链路使用强绑定：模型只能引用本批存在的证据 ID，服务端验证后再渲染路径和行号，并在发布前复核来源版本。

普通聊天目前主要依靠 Prompt 要求模型标注来源，尚未像报告一样对最终自然语言中的每个引用执行服务端结构化校验。因此，报告属于强证据绑定，普通问答属于受控 Grounding，但还不是逐条 Claim 校验。

### 8.2 12 KiB 原文预算

12 KiB 是单次 Agent 请求的前置原文预读预算，不是整个会话上限。当前最多预读两个文件；需要更多内容时使用精确证据工具，报告生成也不受该额度限制。

该预算来自固定样本下的工程对比：早期全量注入约 47.7 KiB，控制到 12 KiB 后减少约 74.8%，同时为系统提示、历史、工具 Schema、摘要和输出保留空间。

使用字节作为第一层限制，是因为 MinIO、网络和日志都以字节为基础，不依赖具体模型的 Tokenizer，便于稳定测试。模型调用前仍由 `LLMContextBuilder` 再按 Token 预算裁剪历史。

## 9. 检索评测与向量方案

### 9.1 Recall@3 与 MRR 的适用范围

当前 A/B 基准包含 **3 个固定检索问题**，运行在同一份经过七轮更新的真实 MinIO 项目快照上：

1. 当前进度与下一阶段；
2. 认证凭证安全约束；
3. 代码实现位置。

相关性标准由脚本中的人工来源判定条件定义，例如候选必须包含特定事实标记，或者逻辑路径必须等于目标文件。当前准确表述是：

> 在三个固定真实快照查询上，词法检索平均 Recall@3 和 MRR 均为 1.0。

该指标不能外推为大规模通用效果。当前排序没有训练过程，因此不存在训练集泄漏，但仍有测试集过小、问题和规则共同调优造成回归集过拟合的风险。

后续应按项目划分开发集、验证集和冻结测试集，增加同义改写、无答案、错误前提、跨文件问题和完整相关文档标注，并同时评估 Recall、MRR、NDCG、无答案识别率和回答忠实度。

### 9.2 为什么当前不引入向量数据库

当前固定样本结果为：

| 方案 | Recall@3 | MRR |
|---|---:|---:|
| 词法召回 | **1.0** | **1.0** |
| 稀疏字符向量 | 1.0 | 0.8333 |
| 词法与向量混合 | 1.0 | 1.0 |

在现有规模下，向量方案会增加 Embedding 调用、向量存储、增量索引、版本同步和排序解释成本，却没有形成可测收益，因此当前暂不引入，而不是永久放弃。

当单项目达到数百或数千文件、数万切片，语义改写和跨语言问题明显增多，或者词法 Recall 在冻结测试集持续下降时，应重新评估。演进方向优先考虑 BM25F 与向量双路召回，再通过 RRF 融合、SimHash 去重和轻量重排提升质量。

## 10. 自动化测试体系

当前通过项目虚拟环境实际收集到 **383 个 Pytest 用例**。用例均位于 `tests/unit`，内部按架构职责划分：

| 测试区域 | 数量 | 主要内容 |
|---|---:|---|
| 业务模块 | 150 | 用户、项目、文件同步、上传、解析、状态机和 API |
| Agent 与会话 | 82 | 工具循环、协议、多轮持久化、学习和事务 |
| 项目知识资产 | 47 | Index、Detail、规范分区和来源替换 |
| 输入归一化与检索 | 38 | 词库、Aho-Corasick、规划、排序和原文补证 |
| LLM 适配层 | 33 | Token 预算、结构化输出、工具协议和 HTTP 异常 |
| 基础设施与数据库维护 | 33 | 时间、ID、MinIO、迁移和清理任务 |

模型相关测试不依赖自然语言措辞，而使用可控 Fake LLM 验证空输出、截断 JSON、字段缺失、结构纠正、工具能力缺失、Token 预算、请求取消和 HTTP 异常。

工具层覆盖未知工具、非法参数、越权、输出结构错误、超时、重复调用 ID、调用上限和协议配对。一致性层覆盖 MinIO 操作失败、哈希冲突、乐观锁冲突、幂等请求、Detail 发布失败、规范来源替换、运行取消和租约恢复。

真实 HTTP、六文件固定样本和 MinIO 基准脚本属于独立验收，不包含在 383 个 Pytest 数量中。

本轮复核中，383 项均成功收集；全量执行结果为 380 项通过，3 项因当前 Windows 临时目录 ACL 导致 `tmp_path` 创建失败，错误发生在测试环境初始化阶段，不是业务断言失败。

## 11. 当前边界与后续演进

当前需要继续完善的重点包括：

1. 将现有流式 Agent 接入正式持久化会话接口，并实现 SSE 事件持久化与断点回放。
2. 为普通聊天增加与报告一致的结构化 Claim—Evidence 校验。
3. 完善文件删除后，文件派生长期记忆的自动失效和对账恢复。
4. 扩大跨项目人工标注检索基准，避免小样本回归集过拟合。
5. 在数据规模和语义查询复杂度增长后，重新评估 BM25F、Embedding、RRF 和重排方案。
6. 增加对象写成功但数据库提交中断等崩溃窗口的自动对账任务。
