# 云端上下文与显式学习改造

> 2026-09-09 设计修正：显式学习只把原来的隐式学习改为“模型提议、用户确认、后端写入”，不改变项目既有的 MinIO 固定文件布局。 `context/manifest.json`、`context/versions/` 及其分类文件不得作为正式上下文来源。当前代码尚未完全符合本文档，实施偏移见第 8 节。

## 1. 背景

项目最初约定以 `system/` 下的固定文件保存当前生效的项目上下文。文件解析、项目更新、Agent 问答和记忆整理都应读取并更新这些固定对象。

显式学习的提出，是为了替代对话后的隐式学习：模型可以从用户与 Agent 的对话中提取项目规则、短期记忆、长期记忆和用户习惯候选，但候选在用户查看、修改并确认前不得生效。该能力增加的是用户对“让 Agent 记住什么”的控制权，不是建立第二套上下文存储系统。

后续实现把显式学习的草稿版本和正式上下文共同放入 `context/manifest.json` 与不可变版本目录，导致固定文件、版本文件和索引引用并存，偏离了原始设计。本次先统一设计口径，代码迁移另行实施。

## 2. 目标与边界

### 2.1 目标

- 用户能够查看模型从本人对话中提取的候选内容。
- 用户能够选择、编辑、反馈、确认或放弃候选。
- 只有用户确认的候选才能更新正式上下文文件。
- 文件解析和显式学习使用同一份固定项目规范，不建立平行规则源。
- Agent、报告和前端“已学习内容”均以固定文件中的当前内容为准。
- 更新过程具备幂等、并发冲突检测、来源追踪和失败恢复能力。

### 2.2 不做范围

- 不恢复自动生效的隐式学习。
- 不新增 `system/context/`、`context/manifest.json` 或 `context/versions/`。
- 不新增 `project_rule.json`、`term.json` 等正式上下文文件。
- 不让草稿、反馈、运行结果或数据库条目成为 Agent 召回的第二事实源。
- 不允许模型直接写 MinIO、数据库或业务实体。

## 3. 正式上下文文件

项目当前生效的上下文只保存在以下固定位置：

```text
PM-AGENT/{userId}/{projectId}/
├── project/{storageName}
├── user/{storageName}
└── system/
    ├── index.json
    ├── project_specification.json
    ├── project_specification/
    │   ├── development_approach.json
    │   ├── technical_constraints.json
    │   ├── coding_rules.json
    │   ├── document_rules.json
    │   └── risk_rules.json
    ├── long_term_memory.json
    ├── short_term_memory.json
    ├── update_journal.jsonl
    ├── file_details/
    │   └── {storageUuid}-{contentHash}-{pathHash}.json
    └── user_habits/
        ├── work.json
        ├── thinking.json
        ├── specification.json
        ├── tooling.json
        └── life.json
```

正式读取规则如下：

- 项目规范先读取 `system/project_specification.json` 清单，再读取清单指向的五个规则分区。
- 长短期记忆只读取 `system/long_term_memory.json` 和 `system/short_term_memory.json`。
- 用户习惯只读取 `system/user_habits/*.json`。
- 项目变化只读取 `system/update_journal.jsonl`。
- 文件详情通过 `system/index.json` 和 MySQL 当前文件投影定位。
- `system/index.json` 只保存固定路径，不保存某次学习版本目录的引用。

MinIO 中同一对象键的覆盖表示更新当前内容。即使 MinIO 桶开启了底层对象版本能力，应用也不得通过改变业务读取路径选择版本。

## 4. 数据职责

| 数据 | 权威位置 | 用途 |
|---|---|---|
| 当前项目文件状态与分析投影 | MySQL `pm_project_file` | 文件列表、状态、当前详情引用和乐观锁 |
| 当前生效的项目上下文正文 | MinIO `system/` 固定文件 | Agent 召回、报告生成、前端已学习内容 |
| 学习候选、反馈、确认计划和处理状态 | MySQL Agent 工作流数据 | 用户审核、幂等恢复、并发检查，不直接参与召回 |
| 学习来源和修改历史 | MySQL 变更记录与 `update_journal.jsonl` | 审计、纠正、问题定位 |
| 模型及工具调用轨迹 | MySQL `agent_run` | 运行状态、错误、费用和 Trace |

学习工作流可以在 MySQL 中保存待确认正文，但这些数据只是提案。前端“已学习内容”必须以固定文件的正式内容为基础，MySQL 只补充来源、确认人、变更原因等元数据。

## 5. 显式学习流程

### 5.1 提取与确认

1. 用户主动点击学习，后端读取本会话尚未处理的用户消息。
2. 模型只能根据用户消息原文生成候选，并为每条候选返回可核验的连续原文。
3. 后端校验来源、目标文件、作用范围和候选结构，将结果保存为待确认草稿。
4. 前端展示候选、来源、目标文件、替换关系和冲突信息。
5. 用户可以编辑候选，或针对选中候选提交自然语言反馈后重新整理。
6. 用户确认时，后端重新读取目标固定文件并检查当前 ETag、内容哈希和冲突。
7. 后端把确认内容稳定合并到目标固定文件的原对象键，再记录更新日志和工作流结果。
8. 未选择、未确认、来源不可靠或发布失败的候选不参与 Agent 召回。

助手回答、工具结果和模型自行推断不能作为用户学习事实。用户直接纠正、确认、失效或晋升已有内容时不需要再次调用模型。

### 5.2 候选与目标文件映射

| 候选内容 | 正式目标 | 规则 |
|---|---|---|
| 项目规则、技术约束、编码规范、文档规范、风险边界 | `system/project_specification/{targetSection}.json` 的 `managed_rules` | 与按 `file_id` 分组的文件规则隔离，保留用户确认来源 |
| 当前任务、待确认事项、短期线索 | `system/short_term_memory.json` | 默认有期限，过期后不召回 |
| 稳定决策、长期偏好、阶段结论、已验证结论 | `system/long_term_memory.json` | 需要用户明确确认或从短期记忆显式晋升 |
| 工作、思考、规范、工具、生活习惯 | `system/user_habits/{category}.json` | 按既有五个分类更新 |

“术语词条”不是独立正式文件类型。属于项目命名或固定约定的内容应合并到项目规范；属于用户表达偏好的内容应合并到相应用户习惯；无法明确归类时继续停留在草稿中，不得创建新的正式文件。

## 6. 文件解析与显式学习的关系

文件解析和显式学习都会影响项目规范分区，但写入区域不同：

- 文件解析只根据本轮成功 `file_details` 的五类候选替换 `file_rule_groups[file_id]`。
- 显式学习只根据用户确认的对话候选更新 `managed_rules`。
- 文件发生变化时，移除或替换对应 `file_id` 规则组，但不修改 `managed_rules`。
- 用户纠正规则时，后续文件解析发现冲突应保留人工规则并记录待核对差异。
- 两条链路必须通过同一个项目规范服务读写固定文件，不能分别维护平行快照。

项目文件解析的发布顺序保持为：

1. 写入新的文件详情对象；
2. 条件回填 MySQL 当前详情引用；
3. 读取五个规则分区并按 `file_id` 替换本轮来源规则；
4. 条件写入变化分区并刷新 `project_specification.json` 清单；
5. 从 `project_facts` 增量更新长期记忆；
6. 从 MySQL 全量重建并覆盖 `index.json`；
7. 记录 `update_journal.jsonl`。

## 7. 并发、一致性与恢复

- 每个固定 JSON 文件更新前读取当前 ETag 或内容哈希，覆盖时执行条件写入。
- 幂等键标识一次用户确认操作；结果未知时使用原键查询或恢复，不重复调用学习模型。
- 同一文件发生并发变化时拒绝无条件覆盖，重新读取当前内容并让用户核对冲突。
- 一个草稿涉及多个目标文件时按目标文件分别报告成功与失败；恢复只处理未成功目标。
- `update_journal.jsonl` 只记录已经完成的更新，不先写成功日志再尝试正式文件。
- `index.json` 不承担上下文版本路由，只记录固定系统路径和当前项目文件快照。
- 缓存必须按对象 ETag 或内容哈希失效，不能把数据库版本号或 manifest revision 当作正式内容版本。

MinIO 不提供跨多个对象的数据库事务，因此不能把“创建整套版本目录”当成跨文件一致性的替代。业务一致性依靠目标文件级条件写、幂等恢复、明确的部分成功状态和更新日志完成。

## 9. 开发顺序

1. 固化本文档、第 19 篇、Agent 设计和接口规范的统一口径。
2. 设计现有学习草稿和变更记录向 MySQL 工作流状态的迁移方案。
3. 提供一次性校验工具，把当前 ContextStore 有效内容与固定文件逐项目对比。
4. 将确认、纠正、晋升和失效操作切换为固定文件条件更新。
5. 将文件解析的项目规范刷新切回固定文件。
6. 将 Agent、报告和前端已学习内容切回固定文件读取。
7. 删除运行时代码中的 manifest 特殊读取和版本目录发布。
8. 完成真实 MinIO、MySQL、断网恢复和并发冲突验收后，再评估旧对象清理。

## 10. 验收标准

- 新项目的 `system/` 目录只包含约定的固定文件和两个固定子目录。
- 文件解析成功后，原路径的 `project_specification.json` 和 `index.json` 更新时间及内容发生预期变化。
- 显式学习候选在用户确认前不改变任何正式上下文文件。
- 用户确认后只更新候选对应的固定文件，不创建 Context 版本目录。
- 文件解析不能覆盖用户确认的项目规则。
- Agent、报告和前端读取到的规则、记忆、习惯与 MinIO 固定文件一致。
- 并发修改返回明确冲突，不发生静默覆盖。
- 断网后恢复不会重复写入、重复调用模型或生成重复条目。
- 仓库文档不再把 `context/manifest.json` 描述为正式事实源。
