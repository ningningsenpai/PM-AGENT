# 接口规范

## 1. 通用约定

业务接口前缀为 `/api/v1`，JSON 字段使用小驼峰。统一响应：

```json
{
  "code": 0,
  "message": "成功",
  "data": {},
  "traceId": "01H..."
}
```

除健康检查与 SSE 外，业务异常也使用该结构。请求校验失败为 `10001`，未处理异常为 HTTP 500 与 `90001`。

用户 ID 和项目 ID 在 MySQL 与 Python 内部均为 64 位整数；所有 JSON 请求、响应、Agent 工具结果和项目上下文 JSON 统一使用十进制字符串，避免浏览器对大于 `2^53-1` 的整数产生精度损失。兼容迁移期间，后端入参也接受未加引号的正整数，出参始终序列化为字符串。

## 2. 请求头

| 请求头 | 规则 |
|---|---|
| `Authorization` | 受保护接口必填，格式 `Bearer <JWT>` |
| `X-Trace-Id` | 可选；缺失时服务端生成，并通过响应体和响应头返回 |
| `X-Idempotency-Key` | 文件上传和内容覆盖必填，最长 128 字符，两分钟内禁止重复 |

JWT 包含 `sub`、`jti`、`iat`、`exp`。Redis 中不存在对应 `jti` 会话时视为未登录。

## 3. 认证与用户

| 方法 | 路径 | 请求 |
|---|---|---|
| `POST` | `/api/v1/auth/register` | `{username,email,password}` |
| `POST` | `/api/v1/auth/login` | `{email,password}` |
| `POST` | `/api/v1/auth/logout` | 无 |
| `GET` | `/api/v1/users/me` | 无 |
| `PUT` | `/api/v1/users/me` | `{username,email}` |
| `PUT` | `/api/v1/users/me/password` | `{oldPassword,newPassword,confirmPassword}` |

注册和登录继续使用 JSON，不使用 OAuth2 表单。

## 4. 项目

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/projects` | 创建项目，请求 `{projectName}` |
| `GET` | `/api/v1/projects` | 当前用户项目列表 |
| `GET` | `/api/v1/projects/{projectId}` | 项目详情 |
| `DELETE` | `/api/v1/projects/{projectId}` | 惰性删除项目，不删除文件与对象前缀 |

项目响应包含 `id`、`projectName`、`status`、`recordStatus`、`createdAt`、`updatedAt`。正常查询只返回 `recordStatus=enabled` 的记录；删除会改为 `disabled`。已删除项目不参与名称判重，再次创建同名项目时返回新项目 ID；只有 `status=init_failed` 的启用项目会复用原 ID 重试初始化。

## 5. 项目文件

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/projects/{projectId}/files` | Multipart 单文件上传 |
| `PUT` | `/api/v1/projects/{projectId}/files/{fileId}/content` | Multipart 覆盖内容 |
| `PATCH` | `/api/v1/projects/{projectId}/files/{fileId}/path` | 修改逻辑路径 |
| `GET` | `/api/v1/projects/{projectId}/files` | 文件列表 |
| `GET` | `/api/v1/projects/{projectId}/files/{fileId}/read-url` | 五分钟只读地址 |
| `DELETE` | `/api/v1/projects/{projectId}/files/{fileId}?lockVersion=0` | 删除文件 |
| `POST` | `/api/v1/projects/{projectId}/files/sync/plan` | 根据完整目录清单生成同步计划，不直接修改文件 |
| `POST` | `/api/v1/projects/{projectId}/files/parse/init?force=false` | 分析待处理文件并刷新索引、项目规范；`force=true` 时重新分析全部有效文件 |

上传表单字段为 `relativePath`、`sourceMtimeMs`、`file`。覆盖表单字段为 `sourceMtimeMs`、`lockVersion`、`file`。

上传流程先提交 `uploading/not_uploaded` 记录，再在事务外写 MinIO，成功后条件更新为 `active/success`。MinIO 失败保留可诊断记录。

项目更新不新增批量写入接口。前端先提交完整目录清单，由后端从 MySQL 权威文件快照生成 `unchanged`、`modified`、`moved`、`added`、`deleted`、`rejected` 和 `ambiguous` 七类同步计划，再分别复用上传、覆盖、路径修改和删除接口。只有 `snapshotComplete=true` 时才生成删除项，远端删除仍必须由用户确认。完整 SHA-256 是内容一致性的最终依据；只有内容哈希唯一的一对一匹配才自动认定为移动，重复内容进入 `ambiguous`，不得任意配对。

同步规划请求示例：

```json
{
  "snapshotComplete": true,
  "scope": "project",
  "items": [
    {
      "relativePath": "docs/README.md",
      "sizeBytes": 1024,
      "sourceMtimeMs": 1760000000000,
      "contentHash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "contentType": "text/markdown"
    }
  ]
}
```

规划响应中的修改、移动和未变化项同时携带本地元数据、`remoteFileId`、`remoteRelativePath` 和 `lockVersion`；新增项只携带本地元数据；删除项携带远端文件身份与锁版本；歧义项按内容哈希返回本地和远端候选集合。文件未提供非空完整哈希时进入 `rejected`，不会被误判为新增或修改；若同路径已有远端文件，该路径仍视为已观察到，不会因此产生删除计划。规划接口只用于决策，上传和覆盖接口仍会根据实际字节重新计算内容哈希并执行后端校验。

前端先执行新增、覆盖和移动。完整快照中的重复内容歧义按“新增本地项 + 删除远端项”显式展示，删除仍需用户二次确认，因此不承诺保留原文件 ID；非完整快照不自动处理歧义。任一非删除操作失败或用户取消确认时跳过本批次删除，避免项目文件在部分成功时进一步丢失。`upload_failed` 和 `verify_required` 记录允许通过内容覆盖接口恢复；内容或路径变化后使旧分析失效，随后由解析入口重新分析。

解析入口成功响应的 `data` 为：

```json
{
  "status": "success",
  "candidateCount": 2,
  "successCount": 2,
  "failureCount": 0,
  "failures": [],
  "specificationStatus": "updated",
  "indexStatus": "updated"
}
```

`force` 默认为 `false`，此时只处理 `detail_ref` 为空且重试未耗尽的有效文件；`true` 时忽略已有详情和重试次数，显式重新分析全部有效文件。强制分析失败时保留原有有效详情和投影。`status` 为 `success` 或 `partial`；文件级失败、项目规范刷新失败或索引发布失败均返回 `partial`，并通过 `failures`、`specificationStatus` 和 `indexStatus` 暴露实际结果。

`/api/v1/project-files/analyze` 已删除，不再存在 Java 到 Python 的内部分析接口。

## 6. Agent

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/agent/chat` | JSON 或 SSE 对话 |

Agent 接口需要 Bearer Token，请求体 `user.user_id` 必须与 JWT `sub` 一致。`trace_id` 用于本轮 SSE 与 Agent 工具链路追踪，`context.project_id` 用于构造受信业务上下文；工具不能接收 JWT、数据库 Session 或由模型生成的用户 ID。

当前请求示例：

```json
{
  "trace_id": "01K1...",
  "conversation_id": 20,
  "messages": [
    {"role": "user", "content": "当前项目是什么？"}
  ],
  "context": {
    "project_id": "10",
    "iteration_id": 0,
    "context_total_usage": 0,
    "task_id": 0
  },
  "user": {
    "user_id": "1",
    "tenant_id": 0,
    "user_name": "测试用户"
  },
  "stream": true,
  "llm_provider": "deepseek"
}
```

客户端只能提交 `system`、`user`、`assistant` 普通消息。`assistant.tool_calls` 和 `tool` 消息由服务端 Agent 循环产生，客户端提交时返回参数校验错误，避免伪造工具结果。

非流式成功响应的 `data` 包含 `answer`、`model`、`conversation_id`、`tool_calls` 和 `usage`。`tool_calls` 只返回工具名、已校验入参、状态、安全摘要、错误标识和耗时，不返回完整业务出参。

流式响应按以下顺序发送事件：

| 事件 | 说明 |
|---|---|
| `meta` | 连接、会话和追踪信息 |
| `tool_call` | 模型发起工具调用，包含调用 ID、工具名、参数和步骤 |
| `tool_result` | 工具完成状态、安全摘要、错误标识和耗时 |
| `token` | 模型最终回答文本增量 |
| `done` | 模型、Provider、会话和累计 token 用量 |
| `error` | 流启动后的业务错误或系统错误 |

流结束后追加 `data: [DONE]`。当前只有声明并验证原生工具调用能力的 Provider 可进入该链路；不支持的 Provider 返回 `40001`。

## 7. 主要错误码

| 范围 | 说明 |
|---|---|
| `10001` | 参数不合法 |
| `10002` | 缺少幂等键 |
| `10003` | 资源冲突或重复提交 |
| `20001` | 未登录 |
| `20002` | 无权限 |
| `20003`～`20009` | 用户、认证和系统文件访问错误 |
| `30001`～`30003` | 项目错误 |
| `30010`～`30017` | 文件业务错误 |
| `40001` | 模型提供方不支持当前工具调用模式 |
| `40002` | 模型请求了未注册工具 |
| `40003` | 工具参数不符合 JSON Schema |
| `40004`～`40005` | 工具执行失败或超时 |
| `40006` | Agent 工具调用超过步数或总次数限制 |
| `50001`～`50008` | 存储、索引、上传、解析、项目规范构建错误 |
| `90001` | 系统异常 |

## 8. 待确认问题

暂无。写工具和人工确认接口不在当前范围，新增时需要补充幂等请求头、确认状态和对应错误码。
