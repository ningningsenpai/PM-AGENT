# 05 接口规范

## 1. 背景

当前 Java 后端提供多用户认证、当前用户资料、最小项目归属和项目文件接口，不包含租户隔离。本文档定义这些接口共同遵循的响应、错误、traceId、认证和日志规则。

项目文件批次上传接口已经按本文合同落地。详细业务规则以 [18-项目文件批次上传模块设计](./18-项目文件可靠上传模块设计.md) 为唯一权威。

## 2. 目标

- 业务接口统一使用 `/api/v1`；
- 所有响应使用 `R<T>`；
- 所有响应和访问日志包含同一条请求链路的 traceId；
- Controller 记录业务入口和成功结果；
- 密码、哈希和 token 不进入日志。

| 方法 | 路径 | 权限 | 说明 |

| `GET` | `/internal/health` | 匿名 | 健康检查 |

| `POST` | `/api/v1/auth/login` | 匿名 | 邮箱密码登录 |
| `POST` | `/api/v1/auth/logout` | 登录用户 | 退出登录 |

业务接口使用 `/api/v1/<module>/<resource>`。健康检查和 Knife4j 等内部接口不使用业务前缀。

## 4. 请求头

| 请求头 | 必填 | 说明 |
|---|---|---|
| `Authorization` | 登录后必填 | Sa-Token JWT，格式为 `Bearer <token>` |
| `X-Trace-Id` | 否 | 调用方可传；未传时由后端生成并写回响应头 |
| `X-Idempotency-Key` | 所有写接口必填 | 长度1到64；同一调用方、同一操作范围内重复请求返回同一业务结果 |

当前没有租户，不使用`X-Tenant-Id`。用户身份只从Sa-Token登录态读取，不接受前端传入用户ID作为权限依据。

Agent 内部接口还必须携带 `X-Internal-Service-Token` 校验服务身份。服务凭证不得放入查询参数、MQ 消息体或日志；内部调用继续透传 `X-Trace-Id`。

### 4.1 批次上传接口

~~~http
POST /api/v1/projects/{projectId}/file-ingest-batches/concurrent-uploads
Authorization: Bearer <token>
X-Trace-Id: <trace-id>
X-Idempotency-Key: <与 batch.idempotencyKey 一致>
Content-Type: multipart/form-data
~~~

接口使用 `multipart/form-data`：

| Part | 必填 | 说明 |
|---|---|---|
| `manifest` | 是 | 当前轮全局清单 JSON；同一轮所有顺序批次调用完全一致 |
| `batch` | 是 | 当前物理批次 JSON |
| `files` | 是 | 与 `batch.files` 顺序一致的文件二进制，数量为 1～50 |

manifest 字段：

~~~json
{
  "userId": 1,
  "projectId": 10,
  "requestId": "upload-request-uuid",
  "executionStatus": "initial",
  "attemptNo": 1,
  "originalTotalFiles": 120,
  "roundTotalFiles": 120,
  "totalBatchCount": 3,
  "batches": [
    {"batchId": "batch-1", "fileCount": 50},
    {"batchId": "batch-2", "fileCount": 50},
    {"batchId": "batch-3", "fileCount": 20}
  ]
}
~~~

batch 字段：

~~~json
{
  "userId": 1,
  "projectId": 10,
  "requestId": "upload-request-uuid",
  "attemptNo": 1,
  "batchId": "batch-1",
  "idempotencyKey": "batch-idempotency-uuid",
  "fileCount": 50,
  "files": [
    {
      "clientFileId": "client-file-uuid",
      "businessCode": "project",
      "relativePath": "backend/src/main/App.java",
      "fileName": "App.java",
      "sizeBytes": 1024,
      "sourceMtimeMs": 1784400000000
    }
  ]
}
~~~

`executionStatus` 只使用 `initial / retry`，`attemptNo` 只允许 1～3。重试轮复用首轮 `requestId`，但重新生成 `batchId` 和批次幂等键。`batch.idempotencyKey` 必须与请求头一致。

前端按“最多 50 个文件且原始文件总大小不超过 240 MB”分批；加入下一文件会突破任一阈值时先结束当前批次。普通源码项目通常优先达到 50 个文件上限。后端 Multipart 请求上限为 256 MB，240 MB 是为 JSON Part 和协议开销预留空间的前端阈值。

目标响应的 `data` 至少包含：

~~~json
{
  "uploadRequestId": 100,
  "requestId": "upload-request-uuid",
  "batchId": "batch-1",
  "attemptNo": 1,
  "batchStatus": "completed",
  "requestStatus": "uploading",
  "totalFiles": 120,
  "completedFiles": 48,
  "succeededFiles": 48,
  "batchSucceededFiles": 48,
  "batchFailedFiles": 2,
  "failedFiles": [
    {
      "clientFileId": "client-file-uuid",
      "relativePath": "backend/src/main/App.java",
      "fileName": "App.java",
      "sizeBytes": 1024,
      "sourceMtimeMs": 1784400000000,
      "errorCode": "50001",
      "errorMessage": "文件上传失败"
    }
  ],
  "requiresRetry": false,
  "requiresProjectUpdate": false
}
~~~

同一轮的各批次由前端逐批顺序调用：等待当前批次响应后再提交下一批，并持续聚合本轮失败结果。路径中的 `concurrent-uploads` 沿用固定接口名称；实际调用模型为前端顺序调用、后端仅在当前单批内部多线程上传文件。空目录和筛选后为空时不得调用该接口。前端传入的 `userId` 不能作为权限依据，后端必须使用登录态校验项目归属。

批次幂等规则：

- `completed` 批次原样重放时，后端校验文件身份、物理批次归属、元信息和内容哈希；全部一致才按 MySQL 事实返回，不重复 PUT；
- `processing` 未超时时返回批次处理中；超过默认 15 分钟后，只有相同幂等键可接管，本批已成功文件跳过 PUT；
- 同一批次使用不同幂等键或重放内容发生变化时，后端按资源冲突拒绝。

本轮批次全部 `completed` 后，后端还必须确认文件事实行总数等于 `originalTotalFiles`，且 `success + not_uploaded = originalTotalFiles`，才能进入请求状态判断和最终索引重建切入点。

### 4.2 Python 文件解析接口边界

已有内部读取地址与结果回调接口不属于当前批次上传闭环。当前最终完成服务不会通过 RabbitMQ 调用 Python；未来接入前需单独更新本文的消息和回调约束。

## 5. 统一响应

### 5.1 成功响应

```json
{
  "code": 0,
  "message": "成功",
  "data": {},
  "traceId": "abc123def456"
}
```

### 5.2 失败响应

```json
{
  "code": 20004,
  "message": "邮箱或密码错误",
  "data": null,
  "traceId": "abc123def456"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | number | 0 表示成功，非 0 表示错误 |
| `message` | string | 中文提示 |
| `data` | object / array / null | 业务数据 |
| `traceId` | string | 请求链路标识 |

## 7. traceId 与日志

### 7.1 traceId

1. `TraceInterceptor` 读取 `X-Trace-Id`；
2. 缺失时生成无连字符 UUID；
3. 写入 MDC 和响应头；
4. `R<T>` 从 `TraceContext` 读取同一 traceId；
5. 请求结束后清理 MDC。

### 7.2 MDC 字段

| 字段 | 说明 |
|---|---|
| `traceId` | 请求链路标识 |
| `userId` | 当前用户 ID，匿名请求为 `-` |
| `action` | HTTP 方法和请求路径 |
| `costMs` | 请求处理耗时 |

### 7.3 日志责任

- Controller：记录业务请求进入和成功完成；
- `GlobalExceptionHandler`：记录业务异常、参数异常和系统异常；
- `TraceInterceptor`：记录 HTTP 状态和耗时；
- Service：默认不重复记录 Controller 入口日志。

日志不得包含密码、密码哈希、JWT token 或完整请求体。

## 8. 权限

- 登录态使用 Sa-Token + JWT；
- 当前只区分匿名和已登录；
- 受保护接口使用 `@SaCheckLogin`；
- Controller 通过 `CurrentUserHolder` 获取当前用户 ID；
- 不实现 RBAC、租户隔离或手写 Service 鉴权。
- `system` 是内部命名空间，公开文件接口不允许上传、覆盖、读取、列出或删除系统文件。

## 10. 验收标准

- 所有接口返回统一响应；
- 响应头和响应体 traceId 一致；
- 未登录接口由 Sa-Token 统一拒绝；
- Controller 输出业务日志；
- 系统异常保留堆栈，业务异常只记录 WARN；
- 日志中不存在密码、哈希或 token。
