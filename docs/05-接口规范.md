# 接口规范

## 1. 通用约定

业务接口前缀为 `/api/v1`，JSON 字段使用小驼峰。统一响应：

```json
{
  "code": 200,
  "message": "成功",
  "data": {},
  "traceId": "01H..."
}
```

业务成功码为 `200`，与 HTTP 状态分开判断。除健康检查外，业务异常也使用该结构；当前业务 API 仅提供普通 JSON 响应。请求校验失败为 `10001`，未处理异常为 HTTP 500 与 `90001`。

用户 ID 和项目 ID 在 MySQL 与 Python 内部均为 64 位整数；所有 JSON 请求、响应、Agent 工具结果和项目上下文 JSON 统一使用十进制字符串，避免浏览器对大于 `2^53-1` 的整数产生精度损失。兼容迁移期间，后端入参也接受未加引号的正整数，出参始终序列化为字符串。

全系统以 `Asia/Shanghai` 为业务时区。所有 API 时间字段输出带 `+08:00` 的 RFC 3339 字符串；旧无偏移值仅由前端兼容层按上海时间解释，客户端不得自行补 `Z`。

## 2. 请求头

| 请求头 | 规则 |
|---|---|
| `Authorization` | 受保护接口必填，格式 `Bearer <JWT>` |
| `X-Trace-Id` | 可选；缺失时服务端生成，并通过响应体和响应头返回 |
| `X-Idempotency-Key` | 上传、内容覆盖、解析、持久化 Agent 运行等写操作必填，最长 128 字符；重复语义由各业务运行记录判断 |

JWT 包含 `sub`、`jti`、`iat`、`exp`。Redis 中不存在对应 `jti` 会话时视为未登录。

## 3. 认证与用户

| 方法 | 路径 | 请求 |
|---|---|---|
| `POST` | `/api/v1/auth/register` | `{username,email,password}` |
| `POST` | `/api/v1/auth/login` | `{email,password}` |
| `POST` | `/api/v1/auth/logout` | 无 |
| `GET` | `/api/v1/users/me` | 无 |
| `PUT` | `/api/v1/users/me` | `{username,email}` |
| `PUT` | `/api/v1/users/me/password` | `{oldPassword,newPassword,confirmPassword}` |

注册和登录继续使用 JSON，不使用 OAuth2 表单。登录使用邮箱；注册必填用户名、邮箱和密码，密码长度为 6～64 位。

## 4. 项目

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/projects` | 创建项目，请求 `{projectName}` |
| `GET` | `/api/v1/projects` | 当前用户项目列表 |
| `GET` | `/api/v1/projects/{projectId}` | 项目详情 |
| `DELETE` | `/api/v1/projects/{projectId}` | 惰性删除项目，三十天后允许定时物理清理 |

项目响应包含 `id`、`projectName`、`status`、`recordStatus`、`createdAt`、`updatedAt`。正常查询只返回 `recordStatus=enabled` 的记录；删除会改为 `disabled`，并在内部记录删除时间和三十天后的最早清理时间。已删除项目不参与名称判重，再次创建同名项目时返回新项目 ID；只有 `status=init_failed` 的启用项目会复用原 ID 重试初始化。保留期到期后，外部定时任务先清理 MinIO 项目前缀，确认清空后再物理删除数据库记录。

## 5. 项目文件

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/projects/{projectId}/files` | Multipart 单文件上传 |
| `PUT` | `/api/v1/projects/{projectId}/files/{fileId}/content` | Multipart 覆盖内容 |
| `PATCH` | `/api/v1/projects/{projectId}/files/{fileId}/path` | 修改逻辑路径 |
| `GET` | `/api/v1/projects/{projectId}/files` | 文件列表 |
| `GET` | `/api/v1/projects/{projectId}/files/{fileId}/read-url` | 五分钟只读地址 |
| `DELETE` | `/api/v1/projects/{projectId}/files/{fileId}?lockVersion=0` | 删除文件 |
| `POST` | `/api/v1/projects/{projectId}/files/sync/plan` | 根据完整目录清单生成同步计划，不直接修改文件 |
| `POST` | `/api/v1/projects/{projectId}/files/parse/init?force=false` | 必填 `X-Idempotency-Key`；分析待处理文件并刷新索引、项目规范，`force=true` 时重新分析全部有效文件 |
| `POST` | `/api/v1/projects/{projectId}/files/parse/recover` | 使用原 `X-Idempotency-Key` 查询结果不确定的解析运行，不重复调用模型 |

上传表单字段为 `relativePath`、`sourceMtimeMs`、`file`。覆盖表单字段为 `sourceMtimeMs`、`lockVersion`、`file`。

上传流程先提交 `uploading/not_uploaded` 记录，再在事务外写 MinIO，成功后条件更新为 `active/success`。MinIO 失败保留可诊断记录。

项目更新不新增批量写入接口。前端先提交完整目录清单，由后端从 MySQL 权威文件快照生成 `unchanged`、`modified`、`moved`、`added`、`deleted`、`rejected` 和 `ambiguous` 七类同步计划，再分别复用上传、覆盖、路径修改和删除接口。只有 `snapshotComplete=true` 时才生成删除项，远端删除仍必须由用户确认。完整 SHA-256 是内容一致性的最终依据；只有内容哈希唯一的一对一匹配才自动认定为移动，重复内容进入 `ambiguous`，不得任意配对。

同步规划请求示例：

```json
{
  "snapshotComplete": true,
  "scope": "project",
  "items": [
    {
      "relativePath": "docs/README.md",
      "sizeBytes": 1024,
      "sourceMtimeMs": 1760000000000,
      "contentHash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "contentType": "text/markdown"
    }
  ]
}
```

规划响应中的修改、移动和未变化项同时携带本地元数据、`remoteFileId`、`remoteRelativePath` 和 `lockVersion`；新增项只携带本地元数据；删除项携带远端文件身份与锁版本；歧义项按内容哈希返回本地和远端候选集合。文件未提供非空完整哈希时进入 `rejected`，不会被误判为新增或修改；若同路径已有远端文件，该路径仍视为已观察到，不会因此产生删除计划。规划接口只用于决策，上传和覆盖接口仍会根据实际字节重新计算内容哈希并执行后端校验。

前端先执行新增、覆盖和移动。完整快照中的重复内容歧义按“新增本地项 + 删除远端项”显式展示，删除仍需用户二次确认，因此不承诺保留原文件 ID；非完整快照不自动处理歧义。任一非删除操作失败或用户取消确认时跳过本批次删除，避免项目文件在部分成功时进一步丢失。`upload_failed` 和 `verify_required` 记录允许通过内容覆盖接口恢复；内容或路径变化后使旧分析失效，随后由解析入口重新分析。

解析入口成功响应的 `data` 为：

```json
{
  "status": "success",
  "candidateCount": 2,
  "successCount": 2,
  "failureCount": 0,
  "failures": [],
  "specificationStatus": "updated",
  "indexStatus": "updated"
}
```

`force` 默认为 `false`，此时只处理 `detail_ref` 为空且重试未耗尽的有效文件；`true` 时忽略已有详情和重试次数，显式重新分析全部有效文件。强制分析失败时保留原有有效详情和投影。`status` 为 `success` 或 `partial`；文件级失败、项目规范刷新失败或索引发布失败均返回 `partial`，并通过 `failures`、`specificationStatus` 和 `indexStatus` 暴露实际结果。

解析幂等键由前端在用户确认一次解析操作时生成，并在网络结果不确定或 `10003` 冲突后的同批恢复中复用。后端按用户、`parse` 操作和幂等键查询 `agent_run`：相同键与相同规范化请求直接复用已归档结果，运行中不再次执行；相同键对应不同 `force/fileIds` 返回 `10003`。同一项目同时只允许一个解析运行，不同幂等键并发提交也返回 `10003`；终态释放项目级租约，过期租约对应的旧运行保留为失败记录。普通解析不传 `fileIds`，后端在首次执行时查询一次候选列表并按该内存快照处理；定向重试对 `fileIds` 排序去重后参与请求指纹。

解析项目租约为 120 秒滑动租约，由独立数据库会话每 30 秒续租。成功、明确失败和请求取消均立即收尾并释放租约；进程异常中断时由恢复查询在租约过期后原子地把旧运行标为失败并释放 `active_scope_key`。写文件详情、项目规范、索引或数据库分析投影前必须再次确认运行仍有效，防止失效执行继续写入。

恢复响应示例：

```json
{
  "runId": "运行编号或 null",
  "status": "absent | running | success | failed",
  "retryable": true,
  "retryMode": "same_key | new_key | null",
  "leaseUntil": "2026-09-10T10:30:00+08:00",
  "result": null,
  "error": null
}
```

`running` 只允许继续恢复查询；`success` 直接展示归档结果；`failed` 解除界面锁定，由用户点击“立即重试”并生成新键；`absent` 才允许以原键重新发送原请求。已知失败不得自动启动第二次模型调用。

模型 HTTP `200` 不代表文件解析成功。输出被 token 上限截断、内容为空或不符合字段要求时，文件错误码为 `FILE_DETAIL_MODEL_OUTPUT_INVALID`，`errorMessage` 返回对应的中文原因；字段错误位置、类型、结束原因及输出用量通过同一 `traceId` 的后端日志定位，不向调用方返回模型原文或校验输入值。

`/api/v1/project-files/analyze` 已删除，不再存在 Java 到 Python 的内部分析接口。

## 6. Agent

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/agent/chat` | 普通 JSON 对话（兼容旧接口） |

Agent 接口需要 Bearer Token，请求体 `user.user_id` 必须与 JWT `sub` 一致。`trace_id` 用于本轮请求与 Agent 工具链路追踪，`context.project_id` 用于构造受信业务上下文；工具不能接收 JWT、数据库 Session 或由模型生成的用户 ID。

当前请求示例：

```json
{
  "trace_id": "01K1...",
  "conversation_id": 20,
  "messages": [
    {"role": "user", "content": "当前项目是什么？"}
  ],
  "context": {
    "project_id": "10",
    "iteration_id": 0,
    "context_total_usage": 0,
    "task_id": 0
  },
  "user": {
    "user_id": "1",
    "tenant_id": 0,
    "user_name": "测试用户"
  },
  "stream": false,
  "llm_provider": "deepseek"
}
```

客户端只能提交 `system`、`user`、`assistant` 普通消息。`assistant.tool_calls` 和 `tool` 消息由服务端 Agent 循环产生，客户端提交时返回参数校验错误，避免伪造工具结果。

非流式成功响应的 `data` 包含 `answer`、`model`、`conversation_id`、`tool_calls` 和 `usage`。`tool_calls` 只返回工具名、已校验入参、状态、安全摘要、错误标识和耗时，不返回完整业务出参。

当前 API 路由没有接通 SSE。内部流式方法和事件模型不代表公开接口可用；前端使用第 9 节的持久化普通 HTTP 会话接口。后续开放流式协议时需另行补齐接口、断线恢复和验收规范。

## 7. 主要错误码

| 范围 | 说明 |
|---|---|
| `10001` | 参数不合法 |
| `10002` | 缺少幂等键 |
| `10003` | 资源冲突或重复提交 |
| `20001` | 未登录 |
| `20002` | 无权限 |
| `20003`～`20009` | 用户、认证和系统文件访问错误 |
| `30001`～`30003` | 项目错误 |
| `30010`～`30017` | 文件业务错误 |
| `40001` | 模型提供方不支持当前工具调用模式 |
| `40002` | 模型请求了未注册工具 |
| `40003` | 工具参数不符合 JSON Schema |
| `40004`～`40005` | 工具执行失败或超时 |
| `40006` | Agent 工具调用超过步数或总次数限制 |
| `50001`～`50008` | 存储、索引、上传、解析、项目规范构建错误 |
| `90001` | 系统异常 |

## 8. 待确认问题

暂无。显式学习确认是受控的上下文文件更新流程，不等同于向模型开放任意写工具。

## 9. 持久化项目助手闭环

Chat 内部路由按 `conversation`、`learning`、`context`、`runs` 子包维护，由 `chat/api.py` 统一注册；旧无状态接口位于 `legacy/api.py`。报告请求与输出结构归 `report/schemas.py`，报告依赖装配归 `report/dependencies.py`。此目录调整不改变已有 URL、参数、响应和鉴权约定。

新接口统一使用 Bearer JWT 和 `X-Trace-Id`；发送消息、显式学习、生成报告必须传 `X-Idempotency-Key`。同一用户、操作和幂等键仅产生一次运行，重复键对应不同内容返回 `10003`。接口返回 HTTP 200 时仍需检查 `data.status`；运行失败会保存 `runId`、错误及轨迹，不能仅凭 HTTP 状态判断业务成功。

| 方法与路径 | 输入与含义 |
|---|---|
| POST `/api/v1/agent/conversations` | `projectId`、可选 `title`，创建项目会话 |
| GET `/api/v1/agent/conversations?projectId=...` | 查询当前用户项目的会话 |
| PATCH `/api/v1/agent/conversations/{id}` | 必填 `title`，修改当前用户拥有的会话名称，返回更新后的会话 |
| POST `/api/v1/agent/conversations/{id}/messages` | `content`，服务端加载历史，不要求任务或迭代 ID |
| GET `/api/v1/agent/conversations/{id}/messages` | 查询持久化普通消息 |
| POST `/api/v1/agent/conversations/{id}/learn` | 无请求体，增量提取待确认草稿；运行结果包含 draftId、draftVersion、candidateCount、processedMessages，不直接生效 |
| GET `/api/v1/agent/context-entries?projectId=...` | 从项目规范、长短期记忆和用户习惯固定文件汇总已学习内容；`effective=false` 可附带工作流中的待确认、失效及过期记录 |
| PATCH `/api/v1/agent/context-entries/{id}` | 必填 `projectId`、目标文件当前校验值、`reason` 及 X-Idempotency-Key；直接纠正对应固定文件，不调用模型 |
| POST `/api/v1/agent/context-entries/publish?projectId=...` | 待移除的旧兼容入口；目标设计不再发布快照或版本清单 |
| GET `/api/v1/agent/tools?conversationId=...` | 返回当前会话实际注册的工具定义 |
| GET `/api/v1/agent/runs/{runId}` | 查询本用户项目的模型和工具完整轨迹 |
| POST `/api/v1/projects/{projectId}/reports` | `kind=development` 或 `risk`，显式生成报告 |
| GET `/api/v1/projects/{projectId}/reports` | 可选 `kind`，查询已有报告 |
| GET `/api/v1/projects/{projectId}/reports/{reportId}` | 查询指定报告，返回包含该报告的数组；无记录时为空数组 |

创建会话时省略 `title` 或传 `null`，服务端按用户和项目自动分配 `项目对话-1`、`项目对话-2` 等名称。新编号取当前会话总数与现有标准名称最大编号的较大值加一，改名后已有会话仍参与计数。分配编号与创建在同一事务内完成，并锁定项目记录以串行化编号分配。显式传入或修改的 `title` 会去除首尾空白，长度必须为 1～128 个字符；空白名称不会自动命名。会话列表按创建 ID 倒序返回当前项目的全部会话，当前没有分页。

持久化消息视图增加可空 `requestKey`，对应创建该消息的运行幂等键。前端发送后可先显示本地消息，读取历史时按 `requestKey` 或运行结果中的消息 ID 替换本地消息，不按正文去重。消息和会话改名均校验当前用户及项目归属，不对其他用户开放。

文件列表新增 `analysisStatus`（`pending/success/failed/unavailable`）、`detailRef`、`lastErrorCode`、`lastErrorMessage`、`lastFailedAt`。`POST /files/parse/init?force=true` 可带 `{"fileIds":[1,2]}` 定向重试；不传请求体保持现有行为。解析入口必须携带 `X-Idempotency-Key`，解析响应增加 `runId`，可查询本批模型轨迹。

旧 `/api/v1/agent/chat` 保留兼容，但不负责持久化会话或显式学习。没有允许客户端任意执行指定工具的公开接口；模型工具只有读取权限。

召回工具的证据增加 `kind`（`source/summary/user_statement`）与 `truncated`。摘要不等于完整原文；只有实际读取的原文证据才能用于核实文档是否记载某内容。持久化会话会在既有配额内预读相关原文，精确补证仍可使用文件 ID 和行范围工具。


## 10. 显式学习与固定上下文文件

上下文正式正文只保存在当前项目 MinIO `system/` 下的固定文件中：`project_specification.json`、`short_term_memory.json`、`long_term_memory.json` 和 `user_habits/*.json`。显式学习负责生成、展示和确认候选；确认前不改变正式文件，确认后由后端条件覆盖对应原路径。草稿、反馈、选择和恢复状态属于工作流数据，不参与 Agent 召回。

以下接口统一携带 `projectId` 查询参数并校验项目所有权。雪花 ID 使用字符串。

| 方法与路径 | 请求及返回 |
|---|---|
| GET `/api/v1/agent/learning-drafts` | 可选 conversationId；返回该项目/会话的持久化草稿，刷新可恢复 |
| GET `/api/v1/agent/learning-drafts/{id}` | 返回具体版本、候选、原文、目标固定文件、冲突、反馈历史和各文件更新结果 |
| PATCH `/api/v1/agent/learning-drafts/{id}` | version、candidates、reason；人工结构化编辑，不调用模型，不生效 |
| POST `/api/v1/agent/learning-drafts/{id}/refine` | version、candidateIds、feedback，必填 X-Idempotency-Key；只整理选中候选，返回运行记录 |
| POST `/api/v1/agent/learning-drafts/{id}/confirm` | version、candidateIds；按所选候选生成固定文件更新计划，同一请求可恢复，无模型调用 |
| POST `/api/v1/agent/learning-drafts/{id}/rebase` | version；读取目标固定文件最新内容形成新预览，须再次确认；部分失败时只保留未成功目标 |
| GET `/api/v1/agent/context-entries/changes` | 可选 entryId；返回来源、人工纠正和固定文件更新历史 |

草稿候选为 `{id, proposal}`。proposal 至少包含 kind、targetFile、key、content、sourceMessageId、sourceQuote、replacesEntryId、invalidate、expiresAt、conditions、relatedEntryIds、coexistReason。targetFile 只能是当前项目的项目规范、长短期记忆或某个用户习惯分类文件，客户端不能提交任意对象键。模型 confirmed 字段保留输入兼容性，**不决定生效**。人工确认的同条件冲突仍会被拒绝；有不同条件的共存需用户明确关联和解释。

模型反馈整理可返回本轮局部 `coexistGroup`，服务端分配真实编号后转换为 `relatedEntryIds`，不把局部分组作为正式关系保存。同组必须包含同类型、同范围、同主题的至少两条候选，并分别说明适用条件和共存理由。确认时关联候选若用于替换，引用自动解析为原正式条目 ID；若关联尚未发布的新候选，必须一并选择或先编辑移除关联。

草稿 state：pending 待确认、updating 更新待恢复、partial 部分失败、applied 已写入、discarded 未采纳。refine 先持久化反馈，再调用模型，因此失败时草稿版本也可能增加；必须重新获取草稿。confirm 返回时仍须检查 state 和 targets，不能将 partial 当成成功。目标文件 ETag 或内容哈希冲突返回 10003，先 rebase 核对差异；已固定的更新计划不能用不同内容重试。直接纠正只有在目标固定文件条件写成功后才返回成功。

运行时已经切换为固定文件读写，`agent_learning_draft` 保存草稿工作流。旧 ContextStore、Manifest、版本对象及旧上下文数据库条目只作为一次性迁移来源保留；兼容 `/context-entries/publish` 仅返回固定文件当前状态，不再创建 Context 版本。迁移命令默认只生成核对报告，显式传入 `--apply` 才合并固定文件和迁移旧 MinIO 草稿。完整边界见 [云端上下文与显式学习改造](./27-云端上下文与显式学习改造.md)。
