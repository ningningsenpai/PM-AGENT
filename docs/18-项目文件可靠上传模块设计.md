# 项目文件批次上传模块设计

## 1. 文档定位

本文档是 PM-Agent 项目文件批次上传链路的唯一权威设计。

当本文档与历史代码、数据库迁移或其他文档冲突时，以本文档描述的当前用户确认方案为准。其他文档只能补充接口、数据模型、MinIO 或 Agent 细节，不得改变本文确定的职责、字段、状态和完成条件。

当前状态：**设计、接口合同、数据库迁移和前后端实现已同步**。

## 2. 核心目标

1. 前端负责空目录判断、文件筛选，并按“最多 50 个文件且原始文件总大小不超过 240 MB”的双阈值分批；普通源码项目通常优先达到 50 个文件上限。
2. 同一轮的各物理批次由前端逐批顺序调用，并持续聚合本轮结果。
3. 后端接收同一项目、同一请求下的多个批次，只在当前单批内部使用线程池并发上传文件。
4. MySQL 是项目、文件、上传请求、批次和索引状态的唯一准确数据源。
5. 文件首次落库时为 `not_uploaded`，存储字段为空。
6. MinIO 上传成功后才回填存储名、对象键和 MinIO 路径。
7. 单次后端调用只尝试上传一次；失败文件由前端收集并重新分批，最多三轮。
8. 后端通过本轮预注册批次总数与已完成批次数判断本轮结束。
9. 全部文件成功，或第三轮结束后，后端同步重建一次 `index.json`。
10. 当前链路不发布文件业务 MQ、不使用 Outbox、不调用 Python。

## 3. 职责划分

| 组件 | 当前职责 |
|---|---|
| 前端 | 判断文件夹是否为空；筛选目录、固定文件、后缀、大小和类型；按最多 50 个文件、单批原始文件总大小不超过 240 MB 分批；生成 manifest 和 batch；逐批顺序调用并聚合本轮结果；最多执行三轮；展示空项目 Mock、进度和最终提示 |
| Java 后端 | 校验登录用户与项目；校验 manifest、batch 和 multipart 一致性；预注册本轮全部批次；生成指纹和内容哈希；首次写入文件元数据；批次内多线程写 MinIO；成功后回填存储字段；返回失败文件；判断本轮与请求终态；同步重建 `index.json` |
| MySQL | 保存项目、逻辑文件、上传请求、预注册批次、上传状态和索引重建时间，是所有业务判断的唯一准确数据源 |
| MinIO | 保存初始索引、成功上传的源文件和可重建的 `system/index.json`；允许暂时存在未被 MySQL 引用的冗余对象 |
| RabbitMQ | 只保留基础连接配置，不参与当前文件上传和解析 |
| Python Agent | 当前链路不调用；未来只能从上传完成服务扩展 |

前端传入的 `userId` 只用于请求一致性校验。后端权限必须以登录态和 `pm_project.owner_user_id` 为准。

## 4. 项目创建前提

创建项目空间并成功上传初始化后的 `system/index.json`，是文件上传的前提。

~~~mermaid
flowchart TD
    A["前端创建项目"] --> B["Java 写 MySQL<br/>status = initializing"]
    B --> C["Java 构造空 index.json"]
    C --> D["同步 PUT MinIO<br/>system/index.json"]
    D --> E{"上传是否成功"}
    E -->|是| F["项目状态改为 active"]
    E -->|否| G["项目保持不可上传<br/>返回初始化失败"]
    F --> H["允许调用批次上传接口"]
~~~

批次上传必须校验项目为 `active`。初始化失败项目必须重新确认索引写入成功，不能只修改项目状态。

## 5. 固定接口合同

### 5.1 路径与请求头

~~~http
POST /api/v1/projects/{projectId}/file-ingest-batches/concurrent-uploads
Authorization: Bearer <token>
X-Trace-Id: <trace-id>
X-Idempotency-Key: <与 batch.idempotencyKey 一致>
Content-Type: multipart/form-data
~~~

### 5.2 Multipart 名称

| Part | 类型 | 说明 |
|---|---|---|
| `manifest` | JSON | 当前轮全局清单；同一轮所有顺序批次调用携带完全相同的内容 |
| `batch` | JSON | 当前物理批次信息 |
| `files` | File[] | 与 `batch.files` 顺序严格一致的文件二进制 |

名称固定为 `manifest`、`batch`、`files`，不得使用其他别名。

### 5.3 manifest

字段必须且只能按当前合同解释：

~~~json
{
  "userId": 1,
  "projectId": 10,
  "requestId": "upload-request-uuid",
  "executionStatus": "initial",
  "attemptNo": 1,
  "originalTotalFiles": 120,
  "roundTotalFiles": 120,
  "totalBatchCount": 3,
  "batches": [
    {"batchId": "batch-1", "fileCount": 50},
    {"batchId": "batch-2", "fileCount": 50},
    {"batchId": "batch-3", "fileCount": 20}
  ]
}
~~~

| 字段 | 规则 |
|---|---|
| `userId` | 必须与项目所有者一致 |
| `projectId` | 必须与路径参数一致 |
| `requestId` | 三轮复用同一个请求 ID |
| `executionStatus` | 第一轮为 `initial`，第二、三轮为 `retry` |
| `attemptNo` | 只允许 1、2、3，必须连续递增 |
| `originalTotalFiles` | 首轮筛选后的文件数，三轮保持不变 |
| `roundTotalFiles` | 当前轮实际上传文件数 |
| `totalBatchCount` | 当前轮预注册物理批次数 |
| `batches` | 当前轮全部批次摘要；数量必须等于 `totalBatchCount`，文件数合计必须等于 `roundTotalFiles` |

重试轮只包含上一轮失败文件，并重新生成所有 `batchId` 和幂等键。

### 5.4 batch

~~~json
{
  "userId": 1,
  "projectId": 10,
  "requestId": "upload-request-uuid",
  "attemptNo": 1,
  "batchId": "batch-1",
  "idempotencyKey": "batch-idempotency-uuid",
  "fileCount": 50,
  "files": [
    {
      "clientFileId": "client-file-uuid",
      "businessCode": "project",
      "relativePath": "backend/src/main/App.java",
      "fileName": "App.java",
      "sizeBytes": 1024,
      "sourceMtimeMs": 1784400000000
    }
  ]
}
~~~

| 字段 | 规则 |
|---|---|
| `userId / projectId / requestId / attemptNo` | 必须与 manifest 一致 |
| `batchId` | 必须存在于 `manifest.batches` |
| `idempotencyKey` | 必须与 `X-Idempotency-Key` 一致 |
| `fileCount` | 1～50，必须与 manifest 摘要、`batch.files` 和 multipart 文件数一致 |
| `files[].clientFileId` | 三轮保持稳定，用于定位同一 MySQL 文件行 |
| `files[].businessCode` | 当前前端使用 `project`；不得使用 `system` |
| `files[].relativePath` | 项目根目录内的规范化相对路径 |
| `files[].fileName` | 必须等于相对路径末段 |
| `files[].sizeBytes` | 必须与二进制文件大小一致 |
| `files[].sourceMtimeMs` | 源文件修改时间 |

### 5.5 响应

~~~json
{
  "uploadRequestId": 100,
  "requestId": "upload-request-uuid",
  "batchId": "batch-1",
  "attemptNo": 1,
  "batchStatus": "completed",
  "requestStatus": "uploading",
  "totalFiles": 120,
  "completedFiles": 48,
  "succeededFiles": 48,
  "batchSucceededFiles": 48,
  "batchFailedFiles": 2,
  "failedFiles": [
    {
      "clientFileId": "client-file-uuid",
      "relativePath": "backend/src/main/App.java",
      "fileName": "App.java",
      "sizeBytes": 1024,
      "sourceMtimeMs": 1784400000000,
      "errorCode": "50001",
      "errorMessage": "文件上传失败"
    }
  ],
  "requiresRetry": false,
  "requiresProjectUpdate": false
}
~~~

所有响应使用统一 `R<T>` 并包含 `traceId`。前端按批次顺序等待响应：非最后一个批次通常返回 `requestStatus = uploading`，最后一个批次完成后触发本轮结果判断；前端仍须聚合本轮所有响应中的 `failedFiles` 后再决定下一轮。

## 6. 前端流程

### 6.1 空目录与筛选

- 空文件夹：不调用后端任何上传接口，使用 Mock 空状态表示项目内容为空；
- 非空文件夹：排除忽略目录、固定文件、敏感文件、空文件、超大文件、不允许的后缀和类型；
- 筛选后为空：仍不调用上传接口；
- 后端保留路径穿越、文件大小、扩展名和请求归属等必要安全校验。

### 6.2 分批与顺序调用

- 单批文件数上限固定为 `batchSize = 50`；
- 单批原始文件总大小上限为 `240 MB`，为后端 `256 MB` Multipart 请求上限预留表单元数据和协议开销；
- 逐个加入筛选后的文件；加入下一个文件将使数量超过 50 或原始文件大小合计超过 240 MB 时，先结束当前批次；
- 普通源码文件通常较小，因此正常源码项目一般先达到 50 个文件上限；最后一批允许少于 50 个文件；
- 先构造完整 manifest，再构造其中每个 batch；
- 同一轮使用循环加 `await` 逐批顺序调用；
- 所有批次携带相同 manifest，各自携带不同 batch 和 files；
- 当前 HTTP 调用异常时，使用同一个 `batchId`、`idempotencyKey` 和完整请求原样补发两次；补发不增加 `attemptNo`；
- 两次补发后结果仍不确定则中断整个上传流程，不能把该批文件当成业务上传失败推进下一轮；
- 每批响应返回后先收集结果，本轮全部批次结束后统一聚合 `failedFiles`；
- 只有后端成功响应中的 `failedFiles` 才能进入下一轮；
- 失败文件按相同的“50 个文件、240 MB”双阈值重新分批，最多执行到 `attemptNo = 3`。

~~~mermaid
flowchart TD
    A["选择项目文件夹"] --> B{"是否为空"}
    B -->|是| C["不调用后端<br/>显示空项目 Mock"]
    B -->|否| D["前端筛选文件"]
    D --> E{"筛选后是否为空"}
    E -->|是| C
    E -->|否| F["按最多 50 个且不超过 240 MB 分批<br/>构造完整 manifest"]
    F --> G["逐批顺序调用<br/>每次 await 当前批次响应"]
    G --> H["持续收集批次结果<br/>本轮结束后聚合 failedFiles"]
    H --> I{"失败文件是否为空"}
    I -->|是| J["上传结束"]
    I -->|否且 attemptNo 小于 3| K["失败文件重新分批<br/>attemptNo + 1"]
    K --> G
    I -->|否且 attemptNo 等于 3| L["提示后续更新项目"]
~~~

## 7. 后端处理

### 7.1 请求与批次预注册

第一轮首个物理批次请求到达时：

1. 创建 `pm_project_file_upload_request`；
2. 根据 `manifest.batches` 一次预注册本轮全部物理批次；
3. 批次初始状态为 `waiting`；
4. 保存 manifest 摘要哈希，确保同一轮所有顺序批次请求使用相同清单。

后续批次请求按 `requestId + attemptNo + batchId` 获取已注册批次。前端批次顺序提交不改变后端的批次预注册和幂等判断：

- `waiting`：由当前请求抢占为 `processing`；
- `processing` 且未超时：返回“批次处理中”，不启动第二组上传线程；
- `processing` 已超过默认 15 分钟：只有相同幂等键才能接管，当前物理批次已经写入 MySQL 为 `success` 的文件直接计成功且不再 `PUT`，其余 `not_uploaded` 文件继续上传；
- `completed`：先校验本次文件身份、归属、元信息和内容哈希与原批次一致，再按 MySQL 事实重建响应，不重复上传；
- 同一 `batchId` 使用不同幂等键：按清单冲突拒绝。

批次首次从 `waiting` 进入 `processing` 时，同时保存稳定的 `payload_hash`。该摘要覆盖当前批次的文件 ID、业务类型、路径、文件名、大小、修改时间、快速指纹和内容哈希，用于 `processing` 接管与 `completed` 重放的完整载荷校验；它不写入文件行，因此上传失败时文件事实仍保持不变。

重试轮只允许在请求为 `awaiting_retry` 时开始。新 manifest 的 `roundTotalFiles` 必须等于 MySQL 中仍为 `not_uploaded` 的文件数。

### 7.2 首次文件落库

第一轮为每个文件生成：

- 标准化相对路径与 `path_hash`；
- 文件名、扩展名、大小和服务端 MIME；
- `source_mtime_ms`；
- `quick_fingerprint`；
- `content_hash`。

随后写入：

~~~text
status = uploading
upload_status = not_uploaded
storage_uuid = NULL
storage_name = NULL
object_key = NULL
minio_path = NULL
detail_ref = NULL
~~~

首次落库不写任何 MinIO 存储身份或位置。

同一 `clientFileId` 在首轮不得跨物理批次复用；否则后端按资源冲突拒绝，避免多个前端文件复用同一条 MySQL 事实记录。

### 7.3 重试复用

第二、三轮通过 `upload_request_id + client_file_id` 查找已有文件：

- 找不到时拒绝，防止重试产生第二条逻辑文件记录；
- 已经 `success` 的文件不得出现在新一轮重试清单中；若出现则按清单冲突拒绝，且绝不重复上传；
- `not_uploaded` 文件进入当前轮；
- 不新建文件行。

### 7.4 当前批次多线程上传

正常批次执行中，每个文件只提交一次 MinIO `PUT`：

1. 在线程任务内生成临时 `storage_uuid`、`storage_name`、`object_key` 和 `minio_path`；
2. 调用 MinIO 上传；
3. 成功后回填存储字段并设置 `upload_status = success`；
4. 失败时不更新文件行，只生成当前响应的失败文件信息；
5. 等待当前批次所有线程结束；
6. 将批次状态改为 `completed` 并写入成功、失败计数。

允许出现 MinIO 已写入但 MySQL 更新失败形成的冗余对象。后续清理以 MySQL 有效对象键为准，不在上传热路径增加复杂补偿。

超时接管是唯一例外：MySQL 已为 `success` 的文件绝不重复 PUT；仍为 `not_uploaded` 的文件可由接管线程再次 PUT，因此允许 MinIO 产生冗余对象，最终仍以 MySQL 为准。

~~~mermaid
flowchart TD
    A["接收 manifest、batch、files"] --> B["校验用户、项目和合同一致性"]
    B --> C["获取上传请求<br/>校验 manifest 哈希"]
    C --> D{"预注册批次状态"}
    D -->|waiting| D1["抢占批次<br/>waiting → processing"]
    D -->|processing 未超时| D2["返回批次处理中"]
    D -->|processing 超过 15 分钟<br/>且幂等键相同| D3["接管批次<br/>复用本批已成功文件"]
    D -->|completed| D4["校验重放内容一致<br/>按 MySQL 重建响应且不 PUT"]
    D1 --> E{"attemptNo"}
    D3 --> E
    E -->|1| F["生成元数据<br/>插入 not_uploaded 文件行"]
    E -->|2 或 3| G["按 clientFileId 查已有文件行"]
    F --> H["提交批次线程池"]
    G --> H
    H --> I["每文件单次 PUT MinIO"]
    I --> J{"上传与数据库回填是否成功"}
    J -->|是| K["upload_status = success"]
    J -->|否| L["文件行保持 not_uploaded<br/>生成失败结果"]
    K --> M["等待当前批次全部线程"]
    L --> M
    M --> N["批次 processing → completed"]
    N --> O["查询本轮预注册与已完成批次数"]
~~~

## 8. 数据模型

### 8.1 `pm_project_file_upload_request`

| 字段 | 说明 |
|---|---|
| `owner_user_id` | 项目所有者 |
| `project_id` | 项目 ID |
| `request_id` | 前端稳定请求 ID |
| `original_total_files` | 首轮文件总数 |
| `current_attempt` | 当前轮次，对应合同 `attemptNo` |
| `round_total_files` | 当前轮文件数 |
| `round_total_batches` | 当前轮预注册批次数，对应 `totalBatchCount` |
| `round_manifest_hash` | 当前轮 manifest 摘要哈希 |
| `status` | 请求状态 |
| `succeeded_files` | 当前请求已成功文件数 |
| `failed_files` | 终态失败文件数 |
| `index_rebuilt_at` | 终态后同步重建索引成功时间 |
| `completed_at` | 请求进入终态时间 |

该表不保存“已完成批次数”。本轮完成情况通过物理批次表实时统计。

### 8.2 `pm_project_file_ingest_batch`

| 字段 | 说明 |
|---|---|
| `upload_request_id` | 上传请求主键 |
| `attempt_no` | 所属轮次 |
| `client_batch_id` | 前端 `batchId` |
| `idempotency_key` | 批次幂等键 |
| `payload_hash` | 首次提交时生成的批次完整载荷摘要，用于接管和重放校验 |
| `total_files` | 批次文件数，1～50 |
| `completed_files` | 当前批次处理完成数 |
| `succeeded_files` | 当前批次成功数 |
| `failed_files` | 当前批次失败数 |
| `status` | `waiting / processing / completed` |

唯一约束：

~~~text
UNIQUE(upload_request_id, attempt_no, client_batch_id)
~~~

### 8.3 `pm_project_file`

- 增加 `upload_request_id` 和 `client_file_id`；
- 增加 `last_upload_attempt` 和 `last_upload_batch_id`；
- `storage_uuid`、`storage_name`、`object_key`、`minio_path`、`detail_ref` 允许为空；
- 新流程使用 `upload_status = not_uploaded / success`；
- `UNIQUE(upload_request_id, client_file_id)` 保证三轮只使用一条文件记录。

## 9. 完成闸门

### 9.1 本轮完成

每个批次变为 `completed` 后，后端查询：

~~~text
registeredBatches =
  当前 upload_request_id + attempt_no 下的全部预注册批次数

completedBatches =
  当前 upload_request_id + attempt_no 下 status = completed 的批次数
~~~

只有同时满足：

~~~text
registeredBatches = round_total_batches
completedBatches = round_total_batches
~~~

才进入本轮结果判断。重复批次不会增加额外记录，也不会误触发完成。

### 9.2 请求终态

本轮全部批次完成后，从 MySQL 查询：

- 当前请求的文件事实行总数；
- `upload_status = success` 的文件数；
- `upload_status = not_uploaded` 的文件数。

进入状态判断前必须同时满足：

~~~text
文件事实行总数 = original_total_files
success 文件数 + not_uploaded 文件数 = original_total_files
~~~

任一条件不满足都按数据冲突拒绝进入终态；不能仅凭批次计数推断整个项目请求已经处理完整。

处理规则：

| 条件 | 请求状态 | 后续 |
|---|---|---|
| `not_uploaded = 0` | `completed` | 同步重建索引 |
| `not_uploaded > 0` 且 `attemptNo < 3` | `awaiting_retry` | 等待前端下一轮 |
| `not_uploaded > 0` 且 `attemptNo = 3` | `completed_with_failures` | 同步重建索引 |

### 9.3 索引重建

请求进入 `completed` 或 `completed_with_failures` 后，当前调用同步执行 `ProjectIndexService.rebuild()`。

- 成功：写入 `index_rebuilt_at`；
- 失败：当前接口返回失败，请求仍保持既有终态，`index_rebuilt_at` 为空；
- 恢复判断：`status` 为终态且 `index_rebuilt_at IS NULL`；
- 后续“更新项目”操作可重新执行索引重建；
- 不增加额外请求状态。

~~~mermaid
flowchart TD
    A["批次变为 completed"] --> B["查询本轮预注册批次数"]
    B --> C["查询本轮 completed 批次数"]
    C --> D{"两者是否都等于 round_total_batches"}
    D -->|否| E["请求保持 uploading"]
    D -->|是| F["查询 MySQL 文件事实总数、success 与 not_uploaded"]
    F --> F1{"事实总数等于 original_total_files<br/>且 success + not_uploaded 等于 original_total_files"}
    F1 -->|否| F2["按数据冲突拒绝<br/>不得进入终态"]
    F1 -->|是| G{"not_uploaded 是否为 0"}
    G -->|是| H["请求状态 completed"]
    G -->|否且 attemptNo 小于 3| I["请求状态 awaiting_retry"]
    G -->|否且 attemptNo 等于 3| J["请求状态 completed_with_failures"]
    I --> K["等待下一轮顺序批次调用"]
    H --> L["同步 rebuild index.json"]
    J --> L
    L --> M{"重建是否成功"}
    M -->|是| N["写 index_rebuilt_at<br/>接口成功返回"]
    M -->|否| O["index_rebuilt_at 保持 NULL<br/>接口失败并等待恢复"]
~~~

## 10. 状态机

### 10.1 上传请求

只使用四种状态：

~~~mermaid
stateDiagram-v2
    [*] --> uploading: 第一轮请求建立
    uploading --> awaiting_retry: 本轮完成且仍有失败，attemptNo 小于 3
    awaiting_retry --> uploading: 下一轮 manifest 通过校验
    uploading --> completed: 全部文件成功
    uploading --> completed_with_failures: 第三轮仍有失败
    completed --> [*]
    completed_with_failures --> [*]
~~~

### 10.2 物理批次

~~~mermaid
stateDiagram-v2
    [*] --> waiting: manifest 预注册
    waiting --> processing: 当前批次请求抢占
    processing --> processing: 超过 15 分钟且幂等键相同后接管
    processing --> completed: 当前批次线程全部结束
    completed --> completed: 完整内容校验通过的幂等重放
~~~

### 10.3 文件

~~~mermaid
stateDiagram-v2
    [*] --> not_uploaded: 第一轮元数据落库
    not_uploaded --> success: MinIO 与 MySQL 回填成功
    not_uploaded --> not_uploaded: 当前轮失败
    success --> success: 重复请求
~~~

## 11. `index.json`

固定对象键：

~~~text
PM-AGENT/{ownerUserId}/{projectId}/system/index.json
~~~

最终重建只查询 MySQL：

- `success` 文件进入 `project` 或 `user`；
- 终态仍为 `not_uploaded` 的文件进入 `upload_failures`；
- 不读取旧索引做增量合并；
- 不通过 MinIO `list/stat` 推断业务状态；
- 在内存中生成完整 JSON 后整体覆盖固定对象键。

上传中和 `awaiting_retry` 状态不得重建索引。

## 12. MQ 与 Python 边界

当前版本：

- RabbitMQ 只保留基础连接配置；
- 不发布上传完成或文件解析消息；
- 不创建文件业务交换机、队列或消费者；
- 不写 Transactional Outbox；
- 不调用 Python 文件解析。

`ProjectFileUploadCompletionService` 是未来扩展点。后续接入 Python 前必须单独评审消息协议、幂等、重试和死信处理。

## 13. 异常与恢复

| 场景 | 处理 |
|---|---|
| 空目录或筛选后为空 | 前端显示空项目 Mock，不调用上传接口 |
| manifest 在同一轮不一致 | 后端通过摘要哈希拒绝 |
| 批次不在 manifest 中 | 后端拒绝 |
| 批次超过 50 个文件 | 后端拒绝 |
| 单批原始文件总大小将超过 240 MB | 前端提前结束当前批次；后端仍以 256 MB 请求上限兜底 |
| 已完成批次原样重放 | 校验文件归属、元信息和内容哈希后返回 MySQL 已有结果，不重复上传或统计 |
| 已完成批次重放内容变化 | 按资源冲突拒绝 |
| `processing` 批次未超时 | 返回批次处理中，不重复启动线程 |
| `processing` 批次超过 15 分钟 | 仅相同幂等键可接管；本批已成功文件跳过 PUT，`not_uploaded` 文件继续上传 |
| 同一批次使用不同幂等键 | 按资源冲突拒绝 |
| 批次 HTTP 响应异常 | 使用同一批次和幂等键原样补发两次；仍失败则中断，不消耗业务上传轮次。当前 MVP 不跨页面持久化 `File` 对象和上传会话，页面关闭后的恢复交给后续“更新项目”能力 |
| 当前文件上传失败 | 文件保持 `not_uploaded`，返回 `failedFiles` |
| 前两轮仍有失败 | 请求进入 `awaiting_retry` |
| 第三轮仍有失败 | 请求进入 `completed_with_failures`，并同步重建索引 |
| MinIO 成功但 MySQL 更新失败 | 允许冗余对象，文件仍为 `not_uploaded` |
| 索引同步重建失败 | 当前接口失败；请求终态不变且 `index_rebuilt_at` 为空 |
| 第四轮请求 | 后端拒绝 |

## 14. 验收标准

1. 空文件夹不产生上传请求。
2. manifest 和 batch 字段、Multipart 名称及接口路径与本文完全一致。
3. 51 个普通小文件拆成 50 和 1 两批，并由前端逐批顺序发送。
4. 加入下一文件会使单批原始文件总大小超过 240 MB 时，提前开始新批次，最终请求不超过后端 256 MB 上限。
5. 第一轮首个请求预注册 manifest 中全部批次，初始状态为 `waiting`。
6. 首次文件落库为 `not_uploaded`，所有存储字段为空。
7. 第二、三轮复用原文件行。
8. 正常批次执行中每文件只提交一次 MinIO 上传；超时接管仅允许重新处理 MySQL 仍为 `not_uploaded` 的文件，已成功文件不得重复 PUT。
9. 上传失败不修改文件行。
10. 首轮同一 `clientFileId` 跨物理批次复用时必须拒绝。
11. 本轮完成先查询预注册与已完成批次统计，再校验文件事实总数和状态分布完整性。
12. 相同幂等键可在 `processing` 超过默认 15 分钟后接管，且本批已成功文件不得重复 PUT。
13. 已完成批次只有在完整文件内容校验一致后才能重放已有结果。
14. 请求状态只使用 `uploading / awaiting_retry / completed / completed_with_failures`。
15. 索引成功以 `index_rebuilt_at` 非空为准。
16. 索引失败时接口失败，不新增请求状态。
17. 当前链路不发布文件业务 MQ、不写 Outbox、不调用 Python。
