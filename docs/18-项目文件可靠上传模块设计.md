# 项目文件可靠上传模块设计

## 1. 权威流程

单文件上传遵循：

1. 校验登录用户与项目归属；
2. 校验逻辑路径、扩展名、大小、MIME、哈希与幂等键；
3. 提交 `uploading / not_uploaded` 数据库记录；
4. 在事务外写 MinIO；
5. 成功后更新为 `active / success`；
6. 失败时保留记录与诊断信息。

不使用数据库与 MinIO 的伪分布式事务，也不双写 Java/Python。

## 2. 路径与内容

- 前端只提交项目内相对路径，不提交本机绝对路径和对象键。
- Python 统一执行 NFC 规范化、目录忽略与扩展名拦截。
- 内容哈希为 SHA-256。
- 快速指纹由规范化路径、大小和源修改时间计算。
- 单文件默认最大 50 MiB。
- `system` 命名空间不通过公开文件接口访问。

## 3. 幂等与并发

- 上传和内容覆盖必须携带 `X-Idempotency-Key`。
- Redis 使用 `SET NX EX 120` 阻止两分钟内重复提交。
- 路径唯一约束防止并发重复上传。
- 更新、移动和删除使用 `lockVersion` 做乐观锁校验。

## 4. 外部调用

MinIO PUT、COPY、DELETE、GET 和模型调用均位于数据库事务外。状态机负责表达中间态和失败恢复：

```text
uploading → active
active → updating → active
updating → verify_required / upload_failed
upload_failed / verify_required → updating → active
active → deleting → 删除记录
upload_failed / verify_required / delete_failed → deleting → 删除记录
deleting → delete_failed
```

## 5. 项目更新

项目更新采用后端同步规划与现有单文件接口组合，不增加新的批量写入接口：

1. 前端校验本地目录、计算文件 SHA-256，并提交带 `snapshotComplete` 的完整清单；
2. 后端从 MySQL 文件快照生成未变化、修改、唯一移动、新增、删除、拒绝和歧义计划；
3. 内容 SHA-256 是最终判定依据，快速指纹只用于预筛；只有唯一的一对一哈希匹配才认定为移动；完整快照中的重复内容歧义经用户确认后按新增和删除处理；
4. 前端先调用上传、内容覆盖和路径修改接口；任一非删除动作失败时跳过本批次删除；
5. 删除项经人工确认后再调用单文件删除接口；
6. 调用解析入口重建失效的分析投影、项目规范和索引。

仅源修改时间变化且内容哈希不变时，覆盖接口更新文件元数据并保留原分析结果。内容或路径变化时清空数据库分析投影并按 `file_id` 移除五个规范分区中的旧规则组，避免索引和规则继续暴露旧详情。删除文件时执行相同的规则组清理。

## 6. 解析入口

文件队列处理后，前端调用：

```text
POST /api/v1/projects/{projectId}/files/parse/init
```

该入口直接调用 Python `ProjectFileAnalysisService`，不再请求 `/api/v1/project-files/analyze`。每个文件先生成详情并按内容哈希条件回填数据库；批次结束后，`ProjectSpecificationService` 只用本轮成功详情按 `file_id` 覆盖五个规则分区，长期记忆继续从 `project_facts` 增量对账，最后从数据库完整生成 `system/index.json`。接口返回文件级失败、规范状态、记忆状态和索引状态，部分失败不得报告为整批成功。
