# 07 成本控制

本文档定义 PM-Agent 智能项目管理 Agent 平台的运行成本控制策略，重点覆盖 LLM 调用、模型路由、Prompt 缓存、Agent Trace 存储、中间件与部署成本。

---

## 1. 背景

PM-Agent 采用 Java + Python + LLM Agent 架构。Agent 能力会带来明显运行成本，尤其是模型调用、Trace 存储、文档切片和向量检索。项目当前以单人 + AI 开发为主，运行时成本必须可控。

---

## 2. 成本目标

| 项 | 目标 |
|---|---|
| 月度运行时 LLM 成本 | 约 600 元人民币以内 |
| 开发期工具成本 | 项目开发完成前暂不与运行成本拆分 |
| 默认模型 | DeepSeek 优先 |
| 高成本模型 | 仅用于复杂推理、关键决策、最终润色 |
| 本地模型 | 后续扩展，暂不纳入当前开发阶段 |

---

## 3. 成本来源

| 成本来源 | 阶段 | 控制重点 |
|---|---|---|
| LLM API 调用 | 第 3 阶段起 | 模型选择、Prompt 长度、调用频次 |
| Agent Trace 存储 | 第 3 阶段起 | 保留期、截断、脱敏 |
| Redis | 第 2 阶段 | 会话、缓存、幂等键 TTL |
| RabbitMQ | 第 5 阶段 | 异步任务数量、失败重试 |
| MinIO | 第 6 阶段 | 文档、附件、大 Trace 输出 |
| 向量库 | 第 6 阶段 | 文档切片数量、向量维度、重建频率 |
| 云服务器 | 后期部署 | 服务数量、中间件数量、监控组件 |

---

## 4. 模型分层策略

| 场景 | 默认模型 | 升级条件 |
|---|---|---|
| 意图识别 | DeepSeek | 识别不稳定、多轮上下文复杂 |
| 项目问答 | DeepSeek | 涉及复杂推理或关键判断 |
| 需求拆解 | DeepSeek 起草 | 拆解质量不达标时升级 Claude / GPT |
| 周报生成 | DeepSeek 草稿 | 最终润色可升级更强模型 |
| 风险分析 | DeepSeek / Claude | 关键风险判断可升级 |
| RAG 问答 | 第 6 阶段再细化 | 取决于召回质量、上下文长度和引用要求 |

原则：

1. 默认模型不等于最强模型；
2. 低成本模型先起草，高成本模型只在高价值环节补强；
3. 模型升级必须可解释：为什么升级、提升什么、增加多少成本；
4. 若月成本接近 600 元，优先限流、缓存、缩短上下文，而不是直接关闭核心能力。

---

## 5. 模型适配层成本策略

第一版采用 **DeepSeek 优先 + 自研轻量 `ModelClient` 适配层**。

适配层只做必要抽象：

- 统一请求参数；
- 统一响应结构；
- 统一流式事件；
- 统一错误结构；
- 统一 token / 耗时 / 成本统计；
- 统一 Trace 接入。

不在第一版强制兼容 OpenAI-compatible 协议，也不提前接入多个供应商。后续接入 Claude / GPT / Gemini 时再扩展 Provider。

---

## 6. Prompt 与上下文控制

### 6.1 Prompt 控制原则

1. Prompt 模板编号管理，避免重复拼接大段固定说明；
2. 项目上下文只传当前任务需要的信息，不传全量项目数据；
3. 工具返回结果由 Agent 总结时优先传摘要；
4. 长列表只传 Top N 与统计信息，必要时让 Agent 追问；
5. RAG 阶段回答必须带引用，但不把所有召回片段塞进上下文。

### 6.2 上下文窗口策略

| 场景 | 策略 |
|---|---|
| 普通项目问答 | 最近会话 + 当前项目摘要 |
| 任务查询 | 让工具按条件返回结果，不把全量任务放入 Prompt |
| 周报生成 | 按时间范围聚合任务、风险、变更 |
| 风险分析 | 规则结果 + 关键证据 + 任务摘要 |
| RAG | Top K 文档片段 + 引用来源 |

---

## 7. 缓存策略

优先缓存可复用、非强实时结果。

| 场景 | 缓存策略 |
|---|---|
| 周报草稿 | 按项目 + 时间范围 + 输入摘要缓存 |
| 风险分析结果 | 按项目 + 数据版本缓存 |
| 文档切片摘要 | 第 6 阶段缓存 |
| Prompt 模板 | 本地配置缓存 |
| 字典 / 术语表 | 前后端均可缓存 |
| 项目概览 | 可短 TTL 缓存 |

禁止缓存：

- 权限敏感结果；
- 未脱敏隐私数据；
- 高风险动作确认结果；
- 用户明确要求重新生成的 Agent 输出。

---

## 8. Agent Trace 成本控制

### 8.1 保留策略

- Agent Trace 默认保留 3 个月；
- 暂不归档；
- 开发和调优阶段保留完整 Prompt、模型输出、工具调用结果；
- 超大字段允许截断并记录 `truncated=true`；
- 第 6 阶段引入 MinIO 后，可将超大原文外挂存储。

### 8.2 脱敏规则

入库前必须脱敏：

- 手机号；
- 邮箱；
- token；
- 密码；
- 可能涉及隐私或敏感业务字段。

### 8.3 存储成本估算方式

估算 Agent Trace 成本时，至少考虑：

```text
日均会话数 × 每会话平均工具调用数 × 单条 Trace 平均大小 × 90 天
```

如果单条工具输出超过阈值，应评估截断或外挂存储。

---

## 9. 中间件成本控制

| 中间件 | 控制策略 |
|---|---|
| MySQL | 第 1 阶段只用 MySQL；慢查询出现后再加索引，不提前复杂化 |
| Redis | 第 2 阶段引入，先用于会话、幂等和少量缓存 |
| RabbitMQ | 第 5 阶段引入，只承接风险扫描、周报生成、文档处理等异步任务 |
| MinIO | 第 6 阶段引入，不提前做附件和文档存储平台 |
| 向量库 | 第 6 阶段引入，优先 pgvector 或 Qdrant 二选一 |
| 监控 | 后期按需引入 Prometheus + Grafana，早期先靠应用日志 |

---

## 10. 降级策略

当成本接近预算上限时，按以下顺序降级：

1. 缩短 Prompt 上下文；
2. 降低自动分析频率；
3. 增加缓存命中；
4. 高成本模型改为仅手动触发；
5. 批量任务改为排队执行；
6. 暂停非核心 Agent 能力；
7. 最后才降低关键业务决策质量。

---

## 12. 验收标准

- 第 3 阶段 Agent 上线时，能记录每次模型调用的 token、耗时、模型名、traceId；
- 第 4 阶段工具调用上线时，能估算单次问答平均成本；
- 第 5 阶段异步风险扫描上线时，能控制扫描频率和并发；
- 第 6 阶段 RAG 上线前，必须重新评估向量库和 MinIO 成本；
- 任一 Agent 能力若可能突破月 600 元预算，必须给出降级策略。
