# 02 技术选型

本文档说明 PM-Agent 智能项目管理 Agent 平台的技术选型与取舍理由。所有选型均以 **单人 + AI 开发**、**月预算 200–600 元** 为前提。

---

## 一、整体架构

```text
┌──────────────────────────┐
│   Vue 3 + TypeScript     │  前端：Naive UI、Pinia、ECharts
└──────────────┬───────────┘
               │ HTTP/JSON
┌──────────────▼───────────┐
│   Java Spring Boot 3     │  业务主系统：Sa-Token、MyBatis Plus、Knife4j
└──────────────┬───────────┘
               │ HTTP/JSON（同步） + RabbitMQ（异步）
┌──────────────▼───────────┐
│   Python FastAPI          │  Agent 智能服务：Prompt、工具调用、RAG
└──────────────┬───────────┘
               │
┌──────────────▼───────────┐
│  LLM API / 向量库 / 文件库 │  DeepSeek / Claude / GPT、Qdrant、MinIO
└──────────────────────────┘
```

## 二、前端

### 2.1 选型

| 类别 | 选型 |
|---|---|
| 框架 | Vue 3 |
| 语言 | TypeScript |
| 构建 | Vite |
| Node.js | Node 20 LTS |
| 包管理器 | pnpm |
| 组件库 | Naive UI |
| 状态管理 | Pinia |
| 路由 | Vue Router |
| 图表 | ECharts |
| HTTP | Axios |
| 样式增强 | UnoCSS（可选） |

### 2.2 选择理由

- **Vue 3 vs React**：Vue 3 单文件组件结构清晰，单人开发可读性更好，Naive UI 等组件生态成熟。React 更灵活，但对单人项目而言额外维护成本不划算。
- **Naive UI vs Element Plus**：Naive UI 视觉更现代、组件 API 更友好、TypeScript 支持更完整；Element Plus 偏传统后台风格，视觉相对死板。
- **Pinia vs Vuex**：Pinia 是 Vue 官方推荐的新一代方案，类型推导更友好，代码更轻量。
- **Vite vs Webpack**：Vite 启动快、热更新体验好，已经是 Vue 3 项目默认选择。

### 2.3 不选用

- React + Ant Design：备选方案，未来如做协作型富交互界面再考虑。
- Vuetify、PrimeVue：风格不够贴合国内后台审美。
- Element Plus：视觉风格不符合本项目偏好。

## 三、Java 后端

### 3.1 选型

| 类别 | 选型 |
|---|---|
| 框架 | Spring Boot 3 |
| 构建工具 | Maven |
| 认证授权 | Sa-Token |
| ORM | MyBatis Plus |
| 数据库迁移 | Flyway |
| 校验 | Jakarta Validation |
| 文件类型识别 | Apache Tika Core |
| API 文档 | Knife4j |
| 工具 | Hutool、MapStruct |

### 3.2 选择理由

- **Sa-Token vs Spring Security**：Sa-Token 上手快、代码量少、权限注解直观，单人项目更高效；Spring Security 适合企业 OAuth2/SSO，本项目第一版用不到。
- **MyBatis Plus vs JPA**：MyBatis Plus 控制力强，SQL 可直接调优，适合需要后续做风险扫描和复杂查询的项目。
- **Knife4j vs Swagger UI**：Knife4j 中文友好、调试体验好，是国内 Spring Boot 项目主流。
- **Apache Tika Core**：根据文件内容识别MIME类型，不信任浏览器声明值；只引入核心探测能力，不加载完整文档解析器。
- **不裸用 JWT**：JWT 只是 Token 格式，裸用需要自己实现一整套登录、刷新、踢人、黑名单逻辑，单人项目不划算。

### 3.3 包结构

```text
com.ning.pm
├── common         通用响应、异常、工具
├── config         配置类
├── infrastructure 缓存、消息、外部服务、Agent 客户端
├── modules
│   ├── auth
│   ├── user
│   ├── project
│   ├── requirement
│   ├── task
│   ├── iteration
│   ├── risk
│   ├── report
│   └── agent
└── PmApplication.java
```

## 四、Python Agent 服务

### 4.1 选型

| 类别 | 选型 |
|---|---|
| 框架 | FastAPI |
| 数据校验 | Pydantic v2 |
| 异步任务 | Celery（第 5 阶段引入） |
| Agent 编排 | 自研轻量编排，必要时引入 LangChain / LlamaIndex |
| 向量库 | Qdrant 或 pgvector |
| 模型 SDK | DeepSeek 优先 + 自研轻量模型适配层 |

### 4.2 选择理由

- **FastAPI**：异步友好，Pydantic 模型校验天然适合结构化输出。
- **不上来就用 LangChain**：LangChain 抽象多、学习成本高，第一版自研更可控，后期再决定是否引入。
- **Qdrant vs pgvector**：单人项目优先 pgvector（一个数据库搞定），未来扩展再迁移到 Qdrant。
- **模型调用策略**：第一版优先接入 DeepSeek，通过自研轻量 `ModelClient` 适配层统一请求、响应、流式事件、错误和成本统计；后续接入 Claude / GPT / Gemini 时再扩展具体 Provider。

### 4.3 模块结构

```text
agent-service/
├── app/
│   ├── api/              FastAPI 路由
│   ├── core/             配置、日志、模型路由
│   ├── agents/           Agent 编排
│   ├── prompts/          Prompt 模板
│   ├── tools/            工具调用实现（调用 Java 业务 API）
│   ├── rag/              RAG 检索（第 6 阶段引入）
│   ├── schemas/          Pydantic 模型
│   └── main.py
└── pyproject.toml
```

## 五、数据库

### 5.1 主数据库：MySQL 8

- 单人项目选 MySQL 更稳妥；
- 工具链成熟；
- 后期如需向量检索可引入 pgvector 时再考虑切换到 PostgreSQL。

### 5.2 缓存：Redis 7

- Sa-Token 会话；
- 接口限流；
- 项目概览缓存；
- 高频查询缓存。

### 5.3 向量库：Qdrant 或 pgvector

- 第 6 阶段 RAG 可优先评估 pgvector；
- 文档量增长后再考虑 Qdrant；
- 不在第 1–5 阶段引入。

### 5.4 文件存储：MinIO

- 文档、附件、报告；
- 仅在第 6 阶段引入；
- 本地开发使用 Docker Compose 启动。

## 六、中间件

| 中间件 | 引入阶段 | 用途 | 替代方案 |
|---|---|---|---|
| MySQL | 第 1 阶段 | 业务存储 | PostgreSQL |
| Redis | 第 2 阶段 | 缓存、会话 | 无 |
| RabbitMQ | 基础配置已加入；第 5 阶段接入业务 | 后续承载异步任务、通知和文件重试 | Spring 内置异步（弱场景） |
| MinIO | 文件可靠上传专项提前启用；第 6 阶段扩展 | 项目文件对象存储，后续承载文档与报告 | 本地文件系统 |
| Qdrant/pgvector | 第 6 阶段 | 向量检索 | 无 |
| Elasticsearch | 可选 | 全文检索 | MySQL LIKE（弱场景） |
| Prometheus + Grafana | 后期 | 监控 | 应用日志 |

原则：**按阶段引入，单中间件先跑稳，再决定是否升级。**

Java模块已引入`spring-boot-starter-amqp`和JSON消息转换基础配置，但当前不创建业务交换机、队列、生产者或消费者。文件重试后续接入RabbitMQ时，消息只保存文件ID等标识，不传输文件二进制，并在业务设计确认后再引入事务Outbox。

## 七、LLM 选型

### 7.1 候选模型

| 模型 | 优势 | 劣势 |
|---|---|---|
| Claude | 长文档、复杂推理、代码理解 | 成本较高 |
| GPT | 综合能力强、工具调用稳定 | 成本中高 |
| DeepSeek | 性价比高、中文友好 | 复杂推理略弱 |
| Gemini | 长上下文、多模态 | 国内调用不便 |
| Qwen | 中文、开源、本地化 | 顶级推理略弱 |

### 7.2 运行时模型策略

运行时模型分层、升级条件与成本边界以 [06-Agent设计.md](./06-Agent设计.md) 第 5 节为唯一权威。本文件不再重复列出场景表，避免双口径。

核心原则：

- 默认运行时模型：DeepSeek。
- 复杂推理、长文档、关键判断、最终润色：升级 Claude / GPT。
- 月度运行成本目标约 600 元人民币以内，必要时按 06 中成本降级策略处理。

### 7.3 开发期模型策略

- 主力 IDE：Claude Code（Opus / Sonnet 视任务选择）；
- 文档初稿与批量生成：DeepSeek；
- 文档终稿与架构设计：Claude；
- 产品方案与接口文档：GPT / Claude。

## 八、部署与本地开发

### 8.1 本地开发

- Docker 容器承载项目涉及到的中间件；
- 本地认证联调启动 MySQL 8 和 Redis 7 容器；
- Redis 当前用于 Sa-Token 会话持久化和文件写请求2分钟幂等校验，业务缓存和限流仍按实际需求接入；
- RabbitMQ已提供Docker和Java基础配置，但尚未接入业务生产或消费；MinIO、向量库等仍按阶段启用；
- Spring Boot 后端本机直接运行，便于断点调试；
- Vue 3 前端本机直接运行，便于热更新；
- 后端和前端分别维护环境变量示例文件；
- 配置统一通过 Spring profile、Vite 环境变量与 Docker Compose 环境变量管理。

### 8.2 部署目标（后期）

- 单台云服务器即可承载；
- 使用 Nginx 做前端静态与反向代理；
- Java、Python 各自打包为镜像；
- 通过 Docker Compose 一键起服务。

### 8.3 Docker 中间件引入策略

| 阶段 | 中间件 | Docker Compose 状态 | 说明 |
|---|---|---|---|
| 第 1 阶段 | MySQL 8 | 默认启用 | 支撑用户、项目、任务等业务表 |
| 第 2 阶段 | Redis 7 | 已加入并启用 | 当前用于 Sa-Token 会话持久化和文件写请求幂等校验，缓存和限流按需接入 |
| 第 5 阶段 | RabbitMQ | 基础配置已加入，业务接入待后续阶段 | 用于异步任务、通知、风险扫描和文件重试 |
| 第 6 阶段 | MinIO | 后续加入并启用 | 用于文档、附件、报告文件 |
| 第 6 阶段 | Qdrant 或 pgvector | 后续评估 | 用于向量检索，不在前 5 阶段提前引入 |

原则：Docker Compose 文件可以预留结构，但未到阶段的中间件不得默认启动，避免第 1 阶段运行负担过重。

## 九、被放弃的方案与原因

| 方案 | 放弃原因 |
|---|---|
| Spring Security + JWT | 配置复杂，单人项目成本高 |
| Element Plus | 视觉风格不符合偏好 |
| React + Ant Design | 单人开发可读性不如 Vue + Naive UI |
| Kafka | 量级用不上，RabbitMQ 已足够 |
| ELK 全套日志栈 | 单人项目过重，先用应用日志 |
| Nacos / Eureka | 单服务架构无需 |
| LangChain（第一版） | 抽象多，自研更可控 |

## 十、未来可演进方向

- 如未来需要多租户，必须作为独立产品重构重新评估；
- 引入 Spring Authorization Server / OIDC；
- 引入 Flowable 做复杂审批；
- 引入 Elasticsearch 做全文检索；
- 引入企业微信 / 钉钉机器人；
- 引入本地模型（Qwen / Ollama）以降低成本。
