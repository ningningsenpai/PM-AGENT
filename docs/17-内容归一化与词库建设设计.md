# 内容归一化与词库建设设计

> 文档状态：第一阶段已实现。已完成 Aho-Corasick、最长匹配、同义词归一、三级 JSON 词库、版本指纹、缓存、离线评估和发布检查；尚未接入 Agent、BM25F 和 SimHash。

## 1. 背景

PM-Agent 的项目文件、任务、需求、用户输入和 LLM 输出可能使用不同说法描述同一概念。例如“登录 API”“登录接口”可以统一为“登录接口”，“JWT 认证”“权限校验”可以统一为“认证鉴权”。如果内容建索引与用户查询使用不同术语，后续关键词召回会出现漏召回、误召回和结果重复。

当前 `agent-service/normalization_demo` 已完成 Aho-Corasick 精确词库匹配实验，但仍是单文件、单词库、请求时构建自动机的实验形态。正式模块需要补齐词库来源、版本、合并、冲突校验、缓存、统一输出和分阶段评估。

## 2. 目标

1. 建立公共、业务、项目三级术语库，并统一标准术语和别名。
2. 让项目内容和用户查询复用同一归一化流水线和词库版本。
3. 按顺序引入 Aho-Corasick、最长正向匹配、同义词归一化、BM25F 和 SimHash。
4. 每引入一个阶段都保留固定评估集和上一步基线，能够判断收益与回归。
5. 保留原文、命中位置、词库版本和规则版本，支持 Agent Trace 回放。

## 3. 范围

### 3.1 已实现范围

- 实现 `app/normalization` 运行时包和统一服务入口。
- 建立公共、业务两级正式 JSON 词库并预留项目词库 Provider。
- 实现词库校验、显式覆盖、合并版本指纹和只读自动机缓存。
- 实现内容、查询和结构化字段共用的归一化流水线。
- 实现固定样例评估和术语库发布检查。
- 为 BM25F、SimHash 保留文件位置，不实现召回和 RAG 链路。

### 3.2 本期不做

- 不接入 FastAPI 路由、现有 `ProjectChatAgent` 或项目内容索引。
- 不新增数据库表、Redis、消息队列、向量数据库或搜索引擎。
- 不允许 LLM 自动发布术语；LLM 只能生成待人工审阅的候选词。
- 不对 LLM 自然语言回答做无条件全文替换。

## 4. 模块边界

| 能力 | 所属模块 | 职责 |
|---|---|---|
| 基础文本处理 | `app.normalization.preprocessing` | 大小写、Unicode、空白和可配置标点处理 |
| 词库管理 | `app.normalization.lexicon` | 加载、校验、合并、版本选择和自动机缓存 |
| 候选识别 | `app.normalization.matching` | Aho-Corasick 一次扫描输出全部候选 |
| 重叠消歧 | `app.normalization.matching` | 在候选结果上执行最长正向匹配策略 |
| 同义词归一 | `app.normalization.mapping` | 将别名映射为标准术语 |
| 统一编排 | `app.normalization.pipeline` | 按固定顺序执行归一化步骤 |
| 对外入口 | `app.normalization.service` | 为内容侧、查询侧和 LLM 结构化输出提供统一调用 |
| 字段召回 | `app.rag.retrieval.bm25f` | 后续按标题、正文、标准术语等字段加权召回 |
| 近重复过滤 | `app.rag.retrieval.simhash_deduplicator` | 后续对召回结果进行近重复判断 |

BM25F 和 SimHash 不属于归一化核心。本期仅预留模块，待归一化指标稳定后分步实现。

## 5. 总体业务流程

```text
词库建设
来源登记 -> 候选提取 -> 人工审阅 -> 草稿生成 -> 合并与冲突校验
        -> 候选自动机构建 -> 离线评估 -> 版本发布 -> 运行时缓存

内容侧
项目内容 -> 字段提取 -> 基础处理 -> Aho-Corasick -> 最长匹配
        -> 同义词归一 -> 标准化字段 -> BM25F 索引 -> SimHash 指纹

查询侧
用户输入 -> 选择索引绑定的词库版本 -> 基础处理 -> Aho-Corasick
        -> 最长匹配 -> 同义词归一 -> 标准化查询 -> BM25F 召回
        -> SimHash 去重 -> 上下文组装 -> LLM

输出侧
LLM 结构化输出 -> Pydantic 校验 -> 指定字段术语归一 -> 风险检查
        -> 保留原始回答和归一化结果 -> 返回用户并记录 Trace
```

## 6. 词库建设流程

### 6.1 来源登记

| 层级 | 第一版来源 | 示例 | 更新方式 |
|---|---|---|---|
| 公共词库 | `docs/00-术语表.md`、通用技术术语 | 项目、需求、任务、Agent Trace | 随代码版本人工维护 |
| 业务词库 | API 名称、业务枚举、页面字段、规则文档 | 逾期任务、风险分析、任务草稿 | 随业务版本人工维护 |
| 项目词库 | 项目模块名、项目简称、受控项目配置 | 认证中心、排期看板 | 后续通过 Java 只读工具 API 获取 |

第一版只使用仓库内 JSON。项目动态词库后续由 Java 后端管理权限和持久化，Python Agent 只通过受控只读接口获取，不直接访问业务数据库。

### 6.2 候选提取和人工审阅

候选词可由文档标题、接口路径、业务枚举、历史查询高频短语和 LLM 辅助提取产生。候选结果必须人工确认以下内容后才能进入草稿词库：

- 标准术语是否与 `docs/00-术语表.md` 一致；
- 别名是否真的表达同一业务概念；
- 术语所属分类、作用域和来源是否明确；
- 是否存在过短、歧义或可能造成大量误召回的别名；
- 项目专属信息是否允许进入该作用域。

### 6.3 词库数据结构

词库清单建议使用以下字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `lexicon_id` | 是 | 稳定词库标识，例如 `pm-common` |
| `version` | 是 | 不可变发布版本；草稿统一使用 `draft` |
| `scope` | 是 | `common`、`domain` 或 `project` |
| `scope_id` | 项目级必填 | 项目级作用域标识 |
| `status` | 是 | `draft`、`published`、`disabled` |
| `description` | 是 | 词库用途和边界 |
| `entries` | 是 | 术语词条列表 |

词条建议使用以下字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `term_id` | 是 | 词条稳定标识，不随标准术语显示名变化 |
| `canonical` | 是 | 系统输出和索引使用的标准术语 |
| `aliases` | 是 | 可匹配别名，标准术语自动并入别名集合 |
| `category` | 是 | 业务分类，例如 `task`、`risk`、`agent` |
| `tags` | 否 | 检索过滤和分析标签 |
| `priority` | 否 | 同长度候选的显式优先级，默认 `0` |
| `enabled` | 是 | 是否参与当前版本匹配 |
| `source` | 是 | 词条来源，例如 `glossary`、`api`、`manual` |

### 6.4 合并和冲突规则

运行时合并顺序为公共词库、业务词库、项目词库，优先级为：

```text
项目词库 > 业务词库 > 公共词库
```

冲突不能依赖 `Automaton.add_word()` 的后写覆盖行为，必须在构建自动机前显式处理：

| 场景 | 处理规则 |
|---|---|
| 同一别名映射到同一标准术语 | 合并标签和来源，保留高优先级元数据 |
| 同一别名映射到不同标准术语 | 校验失败，禁止发布，要求人工选择或缩小作用域 |
| 标准术语重复但 `term_id` 不同 | 校验失败，先合并词条 |
| 空别名、重复别名、禁用词条 | 清理后生成校验报告 |
| 项目词覆盖公共词 | 必须有显式覆盖记录，不能静默覆盖 |

### 6.5 版本发布

1. 草稿词库通过结构和冲突校验。
2. 使用候选版本构建只读 Aho-Corasick 自动机。
3. 运行固定离线评估集并与上一个发布版本比较。
4. 评估通过后发布不可变版本，例如 `2026.07.1`。
5. 自动机缓存键使用 `(tenant_id, project_id, lexicon_version)`。
6. 已发布版本只允许禁用，不原地修改；任何内容变化都生成新版本。
7. 内容索引记录 `lexicon_version`，词库升级后重建对应索引；查询必须使用索引绑定版本。

## 7. 归一化处理设计

### 7.1 基础文本处理

第一版执行 Unicode NFKC、英文大小写统一和连续空白折叠，保留 `/`、`_`、`-` 等技术术语常见字符。词库别名与输入文本必须使用同一处理器。

基础处理可能改变字符长度，因此输出需要保留处理后文本与原文位置映射，不能直接假设处理后下标永远等于原文下标。

### 7.2 Aho-Corasick 候选匹配

词库发布或版本首次使用时构建自动机，请求处理只读取缓存，不重复构建。匹配器输出全部候选及其 `term_id`、标准术语、别名、分类、来源、起止位置和优先级。

### 7.3 最长正向匹配

最长正向匹配不再次扫描全文，而是在 Aho-Corasick 候选集上执行：先按开始位置升序，再按匹配长度降序，再按作用域和词条优先级排序，最终选出不重叠结果。

第一版采用“最长且不重叠”策略。是否允许嵌套实体作为后续可配置策略，不进入第一版。

### 7.4 同义词归一化

匹配命中的 `alias` 通过词条直接映射到 `canonical`。输出既保留原始别名，也保留标准术语；相同标准术语默认只进入一次 `normalized_terms`，详细 `matches` 仍可保留全部命中供 Trace 和评估使用。

### 7.5 统一输出

```json
{
  "raw_text": "登录API需要补充JWT认证",
  "cleaned_text": "登录api需要补充jwt认证",
  "lexicon_version": "2026.07.1",
  "normalized_terms": ["登录接口", "认证鉴权"],
  "matches": [
    {
      "term_id": "auth-login-api",
      "canonical": "登录接口",
      "alias": "登录API",
      "category": "backend",
      "start": 0,
      "end": 4,
      "source": "domain"
    }
  ],
  "warnings": []
}
```

## 8. 内容、查询和 LLM 调用链

### 8.1 项目内容建索引

```text
项目内容扫描/字段提取
  -> NormalizationService.normalize_document()
  -> LexiconRegistry.resolve(project_id, index_version)
  -> NormalizationPipeline.run()
  -> TextNormalizer
  -> AhoMatcher
  -> LongestMatchResolver
  -> SynonymMapper
  -> NormalizedDocument
  -> BM25F 索引和 SimHash 指纹（后续阶段）
```

标题、章节、正文和标准术语必须分字段保存，BM25F 才能分别配置权重。建议初始权重由评估确定，不在本期写死。

### 8.2 用户查询

```text
ProjectChatAgent 收到用户输入
  -> NormalizationService.normalize_query()
  -> 使用目标索引绑定的 lexicon_version
  -> NormalizationPipeline.run()
  -> NormalizedQuery
  -> BM25F 字段召回（后续阶段）
  -> SimHash 近重复过滤（后续阶段）
  -> LLMContextBuilder 组装上下文
  -> LLM
```

归一化结果用于扩展检索词、过滤和 Trace，不直接覆盖用户原始消息。

### 8.3 LLM 输出

LLM 的任务、风险、需求等结构化字段先通过 Pydantic 校验，再对指定字段执行术语归一化。自然语言回答只检测和记录术语，不做全局字符串替换。涉及写业务或高风险动作时，仍按现有人工确认流程执行。

## 10. 分阶段实现与评估

| 阶段 | 实现内容 | 核心指标 | 进入下一阶段条件 |
|---|---|---|---|
| 第 1 步 | Aho-Corasick + JSON 词库 + 自动机缓存 | Precision、Recall、F1、P95 耗时 | 扩充人工标注集后不低于当前基线 |
| 第 2 步 | 候选集最长正向匹配 | 重叠选择准确率、位置准确率 | 长短词和交叉词用例通过 |
| 第 3 步 | 同义词归一和多级词库 | 标准术语准确率、冲突数 | 冲突全部显式处理，无静默覆盖 |
| 第 4 步 | BM25F 字段召回 | Recall@K、MRR、NDCG@K | 相对无字段基线有稳定收益 |
| 第 5 步 | SimHash 近重复过滤 | 重复识别 Precision/Recall、有效结果保留率 | 重复减少且有效结果无明显损失 |

评估集必须包含正例、无术语负例、重叠词、歧义别名、英文大小写、API 路径、项目覆盖词和长文本。当前 demo 的 4 条样例仅作为冒烟测试，不能作为上线指标。

## 13. 风险与取舍

| 风险 | 处理方案 |
|---|---|
| Unicode 处理导致位置偏移 | 保留处理前后位置映射 |
| 同一别名在不同词库含义不同 | 发布前阻断冲突，项目覆盖必须显式记录 |
| 每个请求重复构建自动机 | 按租户、项目、词库版本缓存只读自动机 |
| 词库升级后索引与查询不一致 | 索引绑定版本，升级时重建索引 |
| LLM 候选词污染正式词库 | LLM 只产出草稿，必须人工确认 |
| 归一化改变用户原意 | 永远保留原文，只对检索字段和结构化字段归一化 |

## 14. 验收标准

- 包结构与本文档职责一致，运行时入口只有 `NormalizationService`。
- 内容侧与查询侧使用同一基础处理、匹配、消歧和映射流程。
- 词库冲突不会被 `add_word()` 静默覆盖。
- 每次结果包含原文、处理后文本、标准术语、详细命中和词库版本。
- 已发布词库不可原地修改，索引和查询能够绑定同一版本。
- 每个算法阶段都有独立评估指标和回归样例。
- 本期不提前接入完整 RAG、向量数据库或新的运行中间件。
