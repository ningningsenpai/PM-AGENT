# 数据模型

## 1. 所有权

业务库由 Python SQLAlchemy 访问，结构由 `agent-service/migrations/` 独占管理。本次迁移创建空的开发库基线，不迁移旧 Flyway 数据。

## 2. `pm_user`

| 字段 | 说明 |
|---|---|
| `id` | `BIGINT` 主键，由后端雪花算法生成 |
| `username` | 唯一用户名 |
| `password_hash` | Argon2 密码哈希 |
| `email` | 唯一登录邮箱 |
| `status` | `enabled` / `disabled` |
| `last_login_at` | 最近登录时间 |
| `created_at` / `updated_at` | 审计时间 |

## 3. `pm_project`

| 字段 | 说明 |
|---|---|
| `id` | `BIGINT` 主键，由后端雪花算法生成 |
| `owner_user_id` | 所属用户，外键到 `pm_user` |
| `project_name` | 项目名称 |
| `status` | `initializing` / `active` / `init_failed` |
| `record_status` | 记录状态：`enabled` / `disabled`，用于惰性删除 |
| `enabled_project_name` | 生成列；记录启用时等于 `project_name`，禁用时为 `NULL` |
| `deleted_at` | 惰性删除时间；启用记录为 `NULL` |
| `purge_after` | 最早允许物理清理的时间；删除时间加三十天 |
| `created_at` / `updated_at` | 审计时间 |

`owner_user_id + enabled_project_name` 唯一，只限制同一用户启用中的同名项目；删除用户时数据库外键仍会级联删除所属项目。`record_status + purge_after` 联合索引用于扫描到期记录。业务删除项目时把 `record_status` 更新为 `disabled`，写入 `deleted_at` 和 `purge_after`；项目列表、详情、文件和 Agent 入口均把该记录视为不存在。三十天保留期内不删除项目文件行或 MinIO 对象，再次创建同名项目时创建新记录、新项目 ID 和空白上下文，不恢复旧记录。

外部定时清理先根据 `owner_user_id + id` 生成 MinIO 项目前缀并删除对象，确认前缀为空后再物理删除项目记录。项目文件行通过外键随项目级联删除；任一存储或数据库操作失败时保留项目记录，等待下一次定时扫描。

`pm_user.id` 和 `pm_project.id` 保留 `BIGINT` 存储，但不再使用数据库自增。历史 ID 保持不变，新记录由后端雪花算法生成；不同运行实例必须配置不同的 `PM_AGENT_SNOWFLAKE_NODE_ID`。

## 4. `pm_project_file`

| 分类 | 字段 |
|---|---|
| 归属 | `id`、`project_id`、`business_code` |
| 逻辑路径 | `relative_path`、`path_hash`、`file_name`、`extension` |
| 对象存储 | `storage_uuid`、`storage_name`、`object_key`、`minio_path` |
| 内容事实 | `content_type`、`size_bytes`、`source_mtime_ms`、`quick_fingerprint`、`content_hash` |
| 状态机 | `status`、`upload_status`、`upload_attempts`、`lock_version` |
| 分析投影 | `parse_attempts`、`detail_ref`、`module`、`kind`、`file_type`、`language`、`importance`、`summary`、`keywords` |
| 诊断 | `last_error_code`、`last_error_message`、`last_failed_at` |
| 审计 | `created_at`、`updated_at` |

关键唯一约束：

- `project_id + business_code + path_hash`
- `object_key`
- `project_id + business_code + storage_name`
- `project_id + storage_uuid`

文件生命周期状态：

```text
uploading / active / updating / upload_failed /
verify_required / missing / deleting / delete_failed
```

上传事实状态：

```text
not_uploaded / retrying / success / failed
```

项目业务删除为惰性删除，不立即触发级联删除或 MinIO 对象清理。项目超过三十天保留期并完成 MinIO 清理后，物理删除项目记录会通过外键级联删除项目文件记录。

`detail_ref` 为空表示当前内容或路径尚无有效详情。分析成功后写入引用；内容或路径变化时清空引用和分析投影。`content_hash` 与 `lock_version` 共同保护分析结果回填，不再保存或比较分析管线版本。

## 5. 显式学习与上下文数据职责

显式学习的数据分为“工作流数据”和“正式上下文正文”，两者不能互相替代：

| 数据 | 位置 | 是否参与 Agent 召回 |
|---|---|---|
| 会话消息、学习游标、候选、反馈、确认状态、来源与变更记录 | MySQL `agent_conversation`、`agent_message`、`agent_learning_draft` 等表 | 否，仅用于审核、恢复和审计 |
| 项目规范、长短期记忆、用户习惯当前正文 | MinIO `system/` 固定文件 | 是，唯一正式来源 |
| 文件详情 | MinIO `system/file_details/`，MySQL 保存当前 `detail_ref` | 是，必须通过当前文件投影校验 |
| 运行与模型工具轨迹 | MySQL `agent_run` | 否，仅用于运行恢复和 Trace |

`agent_learning_draft` 保存完整草稿负载与并发控制字段：`id`、用户/项目/会话外键、草稿 `version`、乐观锁 `lock_version`、`state`、JSON `payload` 及审计时间。`state` 只允许 `pending/updating/partial/applied/discarded`。确认计划和每个目标文件的条件写结果均保存在 `payload`，服务重启后可以恢复同一次确认；正式正文仍以固定 MinIO 文件为准。

旧 `agent_context_scope`、`agent_context_entry`、`agent_context_change` 以及 ContextStore 对象不再承担运行时正式正文职责，只作为历史迁移和兼容审计来源保留。用户确认只有在目标固定文件条件写成功后才算生效。

项目正式上下文不使用 `context/manifest.json`、应用级版本目录或按 revision 寻址。详细存储与显式学习边界见 [19-项目上下文索引与MinIO存储设计](./19-项目上下文索引与MinIO存储设计.md) 和 [27-云端上下文与显式学习改造](./27-云端上下文与显式学习改造.md)。

MySQL 时间字段继续使用 `DATETIME`，统一保存上海本地无时区值；连接创建后固定执行 `SET time_zone = '+08:00'`。API 层再将值解释为 `Asia/Shanghai` 并输出 `+08:00`，不依赖数据库主机或进程默认时区。历史时间不做批量平移。

## 6. 迁移

```bash
cd agent-service
python -m alembic upgrade head
python -m alembic downgrade base
```

历史迁移一旦应用不得直接修改；后续结构变更必须新增 Alembic revision。
