# 04 数据模型

## 1. 文档定位

本文档记录当前已经落地的数据模型。项目文件批次上传规则以 [18-项目文件批次上传模块设计](./18-项目文件可靠上传模块设计.md) 为唯一权威，字段以 Java 实体和最新 Flyway migration 为准。

## 2. 建模原则

1. MySQL 8 是项目、文件、上传请求、批次和索引重建状态的唯一准确数据源。
2. 系统支持多个用户，不增加租户字段或租户索引。
3. 普通业务表使用 MySQL 自增 BIGINT 主键。
4. 状态使用小写字符串编码。
5. 不保留文件历史版本。
6. 不增加逐轮文件明细表，同一逻辑文件只保留一条 `pm_project_file`。
7. MinIO 冗余对象不影响业务判断，后续以 MySQL 有效对象键为准清理。
8. 当前文件上传链路不使用 RabbitMQ 或 Outbox。

## 3. 表清单

| 表 | 职责 |
|---|---|
| `pm_user` | 用户认证和基础资料 |
| `pm_project` | 项目空间、所有者和初始化状态 |
| `pm_project_file` | 项目逻辑文件、指纹、上传状态和成功后的 MinIO 存储信息 |
| `pm_project_file_upload_request` | 同一项目一次文件夹上传的根请求、轮次、终态和索引重建时间 |
| `pm_project_file_ingest_batch` | manifest 预注册的物理批次及其完成统计 |
| `pm_event_outbox` | 历史表；当前文件批次上传不读写 |

## 4. 基础表

### 4.1 `pm_user`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 自增主键 |
| `username` | VARCHAR(64) | 全局唯一用户名 |
| `email` | VARCHAR(128) | 全局唯一登录邮箱 |
| `password_hash` | VARCHAR(255) | BCrypt 密码哈希 |
| `status` | VARCHAR(32) | `enabled / disabled` |
| `last_login_at` | DATETIME | 最近登录时间 |
| `created_at / updated_at` | DATETIME | 时间字段 |

不保留 `tenant_id`、`deleted`、`created_by` 或 `updated_by`。

### 4.2 `pm_project`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 自增主键 |
| `owner_user_id` | BIGINT | 项目所属用户 |
| `project_name` | VARCHAR(128) | 项目名称 |
| `status` | VARCHAR(32) | 项目状态 |
| `created_at / updated_at` | DATETIME | 时间字段 |

项目先写 `initializing`，固定 `system/index.json` 同步上传成功后才进入 `active`。

## 5. 上传请求根表

### 5.1 `pm_project_file_upload_request`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 自增主键 |
| `owner_user_id` | BIGINT | 项目所属用户 |
| `project_id` | BIGINT | 项目 ID |
| `request_id` | VARCHAR(64) | 前端三轮复用的请求 ID |
| `original_total_files` | INT | 首轮筛选后的总文件数 |
| `current_attempt` | TINYINT | 当前轮次，对应接口 `attemptNo` |
| `round_total_files` | INT | 当前轮文件数 |
| `round_total_batches` | INT | 当前轮预注册批次数，对应 `totalBatchCount` |
| `round_manifest_hash` | CHAR(64) | 当前轮 manifest 摘要哈希 |
| `status` | VARCHAR(32) | 请求状态 |
| `succeeded_files` | INT | 当前请求已成功上传文件数 |
| `failed_files` | INT | 终态失败文件数 |
| `index_rebuilt_at` | DATETIME | 同步重建 `index.json` 成功时间 |
| `completed_at` | DATETIME | 请求进入终态时间 |
| `created_at / updated_at` | DATETIME | 时间字段 |

请求状态只使用：

~~~text
uploading
awaiting_retry
completed
completed_with_failures
~~~

关键约束：

~~~text
UNIQUE(project_id, request_id)
CHECK(current_attempt BETWEEN 1 AND 3)
CHECK(original_total_files > 0)
CHECK(round_total_files > 0)
CHECK(round_total_batches > 0)
CHECK(succeeded_files BETWEEN 0 AND original_total_files)
CHECK(failed_files BETWEEN 0 AND original_total_files)
~~~

该表不保存已完成批次数。完成闸门直接统计当前轮物理批次。

## 6. 物理批次表

### 6.1 `pm_project_file_ingest_batch`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 自增主键 |
| `project_id` | BIGINT | 所属项目 |
| `upload_request_id` | BIGINT | 上传请求根记录 |
| `attempt_no` | TINYINT | 所属轮次 |
| `client_batch_id` | VARCHAR(64) | 前端 `batchId` |
| `idempotency_key` | VARCHAR(64) | 当前批次首次提交的幂等键 |
| `payload_hash` | CHAR(64) | 当前批次文件身份、元信息、快速指纹和内容哈希的稳定摘要 |
| `total_files` | INT | 当前批次文件数，1～50；前端同时保证原始文件总大小不超过 240 MB |
| `completed_files` | INT | 当前批次已处理文件数 |
| `succeeded_files` | INT | 当前批次成功数 |
| `failed_files` | INT | 当前批次失败数 |
| `status` | VARCHAR(32) | 新流程物理批次状态 |
| `created_at / updated_at` | DATETIME | 时间字段；进入或接管 `processing` 时显式刷新 `updated_at` |

新流程状态：

~~~text
waiting
processing
completed
~~~

历史 `uploading / upload_completed / analyzing` 只用于旧数据兼容，新流程不再写入。

关键索引：

~~~text
UNIQUE(upload_request_id, attempt_no, client_batch_id)
INDEX(upload_request_id, attempt_no, status)
~~~

第一轮或重试轮的首个请求根据 manifest 一次预注册本轮全部批次，状态为 `waiting`。前端随后逐批顺序调用，各请求分别把自己的批次置为 `processing`，处理结束后变为 `completed`。后端只在当前单批内部多线程上传文件。`processing` 超过默认 15 分钟时，仅允许相同幂等键接管；接管过程根据文件行的 `last_upload_batch_id` 和 `upload_status` 跳过当前物理批次已经成功的文件。

数据库不额外保存单批原始字节总数；240 MB 是前端拆批阈值，后端以 256 MB Multipart 请求上限兜底。普通源码项目通常先达到 50 个文件阈值。

## 7. 项目文件表

### 7.1 `pm_project_file` 新流程字段

| 字段组 | 字段 | 第一轮首次落库 |
|---|---|---|
| 归属 | `project_id`、`upload_request_id`、`client_file_id`、`business_code` | 必填 |
| 路径 | `relative_path`、`path_hash`、`file_name`、`extension` | 必填 |
| 元信息 | `content_type`、`size_bytes`、`source_mtime_ms` | 必填 |
| 指纹 | `quick_fingerprint`、`content_hash` | 必填 |
| 状态 | `status`、`upload_status` | `uploading / not_uploaded` |
| 存储 | `storage_uuid`、`storage_name`、`object_key`、`minio_path`、`detail_ref` | NULL |
| 最近上传 | `last_upload_attempt`、`last_upload_batch_id` | 按实际处理更新 |
| 并发 | `lock_version` | 0 |
| 时间 | `created_at / updated_at` | 自动维护 |

### 7.2 上传状态

新批次流程使用：

~~~text
not_uploaded
success
~~~

- 第一轮元数据落库为 `not_uploaded`；
- 当前轮失败不更新文件行，仍为 `not_uploaded`；
- MinIO 成功且 MySQL 回填成功后变为 `success`；
- 第三轮结束后仍为 `not_uploaded` 的文件进入索引失败列表。

数据库暂时保留历史 `retrying / failed` 兼容值，但新流程不写入。

### 7.3 存储字段

`storage_uuid`、`storage_name`、`object_key`、`minio_path` 和 `detail_ref` 允许为空，只在成功上传后回填。

关键索引：

~~~text
UNIQUE(project_id, business_code, path_hash)
UNIQUE(upload_request_id, client_file_id)
UNIQUE(object_key)
INDEX(upload_request_id, upload_status)
INDEX(project_id, business_code, upload_status)
INDEX(project_id, content_hash)
~~~

`UNIQUE(upload_request_id, client_file_id)` 与业务校验共同保证一个请求内每个前端文件只有一条事实记录；首轮同一 `client_file_id` 不得跨物理批次复用。

## 8. 完成闸门

物理批次处理完成后实时查询：

~~~sql
SELECT COUNT(*)
FROM pm_project_file_ingest_batch
WHERE upload_request_id = ?
  AND attempt_no = ?;

SELECT COUNT(*)
FROM pm_project_file_ingest_batch
WHERE upload_request_id = ?
  AND attempt_no = ?
  AND status = 'completed';
~~~

只有“预注册批次数”和“已完成批次数”都等于 `round_total_batches`，当前轮才结束。

随后查询文件事实完整性和状态分布：

~~~sql
SELECT COUNT(*)
FROM pm_project_file
WHERE upload_request_id = ?;

SELECT upload_status, COUNT(*)
FROM pm_project_file
WHERE upload_request_id = ?
  AND upload_status IN ('success', 'not_uploaded')
GROUP BY upload_status;
~~~

只有“文件事实行总数等于 `original_total_files`”且“`success + not_uploaded` 等于 `original_total_files`”时，才允许继续判断请求状态；否则按数据冲突拒绝进入终态。

| 条件 | 请求状态 |
|---|---|
| 未上传数为 0 | `completed` |
| 未上传数大于 0 且当前轮小于 3 | `awaiting_retry` |
| 未上传数大于 0 且当前轮等于 3 | `completed_with_failures` |

请求进入终态后同步重建索引。`index_rebuilt_at` 非空表示重建成功；终态请求的该字段为空表示待恢复。索引失败不增加新状态。

## 9. 索引与 MinIO

固定索引对象键：

~~~text
PM-AGENT/{ownerUserId}/{projectId}/system/index.json
~~~

- `success` 文件进入正常文件数组；
- 终态 `not_uploaded` 文件进入 `upload_failures`；
- 索引完全从 MySQL 全量构造；
- 不读取旧索引合并；
- 不用 MinIO 对象列表推断业务状态；
- 当前不通过 MQ 或 Outbox 重建索引。

## 10. Flyway 迁移

V1～V11 是历史迁移，不直接修改。新版批次上传通过 `V12__redesign_project_file_batch_upload.sql` 落地：

1. 创建 `pm_project_file_upload_request`；
2. 为导入批次增加上传请求、轮次和前端批次 ID；
3. 增加 `waiting / processing / completed`；
4. 为文件增加上传请求、前端文件 ID 和最近上传字段；
5. 将存储字段改为可空；
6. 增加 `not_uploaded`；
7. 增加请求、批次和文件索引。

历史 `pm_event_outbox` 表不参与当前新流程。

## 11. 数据事实归属

| 判断 | MySQL 事实 |
|---|---|
| 项目是否可上传 | `pm_project.status = active` |
| 当前轮合同 | 请求表中的轮次、总数和 manifest 哈希 |
| 物理批次是否结束 | 批次表 `status = completed` |
| 当前轮是否全部结束 | 预注册批次数与已完成批次数统计 |
| 文件是否成功 | `pm_project_file.upload_status` |
| 是否需要重试 | 请求状态 `awaiting_retry` |
| 最终失败文件 | 终态请求下仍为 `not_uploaded` 的文件 |
| 索引是否已重建 | `index_rebuilt_at IS NOT NULL` |

## 12. 验收标准

1. 请求状态只使用四种当前状态。
2. 物理批次新流程只使用三种状态。
3. manifest 全量预注册物理批次。
4. 完成闸门不依赖请求表完成计数字段。
5. 第一轮文件存储字段为空。
6. 三轮通过 `client_file_id` 复用同一文件行。
7. 索引失败通过终态加空 `index_rebuilt_at` 恢复。
8. 当前上传链路不读写 Outbox。
