# 04 数据模型

## 1. 背景

当前 Java 后端承载公共基座、用户认证、当前用户资料和项目文件存储。系统支持多个用户，但不设计租户、组织或租户隔离。

## 2. 目标

- 保留 `pm_user`，并新增最小项目归属和项目文件表；
- 使用全局唯一邮箱登录；
- 用户名和邮箱分别保持唯一；
- 删除多租户、逻辑删除和操作人审计字段；
- 删除 `single_account_key`、`display_name` 和 `mobile`。
- 普通文件使用持久化 `storage_uuid` 生成稳定存储名，内容更新覆盖同一对象，不保存历史版本；
- 项目上下文总索引固定存储在 `system/index.json`，不作为 `pm_project_file` 普通记录对外暴露。

## 3. 范围

### 3.1 本期范围

- 多用户注册；
- 邮箱密码登录；
- 用户名和邮箱资料维护；
- 密码修改和最近登录时间记录。
- 用户项目文件空间；
- 项目文件元信息、逻辑路径、稳定存储标识、双哈希、上传次数和失败状态。

### 3.2 不做范围

- `tenant_id`、租户表和租户过滤；
- 角色、权限和组织表；
- 逻辑删除；
- 完整项目管理、任务、Agent和outbox等业务表；
- 文件历史版本表；
- 展示名称和手机号字段。

## 4. 详细设计

### 4.1 表清单

| 表名 | 说明 |
|---|---|
| `pm_user` | 用户认证信息和基础资料 |
| `pm_project` | 文件归属所需的最小项目信息 |
| `pm_project_file` | 项目逻辑文件及当前内容元信息 |

### 4.2 `pm_user` 字段

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 是 | 自增 | 主键 |
| `username` | VARCHAR(64) | 是 | 无 | 用户名，全局唯一 |
| `email` | VARCHAR(128) | 是 | 无 | 登录邮箱，全局唯一 |
| `password_hash` | VARCHAR(255) | 是 | 无 | BCrypt 密码哈希 |
| `status` | VARCHAR(32) | 是 | `enabled` | `enabled` 或 `disabled` |
| `last_login_at` | DATETIME | 否 | NULL | 最近登录时间 |
| `created_at` | DATETIME | 是 | 当前时间 | 创建时间 |
| `updated_at` | DATETIME | 是 | 当前时间 | 更新时间 |

### 4.3 主键与索引

| 名称 | 类型 | 字段 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 用户标识 |
| `uk_user_username` | 唯一索引 | `username` | 防止用户名重复 |
| `uk_user_email` | 唯一索引 | `email` | 登录查询并防止邮箱重复 |

### 4.4 数据约束

- `email` 必填，写入前统一去除首尾空格并转小写；
- `username` 必填，当前同样规范化为小写；
- `status` 只能为 `enabled` 或 `disabled`；
- 密码只保存 BCrypt 哈希；
- 不限制用户记录数量；
- 不保留 `tenant_id`、`deleted`、`created_by` 或 `updated_by`。

### 4.5 BaseEntity

Java `BaseEntity` 只包含：

```text
id
createdAt
updatedAt
```

## 5. 迁移策略

Flyway 使用 `V1__init_phase1_schema.sql` 创建历史初始表，`V3__align_phase1_schema_and_add_project_file_storage.sql` 对齐无租户模型并创建项目文件表，`V4__move_file_idempotency_to_redis.sql` 移除数据库幂等约束，`V5__drop_project_file_upload_tables.sql` 删除上传批次表，`V6__align_project_context_storage.sql` 增加稳定存储标识、失败信息字段和项目删除状态，`V7__drop_legacy_tenant_tables.sql` 删除当前阶段未使用的 `pm_project_member`、`pm_task`、`pm_task_status_log`。2分钟重复提交校验统一由 Redis 原子占位负责。

V1、V2 中的 `tenant_id` 属于历史多租户设计，仅用于保证既有 Flyway 迁移链可追溯，不代表当前模型仍保留租户。已执行过的历史迁移不直接改写，最终结构由后续迁移收敛。执行 V1–V7 后，当前阶段业务表只保留 `pm_user`、`pm_project`、`pm_project_file`，另有 Flyway 自身维护的 `flyway_schema_history`。

## 6. 风险与取舍

| 风险 | 处理 |
|---|---|
| 并发注册相同邮箱或用户名 | 应用层检查，数据库唯一索引最终兜底 |
| 邮箱大小写导致重复 | 注册、登录和资料修改均规范化为小写 |
| 旧库迁移校验失败 | 重置旧数据库，不兼容已删除业务表 |
| 密码泄露 | 不保存明文，不在日志输出密码、哈希或 token |
| 文件改名需要搬迁对象 | 保留 `storage_uuid`，复制新对象、更新数据库、删除旧对象并在异常时执行补偿 |
| 并发覆盖文件 | `status`与`lock_version`共同抢占更新权 |
| 文件写请求重复提交 | Redis按用户、操作范围和幂等键原子占位2分钟 |
| MinIO覆盖成功但最终落库失败 | 文件进入`verify_required`，客户端使用新幂等键重新提交内容 |

## 7. 验收标准

- 新数据库包含用户、最小项目和项目文件表，不包含上传记录表及上传明细表；
- 完整执行 V1–V7 后不存在 `pm_project_member`、`pm_task`、`pm_task_status_log`；
- 可以注册多个邮箱不同的用户；
- 重复用户名或邮箱被拒绝；
- 登录只按邮箱查询；
- 表中不存在 `single_account_key`、`display_name`、`mobile` 和 `tenant_id`。
- 不存在文件版本表，内容更新始终覆盖稳定 `object_key`；
- `(project_id, business_code, storage_uuid)` 和 `object_key` 均保持唯一。

## 8. 文件存储模型

### 8.1 层级

```text
pm_user -> pm_project -> business_code -> pm_project_file
```

`business_code` 使用 `project/user/system` 枚举，不单独建表。公开接口只允许 `project` 和 `user`；`system` 由索引等内部组件使用。

### 8.2 路径

- `relative_path`：用户和 Agent 看到的可变逻辑路径；
- `storage_uuid`：文件首次创建时生成的16位十六进制稳定标识；
- `object_key`：`PM-AGENT/{ownerUserId}/{projectId}/{businessCode}/{文件主名}-{storageUuid}.{扩展名}`；
- 仅目录变化不改变 `object_key`，文件名变化时保留 `storage_uuid` 并迁移对象键；
- Bucket 固定为 `pm-agent`，预签名 URL 不进入文件表；
- 项目上下文索引固定对象键为 `PM-AGENT/{ownerUserId}/{projectId}/system/index.json`。

### 8.3 哈希

- `quick_fingerprint`：规范化路径、大小和源修改时间的SHA-256，不读取内容；
- `content_hash`：文件完整内容的SHA-256；
- 内容哈希相同则不写MinIO，内容哈希不同则覆盖原对象。

### 8.4 枚举

数据库保存字符串编码，Java 分别使用 `UserStatus`、`ProjectStatus`、`FileBusinessType` 和 `ProjectFileStatus`。项目删除状态增加 `deleting`、`delete_failed`；文件状态继续使用 `uploading`、`active`、`updating`、`upload_failed`、`verify_required`、`missing`、`deleting`、`delete_failed`。

### 8.5 上传失败字段与约束

| 字段 | 类型 | 说明 |
|---|---|---|
| `storage_uuid` | `CHAR(16)` | 对象存储名中的稳定随机标识 |
| `upload_attempts` | `INT` | 当前累计上传次数，不能小于0 |
| `last_error_code` | `VARCHAR(64)` | 最后一次统一错误码标识 |
| `last_error_message` | `VARCHAR(500)` | 脱敏后的中文错误摘要 |
| `last_failed_at` | `DATETIME` | 最后失败时间 |

关键唯一约束为 `UNIQUE(project_id, business_code, storage_uuid)` 和 `UNIQUE(object_key)`。最终上传失败记录保留在 `pm_project_file`，由重建索引流程写入 `upload_failures`。
