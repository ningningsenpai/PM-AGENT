# 04 数据模型

## 1. 背景

当前 Java 后端承载公共基座、用户认证、当前用户资料和项目文件存储。系统支持多个用户，但不设计租户、组织或租户隔离。

## 2. 目标

- 保留 `pm_user`，并新增最小项目归属和项目文件表；
- 使用全局唯一邮箱登录；
- 用户名和邮箱分别保持唯一；
- 删除多租户、逻辑删除和操作人审计字段；
- 删除 `single_account_key`、`display_name` 和 `mobile`。
- 文件内容更新覆盖同一个MinIO对象，不保存历史版本。

## 3. 范围

### 3.1 本期范围

- 多用户注册；
- 邮箱密码登录；
- 用户名和邮箱资料维护；
- 密码修改和最近登录时间记录。
- 用户项目文件空间；
- 项目文件元信息、逻辑路径、双哈希和上传追踪。

### 3.2 不做范围

- `tenant_id`、租户表和租户过滤；
- 角色、权限和组织表；
- 逻辑删除；
- 完整项目管理、任务、Agent和outbox等业务表；
- 文件历史版本表；
- 展示名称和手机号字段。

## 4. 详细设计

### 4.1 表清单

| 表名 | 说明 |
|---|---|
| `pm_user` | 用户认证信息和基础资料 |
| `pm_project` | 文件归属所需的最小项目信息 |
| `pm_project_file` | 项目逻辑文件及当前内容元信息 |
| `pm_project_file_upload` | 单文件上传或覆盖操作记录 |
| `pm_project_file_upload_item` | 上传候选元信息与处理结果 |

### 4.2 `pm_user` 字段

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | 是 | 自增 | 主键 |
| `username` | VARCHAR(64) | 是 | 无 | 用户名，全局唯一 |
| `email` | VARCHAR(128) | 是 | 无 | 登录邮箱，全局唯一 |
| `password_hash` | VARCHAR(255) | 是 | 无 | BCrypt 密码哈希 |
| `status` | VARCHAR(32) | 是 | `enabled` | `enabled` 或 `disabled` |
| `last_login_at` | DATETIME | 否 | NULL | 最近登录时间 |
| `created_at` | DATETIME | 是 | 当前时间 | 创建时间 |
| `updated_at` | DATETIME | 是 | 当前时间 | 更新时间 |

### 4.3 主键与索引

| 名称 | 类型 | 字段 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 用户标识 |
| `uk_user_username` | 唯一索引 | `username` | 防止用户名重复 |
| `uk_user_email` | 唯一索引 | `email` | 登录查询并防止邮箱重复 |

### 4.4 数据约束

- `email` 必填，写入前统一去除首尾空格并转小写；
- `username` 必填，当前同样规范化为小写；
- `status` 只能为 `enabled` 或 `disabled`；
- 密码只保存 BCrypt 哈希；
- 不限制用户记录数量；
- 不保留 `tenant_id`、`deleted`、`created_by` 或 `updated_by`。

### 4.5 BaseEntity

Java `BaseEntity` 只包含：

```text
id
createdAt
updatedAt
```

## 5. 迁移策略

Flyway使用`V1__init_phase1_schema.sql`创建用户表，使用`V2__add_project_file_storage.sql`新增项目和文件表。

## 6. 风险与取舍

| 风险 | 处理 |
|---|---|
| 并发注册相同邮箱或用户名 | 应用层检查，数据库唯一索引最终兜底 |
| 邮箱大小写导致重复 | 注册、登录和资料修改均规范化为小写 |
| 旧库迁移校验失败 | 重置旧数据库，不兼容已删除业务表 |
| 密码泄露 | 不保存明文，不在日志输出密码、哈希或 token |
| 路径修改导致对象搬迁 | 逻辑路径与稳定对象键分离，只修改MySQL元信息 |
| 并发覆盖文件 | `status`与`lock_version`共同抢占更新权 |
| MinIO覆盖成功但最终落库失败 | 文件进入`verify_required`，上传明细保留候选元信息 |

## 7. 验收标准

- 新数据库包含用户、最小项目、项目文件和上传追踪表；
- 可以注册多个邮箱不同的用户；
- 重复用户名或邮箱被拒绝；
- 登录只按邮箱查询；
- 表中不存在 `single_account_key`、`display_name`、`mobile` 和 `tenant_id`。
- 不存在文件版本表，内容更新始终覆盖稳定`object_key`。

## 8. 文件存储模型

### 8.1 层级

```text
pm_user -> pm_project -> business_code -> pm_project_file
```

`business_code`使用`project/user/system`枚举，不单独建表。

### 8.2 路径

- `relative_path`：用户和Agent看到的可变逻辑路径；
- `object_key`：`PM-AGENT/{ownerUserId}/{projectId}/{businessCode}/{fileId}`；
- 路径修改不改变`object_key`；
- MinIO桶名和预签名URL不进入文件表。

### 8.3 哈希

- `quick_fingerprint`：规范化路径、大小和源修改时间的SHA-256，不读取内容；
- `content_hash`：文件完整内容的SHA-256；
- 内容哈希相同则不写MinIO，内容哈希不同则覆盖原对象。

### 8.4 枚举

数据库保存字符串编码，Java分别使用`UserStatus`、`ProjectStatus`、`FileBusinessType`、`ProjectFileStatus`、`FileUploadStatus`、`FileUploadItemStatus`、`FileChangeAction`和`FileUploadSource`。
