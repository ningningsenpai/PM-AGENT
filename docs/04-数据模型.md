# 04 数据模型

## 1. 文档定位

本文档记录当前已落地的数据模型。项目文件上传规则以 [18-项目文件可靠上传模块设计](./18-项目文件可靠上传模块设计.md) 为准，字段以 Java 实体和最新 Flyway migration 为准。

## 2. 建模原则

1. MySQL 8 是用户、项目和项目文件元数据的准确数据源。
2. 系统支持多个用户，不增加租户字段或租户索引。
3. 普通业务表使用 MySQL 自增 BIGINT 主键。
4. 状态使用小写字符串编码。
5. 不保留文件历史版本。
6. 每个项目文件只保留一条 `pm_project_file` 记录。
7. 当前文件上传不使用批次根表、物理批次表、RabbitMQ 或 Outbox。

## 3. 表清单

| 表 | 职责 |
|---|---|
| `pm_user` | 用户认证和基础资料 |
| `pm_project` | 项目空间、所有者和初始化状态 |
| `pm_project_file` | 项目文件路径、指纹、上传状态和 MinIO 存储位置 |

## 4. 基础表

### 4.1 `pm_user`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 自增主键 |
| `username` | VARCHAR(64) | 全局唯一用户名 |
| `email` | VARCHAR(128) | 全局唯一登录邮箱 |
| `password_hash` | VARCHAR(255) | BCrypt 密码哈希 |
| `status` | VARCHAR(32) | `enabled / disabled` |
| `last_login_at` | DATETIME | 最近登录时间 |
| `created_at / updated_at` | DATETIME | 时间字段 |

不保留 `tenant_id`、`deleted`、`created_by` 或 `updated_by`。

### 4.2 `pm_project`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 自增主键 |
| `owner_user_id` | BIGINT | 项目所属用户 |
| `project_name` | VARCHAR(128) | 项目名称 |
| `status` | VARCHAR(32) | 项目状态 |
| `created_at / updated_at` | DATETIME | 时间字段 |

项目先写为 `initializing`，固定 `system/index.json` 同步上传成功后才进入 `active`。

## 5. 项目文件表

### 5.1 `pm_project_file`

| 字段组 | 字段 | 说明 |
|---|---|---|
| 归属 | `project_id`、`business_code` | 所属项目和业务类型 |
| 路径 | `relative_path`、`path_hash`、`file_name`、`extension` | 逻辑路径及其唯一标识 |
| 存储 | `storage_uuid`、`storage_name`、`object_key`、`minio_path` | Java 生成的 MinIO 存储位置 |
| 文件元数据 | `content_type`、`size_bytes`、`source_mtime_ms` | MIME、大小和源修改时间 |
| 指纹 | `quick_fingerprint`、`content_hash` | 快速比较和内容 SHA-256 |
| 生命周期 | `status`、`upload_status` | 文件业务状态和上传事实状态 |
| 失败信息 | `upload_attempts`、`last_error_code`、`last_error_message`、`last_failed_at` | 已有文件更新等流程使用 |
| 并发 | `lock_version` | 乐观锁版本 |
| 时间 | `created_at / updated_at` | 自动维护 |

关键索引：

```text
UNIQUE(project_id, business_code, path_hash)
UNIQUE(object_key)
INDEX(project_id, business_code, status)
INDEX(project_id, business_code, content_hash)
```

### 5.2 单文件上传状态

首次插入：

```text
status = uploading
upload_status = not_uploaded
upload_attempts = 1
```

MinIO 上传成功后：

```text
status = active
upload_status = success
```

MinIO 上传失败时不更新文件行，因此仍为 `uploading / not_uploaded`。

数据库继续保留 `retrying / failed` 等值供已有文件覆盖更新流程使用；新的首次单文件上传不写入这些值。

## 6. 索引与 MinIO

固定索引对象键：

```text
PM-AGENT/{ownerUserId}/{projectId}/system/index.json
```

- 项目创建时同步初始化该对象；
- 单文件上传不读取或修改该对象；
- 文件解析占位接口也不修改该对象；
- 解析状态和解析结果不存入 `pm_project_file`，后续实现时需单独设计解析模型；
- MinIO 对象键不由前端传入；
- 预签名 URL 不持久化。

## 7. Flyway 初始化

当前只保留 `V1__init_phase1_schema.sql`，它直接创建 `pm_user`、`pm_project` 和 `pm_project_file` 三张当前业务表。

- 不再通过连续 ALTER 和 DROP 得到最终结构；
- 不创建上传请求根表、物理批次表、任务旧表或 Outbox 表；
- 不初始化默认用户、示例项目或示例任务；
- 已执行过旧 V1～V13 的数据库不能直接升级到该基线，开发环境需要重建空 schema；
- 生产或共享数据库需要另行制定数据迁移方案。

## 8. 数据事实归属

| 判断 | MySQL 事实 |
|---|---|
| 项目是否可上传 | `pm_project.status = active` |
| 相对路径是否已占用 | `project_id + business_code + path_hash` 唯一约束 |
| 文件是否已上传 | `pm_project_file.upload_status` |
| 文件是否可用 | `pm_project_file.status = active` |

## 9. 验收标准

1. 当前业务表清单不包含上传请求根表和物理批次表。
2. 单文件首次落库为 `uploading / not_uploaded`。
3. MinIO 成功后更新为 `active / success`。
4. MinIO 失败时不再更新文件行。
5. 单文件上传不读写 Outbox 或索引。
6. `pm_project_file` 不包含解析状态、解析结果或详情引用字段。
7. Flyway 目录只包含一个直接创建当前结构的 V1 脚本。
