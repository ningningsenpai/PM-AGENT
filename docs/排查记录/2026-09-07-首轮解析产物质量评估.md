# 首轮解析产物质量评估：system-turn1

## 结论

本轮已经实现解析成功和产物完整落地，可以支持粗粒度的文件检索、用途说明和部分风险提示。内容质量尚不足以独立支撑精确源码定位、项目进度判断和自动采用项目规范。

需要同时改进提示词与流程。优先级最高的是证据定位、项目阶段信息传递，以及实现事实和项目规则的区分。提高 token 上限不能解决这些问题。

本次仅进行本地只读评估并编写报告，没有修改提示词或业务代码，没有调用真实模型，也没有改动两个 Assessment 样本目录。

## 主要问题

### 1. 切片行号错位，会直接影响原文证据读取

本轮所有 63 个切片的起止行都在对应文件行数范围内，但核实发现至少以下四处明显错位：

| 文件与切片 | 产物给出的行号 | 源码中的实际位置 |
|---|---|---|
| `StudentRepository.java` 姓名查询 SQL 注入 | 36—40 | 方法为 48—52，危险 SQL 在第 50 行 |
| `StudentController.java` 创建学生 | 30—35 | 42—46；产物行号实际上指向列表接口附近 |
| `App.tsx` 学生列表表格 | 60—80 | 表格主体为 101—117 |
| `App.tsx` 新建学生表单 | 100—120 | 136—148；产物行号实际上指向表格 |

证据示例：本轮 SQL 注入切片（本地产物：`agent-service/Assessment/test_turn/system-turn1/file_details/ad107f35c4ab431f-bafa60e7bcd2d9665c1e3b117df5a84a2b003bfafc5d5282dcf121d52ba378c4-ce037abec274cdbbd090dacdd48b0b6bf552f2ae019c7e7fc17da2bad912ecdc.json`，第 66 行）、[实际源码](../../agent-service/project_test/backend/src/main/java/com/ning/demo/student/student/StudentRepository.java#L48)。

本地调用现有 `RetrievalRanker.best_source_range` 和 `RawEvidenceLoader._source_slice` 验证，SQL 注入查询会按该切片截取第 36—40 行，得到字段和构造函数，而不是危险 SQL。这是对已有详情的定位与截取函数验证，不是一次完整在线 Agent 问答测试。

当前文本提取器保留原始文本，传给模型时没有行号锚点；行号由模型自由生成。下游会直接使用它，检查起止行未越界不足以发现语义错位。

**建议：提示词和流程一起改。** 服务端为源文本提供稳定的行号或段落 ID，模型引用已有锚点；返回后检查锚点是否包含声明的符号或证据。无法定位时返回未知状态，不能编造精确行号。源码引用应指向方法或语句的实际范围，而不是只保证数字合法。

### 2. 核心功能提取偏浅，部分用语扩大了已实现范围

`StudentController.java` 包含列表、详情、新增三个接口，本轮只生成一个创建接口切片。`App.tsx` 的 `role` 知道列表、搜索、新建和详情，但切片只保留表格和新建表单，没有描述加载、错误处理、新增后刷新、详情抽屉等交互。

`StudentRepository.java` 摘要写“实现 CRUD”，实际只实现查询和新增，没有更新、删除方法；`App.tsx` 的关键词也包含 `CRUD`。这种概括容易让下游误认为维护能力已经完整实现。

**建议：主要改提示词，辅以确定性覆盖检查。** 按文件类型提取接口、导出函数、核心交互、数据流和已知限制；摘要应写实际能力，例如“查询和新增”，明确区分已实现、计划和未确认。只对 Controller、主页面等关键文件要求覆盖所有主要入口，避免给每个小配置文件堆叠大量切片。

### 3. 风险识别有价值，但结构与证据强度不稳定

本轮明确识别了样本中的明文凭据、自增 ID 暴露、SQL 注入、宽松 CORS、鉴权及幂等缺失、个人信息未脱敏等问题。在样本声明的 R-01 至 R-07 中，前六类有明确发现；R-07“前端交互自动化覆盖不足”只在开发文档的泛化切片中被包含，没有形成具体风险结论。

需要改进的部分：

- `App.tsx` 直接展示电话、邮箱，但自身 `risk_flags=[]`，个人信息风险主要依赖接口/开发文档发现。
- `GlobalExceptionHandler.java` 没有记录未知异常日志；本轮没有指出这一点。Controller 与异常处理器分别生成新的 traceId，链路传递问题也未识别。
- 12 个风险项中 11 个是字符串。唯一对象使用 `type/description`，下游详情补充代码提取高权重风险字段时读取的是 `code`，因而本轮没有风险项能通过这一路径提供规范化风险码；风险正文仍会进入普通检索字段，并非完全不可检索。
- SQL 注入被记录为 `high`，参考样本和开发文档标为“严重”。如果风险等级要参与排序，应建立固定映射，不能由各文件临时选择标准。

**建议：同时改 Schema、提示词和项目级复核。** 风险项固定为对象，至少包含稳定风险码、等级、摘要、证据定位及判断依据。区分“文档声明存在风险”“直接代码证据”“需要跨文件确认”。代码中找不到鉴权注解不能单独证明全项目无鉴权；测试覆盖也必须结合完整文件清单判断。空数组应表示“本轮未发现”，不等于安全保证。

### 4. 关联项混用了文件路径、符号和目录

32 个关联项中，15 个可以直接匹配索引路径，17 个不能直接匹配。这 17 个不能全部算幻觉：其中有 Java 包相对路径、相对配置路径、目录、方法符号和原文里的名称。

典型例子：

- Controller 和 Service 使用 `com/ning/demo/.../Student.java`，缺少 `backend/src/main/java/` 前缀。
- `tsconfig.json` 使用 `./tsconfig.app.json`，需要按当前文件目录解析。
- HTML 使用 `/src/main.tsx`，这是前端资源路径，不是项目根目录文件路径。
- 开发文档关联项包含 `StudentRepository#searchByNameUnsafe`、`WebConfig`、`frontend/`。
- `StudentResponse` 在实际源码中不存在，但这个名字来自开发文档第 85 行，属于源文档与代码不一致，不能直接归为模型凭空生成。

**建议：主要增加服务端解析。** 保留原始引用，区分文件、目录、代码符号和外部资源；结合索引与当前文件路径生成规范路径、文件 ID 和解析状态。无法解析时明确标记，不伪装成已经确认存在的文件。当前在线召回主要把这些内容作为文本检索，尚不能把它当成可靠的依赖关系图。

### 5. 项目阶段信息在汇总环节丢失

本轮开发文档详情（本地产物：`agent-service/Assessment/test_turn/system-turn1/file_details/32e27bd3442342ad-c95ec0d8650a767c24af2c2a5f24bebe038d1ab3ee5e0fd256a1f0ecce5a93ce-97631594ac2a340eb499664de7e7f42f1ca85d58bea86c3f94290aaa7c1dd1a1.json`，第 56 行）已提取阶段一、二、三及 50%/30%/20% 信息，但项目规范（本地产物：`agent-service/Assessment/test_turn/system-turn1/project_specification.json`，第 6 行）的 `development_stage` 全为空。

原因可以定位到流程：[规范来源收集](../../agent-service/app/project_context/specification/service.py#L283)只传文件摘要和 `rule_candidates`，不传 `content_slices`。当前候选的五种分类不包含阶段事实；开发文档的摘要也没有保留具体阶段数据，因此模型在规范汇总时拿不到这部分信息。

**建议：必须改数据传递。** 单文件详情增加受约束的阶段/能力事实，或由服务端挑选阶段切片并附带来源送入汇总。记录阶段状态、目标、待办方向与证据，不把这些信息硬塞进编码规则。样本中的“整体约 50%”属于文档自述，应标记来源，不能声称是系统独立测量结果；也应避免“阶段一已完成 50%”这种把阶段占比和阶段完成状态混在一起的表达。

### 6. 项目规范混入实现事实，缺少去重和适用条件

72 条文件候选汇总为 57 条规范，所有规范均为 `active`，其中 50 条高置信度、7 条中置信度，`ignored_items=[]`。

数量多本身不等于质量差，但其中以下内容更接近实现事实，而非应约束未来开发的规范：

- “启动类位于包 com.ning.demo.student 下”。
- “服务层方法命名遵循 list/get/create 约定”。
- “使用 Java record 定义不可变数据模型”。
- “前端源代码位于 src 目录”。

一个类使用 record，不足以证明所有后续数据模型都必须采用 record。类似事实适合放在文件详情，晋升为全项目约束需要明确文档要求或足够的跨文件依据。

此外，`tech-student-auto-increment-id` 记录“学生表使用自增 ID 作为业务主键”，`risk-auto-increment-id-exposure` 又记录“对外业务主键不应直接使用自增 ID”，两者都处于 `active`。作为“当前实现”和“改进要求”可以同时成立，但目前没有结构化区分，容易被当作互相冲突的两条规范。H2/Spring Boot/API 响应结构/参数化 SQL 也存在重复或高度重叠条目。

**建议：提示词与汇总策略一起改。** 区分实现事实、明确约束、规划要求、整改建议和不确定推断；将开发环境、生产环境、模块范围和实施阶段写清楚。不要为了让每个文件都有候选而提炼规则。按主题、适用范围和来源合并重复项，并把有冲突或证据不足的候选保留为待确认。保留分批方案，避免最后又要求模型整份重写导致截断。

`document_rules=[]` 相比参考样本值得检查，但不应为了对齐参考样本的两条规则而强行补齐。应先确认原文是否明确要求文档区分已实现与规划、保留非生产警告；满足证据条件后再形成规则。

### 7. 输入过滤让测试源码缺席，却让构建缓存参与语义解析

本轮缺少 `backend/src/test/java/com/ning/demo/student/StudentControllerTest.java`。本轮 manifest 明确记录原因是“命中忽略目录：test”，不是模型漏读或详情文件丢失。

[测试扫描器](../../agent-service/tests/project_file_flow/manifest.py#L33)和前端上传筛选都忽略 `test/tests`；同时两个 `.tsbuildinfo` 构建缓存进入了解析。这会削弱系统对测试覆盖的判断，并增加低价值输入。

**建议：调整筛选和分流策略。** 保留测试源码，继续排除 `target`、`node_modules` 等产物；对 `.tsbuildinfo` 跳过或仅记录元数据。锁文件可先做确定性依赖摘要，再决定是否调用模型。不要把规则简单改成“忽略所有配置或锁文件”，它们仍可能包含有价值的版本和构建信息。

### 8. 时间与解析策略缺少可信的运行来源

项目规范及 57 条规则的 `updated_at` 全部为 `2026-09-07T22:28:06.774318`，早于本轮详情生成，且紧邻其他系统文件的初始化时间；本轮详情实际生成时间为 22:28:57—22:31:40，索引更新时间为 22:36:10。现有规范写入直接保存模型输出的时间，推测沿用了初始对象值，不能可靠反映本轮更新。

本轮 `.tsbuildinfo` 详情中还出现模型填写的 `parser.strategy=metadata_only`；这个值来自语义输出，不能作为实际没有调用 LLM 的运行证据。

**建议：由服务端记录元数据。** 服务端生成更新时间、实际解析策略、模型标识、Prompt/Schema 版本和运行 ID。Prompt 变更后应能选择需要重新解析的文件；现有“有详情就跳过”机制会让旧版产物长期保留，单靠调整提示词不会自动升级已有详情。

## 用户习惯和记忆是否缺失

本轮存在五类用户习惯文件以及长短期记忆文件，但对应数组均为空，`update_journal.jsonl` 也是空文件。它们是初始化占位产物，不能理解成已经完成行为学习或记忆提炼。

这符合当前文件解析流程：本轮主要生成文件详情、项目规范和索引。不能从用户上传的项目文件擅自推断其生活习惯、工作偏好或对话记忆，也不应把这些空内容算作本轮质量缺陷。

## 下一轮固定评估问题

1. 学生管理有哪些已实现接口，哪些尚在规划？必须区分查询/新增与编辑/删除。
2. SQL 注入具体在哪个方法、哪一行？必须指向真实拼接 SQL。
3. 新增学生成功后前端做了什么？应识别关闭表单、选中新记录和刷新列表。
4. 当前处于哪个阶段，整体约完成多少？应给出文档依据，并区分自述与测量。
5. 电话、邮箱在哪里暴露？应同时追溯接口文档和前端显示位置。
