## 原因一：关联文件元素类型不符合约定

九个文件均出现 `FileDetailSemanticOutput` 校验错误：字段位置为 `related_files` 的数组元素，错误类型为 `dict_type`。模型请求返回 HTTP 200，结束原因为 `stop`，不是本次调用超时或生成截断。

| 文件 ID | 项目内路径 |
|---|---|
| 49 | `backend/src/main/java/com/ning/demo/student/common/GlobalExceptionHandler.java` |
| 54 | `backend/src/main/java/com/ning/demo/student/student/StudentController.java` |
| 56 | `backend/src/main/java/com/ning/demo/student/student/StudentService.java` |
| 63 | `frontend/index.html` |
| 67 | `frontend/src/api.ts` |
| 66 | `frontend/src/App.tsx` |
| 68 | `frontend/src/main.tsx` |
| 72 | `frontend/tsconfig.app.tsbuildinfo` |
| 74 | `frontend/tsconfig.node.json` |

服务端要求 `related_files: list[dict[str, Any]]`，但原 Prompt 只要求“路径关系”，示例只给空数组，没有说明非空元素的结构。因此模型可能返回路径字符串数组，而服务端要求对象数组。

日志能够确认元素不是字典，但没有记录原始输出值，不能仅凭日志确认实际元素一定是字符串。路径字符串是结合 Prompt 缺口推断的最可能情况。

修复措施：

1. Prompt 明确要求对象数组并提供 `path`、`relation` 示例；没有可确认关系时使用空数组。
2. 在语义模型校验前，将非空字符串元素转换为 `{"path":"原路径"}`；不生成不存在的关系信息，不丢弃非法元素。
3. 保持字典元素和存储格式兼容，继续拒绝空字符串、数字、空值、嵌套数组及超出五十项的数组。
4. 校验日志增加 `inputType`，只记录类型名称，便于下次区分字符串、空值和其他错误，不输出正文或敏感值。

## 原因二：项目规范生成达到输出上限

22:09:38 的规范生成日志明确记录：

```text
schema=ProjectSpecificationDocument
maxTokens=16384
finishReason=length
contentChars=44500
reasoningChars=0
outputTokens=16384
```

这次请求也已获得 HTTP 200，但正文生成耗尽输出额度。生成器正确拒绝不完整结果，业务层返回 `PROJECT_SPECIFICATION_BUILD_FAILED` 并保留原规范。

该错误与九个文件的 `related_files` 错误独立。原流程把全部有效详情的候选和旧规范交给一次生成，输出规模随规则数量增长。提高超时时间无法解决输出 token 截断；仅提高 token 上限也没有限制不断增长的单次汇总规模。

修复措施：

1. 每批最多十二条候选，并按估算的来源文本长度继续拆批；单个大文件也可以拆分，所有候选均参与处理。
2. 每批只生成新增或修改的规则，以此前合并结果作为上下文，复用稳定规则 ID。
3. 服务端合并各批次，保留旧规则、未返回的开发阶段字段、变更记录和忽略项。
4. 批次截断时丢弃不完整输出，二分候选后重试；最小批次仍失败则终止，避免无限重试。
5. 所有批次完成、来源复核完成后才发布规范；任何批次失败都不覆盖旧对象。

重新启动后端或确认源码热重载已经完成，然后使用现有测试配置执行：

```powershell
& $flowPython $flowScript files
& $flowPython $flowScript parse
& $flowPython $flowScript files
```

保持 `forceAnalysis=false` 时，已成功且有 `detail_ref` 的文件会被跳过，缺少详情且 `parse_attempts < 3` 的文件会重新分析。即使没有待分析文件，规范和索引刷新仍会执行。

如果失败文件已经达到三次尝试，普通解析会跳过它们。当前接口的 `force=true` 会重新分析整个项目中符合基础条件的文件，并非只重试失败文件；使用前应结合文件列表确认范围。此次修复不自动改写尝试次数，也不更改现有测试环境配置。

检查下一轮结果应同时满足文件失败数为零、项目规范更新成功、索引更新成功；服务端会新增 `project.specification.batch` 日志，显示批次、候选数和截断拆分情况。
