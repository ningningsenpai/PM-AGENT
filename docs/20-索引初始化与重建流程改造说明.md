# 索引初始化与批次上传链路落地说明

## 1. 文档说明

本文档记录本次项目文件批次上传、请求级完成闸门和同步索引重建的实际落地结果。

业务规则以 [18-项目文件批次上传模块设计](./18-项目文件可靠上传模块设计.md) 为唯一权威，MinIO 与索引细节见 [19-项目上下文索引与MinIO存储设计](./19-项目上下文索引与MinIO存储设计.md)。

## 2. 本次落地范围

| 模块 | 落地内容 |
|---|---|
| 前端 | 空文件和目录规则筛选、最多 50 个文件且不超过 240 MB 的双阈值分批、manifest/batch 构造、同轮逐批顺序调用、最多三轮失败重试 |
| Java 接口 | 固定批次上传路径，接收 `manifest`、`batch`、`files` |
| Java 服务 | manifest 校验、批次预注册、文件首次落库、批次内多线程上传、本轮完成判断、失败文件响应 |
| MySQL | 上传请求根表、批次轮次字段、文件请求关联、`not_uploaded`、可空存储字段和相关索引 |
| MinIO | 项目初始索引、成功文件对象、请求终态后的同步索引重建 |
| 消息 | 移除文件业务 MQ、消费者、事件和 Outbox 代码依赖，保留 RabbitMQ 基础配置 |

## 3. 总体流程

~~~mermaid
flowchart TD
    A["创建项目"] --> B["同步初始化 system/index.json"]
    B --> C{"项目是否 active"}
    C -->|否| D["拒绝上传"]
    C -->|是| E["前端筛选文件<br/>按最多 50 个且不超过 240 MB 分批"]
    E --> F["生成完整 manifest 和各 batch"]
    F --> G["逐批顺序调用<br/>等待当前批次响应后再提交下一批"]
    G --> H["首个请求创建上传根记录<br/>预注册 manifest 中全部批次为 waiting"]
    H --> I["各请求抢占自己的批次<br/>waiting → processing"]
    I --> J["第一轮落库 not_uploaded<br/>重试轮复用已有文件行"]

    K --> L["成功回填存储字段<br/>失败文件行保持不变"]
    L --> M["批次 processing → completed"]
    M --> N{"预注册批次数和 completed 批次数<br/>是否都等于 totalBatchCount"}

    P -->|否| Q["请求 completed"]
    P -->|是且未满三轮| R["请求 awaiting_retry"]
    R --> G
    P -->|是且第三轮| S["请求 completed_with_failures"]
    Q --> T["同步 rebuild index.json"]
    S --> T
    T --> U{"索引是否成功"}
    U -->|是| V["写 index_rebuilt_at"]
    U -->|否| W["接口失败<br/>终态不变且时间为空"]
~~~

## 4. 固定接口合同

~~~http
POST /api/v1/projects/{projectId}/file-ingest-batches/concurrent-uploads
Authorization: Bearer <token>
X-Trace-Id: <trace-id>
X-Idempotency-Key: <与 batch.idempotencyKey 一致>
Content-Type: multipart/form-data
~~~

Multipart 名称：

| Part | 说明 |
|---|---|
| `manifest` | 当前轮全局清单 JSON |
| `batch` | 当前物理批次 JSON |
| `files` | 当前批次文件数组 |

manifest：

~~~json
{
  "userId": 1,
  "projectId": 10,
  "requestId": "upload-request-uuid",
  "executionStatus": "initial",
  "attemptNo": 1,
  "originalTotalFiles": 120,
  "roundTotalFiles": 120,
  "totalBatchCount": 3,
  "batches": [
    {"batchId": "batch-1", "fileCount": 50},
    {"batchId": "batch-2", "fileCount": 50},
    {"batchId": "batch-3", "fileCount": 20}
  ]
}
~~~

batch：

~~~json
{
  "userId": 1,
  "projectId": 10,
  "requestId": "upload-request-uuid",
  "attemptNo": 1,
  "batchId": "batch-1",
  "idempotencyKey": "batch-idempotency-uuid",
  "fileCount": 50,
  "files": [
    {
      "clientFileId": "client-file-uuid",
      "businessCode": "project",
      "relativePath": "backend/src/main/App.java",
      "fileName": "App.java",
      "sizeBytes": 1024,
      "sourceMtimeMs": 1784400000000
    }
  ]
}
~~~

## 5. 前端落地

主要位置：

| 文件 | 作用 |
|---|---|
| `frontend/src/modules/project/file-upload.ts` | 文件筛选、50 个/240 MB 双阈值分批、manifest 和 batch 构造 |
| `frontend/src/modules/project/api.ts` | Multipart 组装、固定路径和批次幂等请求头 |
| `frontend/src/modules/project/types.ts` | 接口合同和状态类型 |
| `frontend/src/modules/project/components/project-file-upload-card.vue` | 文件夹选择、同轮逐批顺序调用、失败聚合和三轮控制 |

落地规则：

- 空选择和筛选后为空不调用上传接口；
- `PROJECT_FILE_BATCH_SIZE = 50`；
- `PROJECT_FILE_BATCH_MAX_BYTES = 240 * 1024 * 1024`，为后端 `256 MB` Multipart 请求上限预留开销；
- 加入下一文件会突破数量或大小任一阈值时先结束当前批次；普通源码项目通常先达到 50 个文件阈值；
- `PROJECT_FILE_MAX_ATTEMPTS = 3`；
- 同一轮所有请求携带相同 manifest；
- 使用循环加 `await` 逐批顺序调用并收集响应，本轮结束后聚合失败文件；
- HTTP 异常时以同一批次和幂等键原样补发两次，仍失败则中断且不增加上传轮次；当前 MVP 不跨页面持久化文件对象和上传会话；
- 只有成功响应中的 `failedFiles` 进入下一轮；
- 重试保留 `requestId` 和 `clientFileId`，重新生成批次 ID 与幂等键。

## 6. Java 落地

主要位置：

| 文件 | 作用 |
|---|---|
| `ProjectUploadManifestRequest.java` | manifest 合同与校验 |
| `ProjectUploadBatchRequest.java` | batch 和文件描述合同 |
| `ProjectFileUploadResponse.java` | 批次响应与失败文件 |
| `ProjectFileBatchUploadService.java` | 请求、批次、文件、线程池和完成闸门主流程 |
| `ProjectFileUploadCompletionService.java` | 请求终态后的同步索引重建与时间回填 |
| `ProjectFileIngestBatchController.java` | 固定 HTTP 入口 |
| `FileUploadExecutorConfig.java` | 批次内文件上传线程池 |

后端处理：

1. 校验路径项目、登录用户、manifest 和 batch 一致；
2. 校验同轮 manifest 哈希；
3. 根据 manifest 预注册全部 `waiting` 批次；
4. 当前调用抢占自己的批次为 `processing`；同幂等键的 `processing` 批次超过默认 15 分钟后可接管，并跳过本批已成功文件；
5. 第一轮插入 `not_uploaded` 文件，重试轮按 `clientFileId` 复用；
6. 当前批次文件在线程池中并发上传一次；
7. 成功后回填存储字段，失败不更新文件行；
8. 批次写入统计并变为 `completed`；
9. 查询当前轮预注册和已完成批次数；
10. 最后一批完成时校验文件事实总数及 `success + not_uploaded` 状态分布均等于 `original_total_files`；
11. 完整性校验通过后更新请求状态，并在终态同步重建索引。

## 8. 完成闸门落地

当前实现不在上传请求表保存批次完成计数，而是查询物理批次表：

~~~text
registeredBatches = 当前请求和轮次下的全部批次数
completedBatches = 当前请求和轮次下 status=completed 的批次数
~~~

两者都等于 `round_total_batches` 时，本轮才结束。

随后查询文件表。仅当“文件事实行总数等于 `original_total_files`”且“`success + not_uploaded` 等于 `original_total_files`”时才允许进入下列状态判断；否则按数据冲突拒绝进入终态。

| 条件 | 请求状态 |
|---|---|
| 未上传数为 0 | `completed` |
| 未上传数大于 0 且轮次小于 3 | `awaiting_retry` |
| 未上传数大于 0 且第三轮 | `completed_with_failures` |

## 9. 索引重建落地

`ProjectFileUploadCompletionService` 在请求进入终态后同步调用 `ProjectIndexService.rebuild()`：

- 成功后写 `index_rebuilt_at`；
- 失败时当前接口失败；
- 请求终态不回滚；
- `index_rebuilt_at IS NULL` 表示索引待恢复；
- 不为索引失败增加请求状态。

索引完全由 MySQL 当前文件数据构造：

- `success` 文件进入正常列表；
- 终态 `not_uploaded` 文件进入 `upload_failures`。

## 10. RabbitMQ 与 Agent

本次落地删除文件上传相关：

- 完成事件；
- 文件解析事件；
- 文件业务拓扑；
- Java 文件业务生产者和消费者；
- Outbox 运行时代码。

RabbitMQ 只保留基础连接配置。`ProjectFileUploadCompletionService` 是未来接入 Python 的唯一扩展点，当前没有 MQ 副作用。

## 12. 验收标准

1. 接口路径、Multipart 名称和 DTO 字段与本文一致。
2. 前端同轮批次逐批顺序发送，单批最多 50 个文件且原始文件总大小不超过 240 MB。
3. 第一轮预注册全部物理批次。
4. 文件首次落库为 `not_uploaded` 且存储字段为空。
5. 上传失败不更新文件行。
6. 完成闸门先通过批次查询统计判断，再校验文件事实总数与状态分布完整性。
7. `processing` 超过默认 15 分钟时，只有相同幂等键可以接管，且不得重复 PUT 本批已成功文件。
8. 已完成批次必须在文件身份、归属、元信息和内容哈希均一致时才返回已有结果。
9. 请求只使用四种状态。
10. 索引失败以终态加空 `index_rebuilt_at` 表示。
11. 当前链路无文件业务 MQ 或 Outbox。
